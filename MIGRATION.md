# Міграція v3 → v4

Код переноситься з `v3/packages/factory/src` копією. Нове пишеться тільки на швах: порт, тестова обгортка, тип замість важкого імпорту. Кожен шов — окремий коміт і рядок нижче.

Перевірка кроку: `pnpm verify` (типи разом із тестами, тести, звірка кількості тестів з v3 за `migration/test-pairs.tsv`).

## Прибрані інтеграції

v4 лишає GitHub і GitLab. Linear, Jira, incident.io, Slack і WorkOS прибрано на вимогу (у git історія збережена, коміт «drop integrations»):

- пакети `integration-{linear,jira,incidentio,slack,workos}` видалено разом із тестами (пари тестів прибрано з `test-pairs.tsv`);
- `factory.ts` більше не ставить Platform-версії Linear, Jira, incident.io;
- з наскрізних тестів прибрано кейси, що їх кликали (`default-handlers` −3, `issue-reconciler` −1);
- WorkOS-інтеграцію у v3 ніхто не імпортував; вхід через WorkOS лишається в `@factory/auth`;
- Slack у v3 ставив хост (`apps/server`), не пакет.
- UI підключення Slack і Connected Accounts прибрано разом із ClickUp-інтеграцією (коміт `962a7d5`): `SlackConnectionPage`, `ConnectedAccountsSection`, `channelAccounts` видалено з тестами, їхні пари прибрано з `test-pairs.tsv`; `IntakeSection` +5 тестів ClickUp, ще +1 на правила статусів ClickUp (`d85dd0c`).
- Налаштування › Надходження задач тепер лише ClickUp: одна секція замість трьох, кожен підключений List — картка, що розгортається (дошка, статуси таблицею з «Типовим набором», маршрути за тегами згорнуті), вибір Lists у діалозі. UI GitHub- і GitLab-інтейку (`GithubLabelRouting`, `LinearRouting`, секції GitHub/GitLab у `IntakeSection`, їхні тести й переклади) прибрано. Бекенд, маршрути та збережені налаштування GitHub/GitLab не чіпали: наявна конфігурація працює на сервері, але налаштувати її з UI більше не можна.

### Словник Linear/Jira/incident.io

Власник вирішив: Linear, Jira, incident.io не підтримуються. Прибрано решту словника:

- `core`: джерела `linear-issue`/`jira-issue`/`incidentio-follow-up` і `linearIssue`/`jiraIssue`/`incidentioFollowUp`, `FACTORY_{LINEAR,JIRA,INCIDENTIO}_EVENTS`, контексти правил, ключі `BoardEventRules`, типи ingress;
- `pipelines`: обробники тріажу Work для них, гілки `factory/linear-*`/`jira-*`/`incidentio-*`;
- `store`/`session`/`api`/`harness-mastra`: мапа «проєкт Linear → репозиторій» (`repositoryByLinearProject`, параметр `intake` у `FactoryStartCoordinator` і `prepareFactoryRuleBinding`), заглушки `/web/linear/status`, `/web/jira/status`, провайдери Jira й incident.io в `PLATFORM_CONNECT_PROVIDERS`;
- `apps/server`: змінні `LINEAR_*`, `JIRA_*`, `INCIDENT_IO_API_KEY` у `.env.schema`;
- `apps/ui`: налаштування надходження, фільтр за проєктом Linear, крок онбордингу «Connect your work», дані й іконки Linear/Jira/incident.io;

Збережені картки з такими джерелами не ламаються: `workItemSource` повертає `manual` для невідомої інтеграції, відкладене рішення зі старим джерелом не проходить перевірку і падає як звичайна помилка рішення. Міграції бази нема.

Тести: пакети −7 (`default-handlers` −2, `factory.test` −3, `work-item-branch` −1, `platform-connect-routes` −1); UI −121 (4 файли видалено: −34, решта −88, +1 тест на стару картку). Тести, що перевіряли спільну логіку через Linear, переведено на GitLab/GitHub. `Slack-thread` лишився: UI показує такі картки.

## Прибрано: особисті моделі й пам'ять

Фабрика належить організації (рішення власника). Кожна інтерактивна сесія, запуск картки й хід Supervisor беруть ключі організації, модель за замовчуванням Фабрики й її налаштування пам'яті. Вибору області нема.

- `modelScope` (`factory | user | hybrid`) прибрано з `FactoryProject`, контрактів створення й PATCH проєкту, `effectiveModelScope` видалено. Колонку `model_scope` не читають і не пишуть.
- Політика ключів (`credential-policy`) завжди дає область організації, зокрема для чатів поза Фабрикою. Middleware підготовки ключів готує лише її. Каталоги моделей і список провайдерів показують лише ключі організації. Новим відповідям `credentialOwnerId` не ставиться.
- Ключі провайдерів і OAuth-входи: лише рядки організації й лише для адміністраторів організації. Параметр `scope` ігнорується.
- Особиста модель за замовчуванням: маршрути `/web/config/default-model` (GET, PUT, DELETE, `apply`) видалено. Домен `model-defaults` більше не реєструється й не передається інтеграціям. Модель сесії — `defaultModelId` Фабрики, без нього — модель режиму сервера.
- Особиста пам'ять: маршрути `/web/config/om*` вимагають `factoryId` (інакше 400 `factory_id_required`) і пишуть лише рядок Фабрики. `layerPersonalMemorySettings` прибрано. Сесія поза Фабрикою працює на типових порогах, назви тредів беруть рядок Фабрики сесії.
- Базу не чіпали. Таблиці `user_default_models`, особисті рядки `model_credentials` і `memory_settings` лишаються як були, їх просто не читають.
- Без змін лишились `TenantCredentialStore` з двома областями SDK (Фабрика ніколи не просить `user`), поля `userCredential` і `stored-user` у `ProviderInfo` (тепер завжди порожні) та показ старих підписів «Ваш …» на давніх відповідях.

Тести (дельти в `test-pairs.tsv`): `projects/model-scope.test.ts` видалено (тестував `effectiveModelScope`), `projects/base` −1, `credential-policy` −6, `default-model-hydration` −3, `factory-session` −3, `memory-settings-hydration` −2, `session-tools` −2, `start-coordinator` −1, `config` −6, `session-model-catalog` −1. UI: прибрано «Ваші моделі», «Ваша пам'ять», вибір області (налаштування, онбординг), футер області в пікері, особисту модель за замовчуванням; вхід у провайдера веде в моделі Фабрики. Видалено тести `use-default-model`, `DefaultModelSection`, `FactoryModelScopeNotice`, `FactoryModelScopeSection`; `ModelPicker` −7, `EmptyFactoryState` −6, `ProviderAccessSection` −3, `SettingsScopesPage`, `FactoryDefaultModelSection`, `OnboardingPreview`, `ProviderConnectionMethods`, `ProviderConnectionRecovery` по −1.

## Борг типів у тестах

`core`, `pipelines`, `store`, `runtime`, `internal-workspace`: тести тайпчекаються, борг нуль.

`platform`: `check` перевіряє лише код, як у v3. `pnpm --filter @factory/platform check:tests` рахує помилки типів у тестах: зараз 794. Борг закривається, коли пакет виходить із `platform`.

`platform/src/session/source-control-tools.test.ts`: блок зі справжнім git отримав таймаут 30 с (у v3 — 5 с за замовчуванням), бо під повним паралельним прогоном окремі кейси йдуть кілька секунд і вилітали.

### Bug злито у Work (2026-10-29)

Рішення власника: окрема дошка — лише для іншого процесу (інший результат, тригер чи ворота), а не для типу задачі. Тип задає тріаж. Коли тест перед кодом потрібен і багам, і фічам, Bug відрізнявся від Work лише скілами, тож дошку прибрано.

- **Work:** нова фаза `tests` (роль `tester`) між `planning` і `execute`, `reproductionTest: { record: 'tests', protect: 'execute' }`. Test-first типи — `bug` і `feature request` (`TEST_FIRST_TRIAGE_TYPES`): затверджений план веде в `tests`, агент потрапляє в `execute` лише з `tests` із записаним тестом або назад з `review`. Інші типи — як у v3: `planning` → `execute`. Входу в `tests` діють ворота Building (затвердження плану; людина для не-бага). Перевірки Work (картка, відкладена self-review для людини, тощо) відповідають раніше за test-first.
- **Скіли за `triageType`:** `planning` — `bug-plan` для бага, `factory-plan` для решти; `tests` — `bug-test` / новий `factory-test`; `execute` — `bug-build` для бага, промпт для решти. `factory-plan` отримав розділ **Test plan** і перехід у `tests` для фічі. `bug-triage` видалено: тріаж у Work один, `factory-triage`.
- **Шов у core:** `FactoryRuleItemContext.triageType` (необов'язкове). `transition-service` ставить `item.triageType ?? request.triageType` (вихід із Triage записує класифікацію вже після знімка), `harness-mastra` `processor` — для правил інструментів (`submit_plan` вибирає `tests` чи `execute`).
- **Claude Code:** `createClaudeBoundTools` отримав `checkoutFor` — git для запису й захисту тесту йде в теку сесії на хості. Без цього тестер на Claude-фабриці не міг записати тест, а білдер — вийти з `execute` (діра була й у дошці Bug).
- **Хост:** `boards: [acceptanceBoard]`. Маршрут мітки на дошку, якої нема, падає на звичайну логіку (прив'язка або Work); у локальній базі карток і маршрутів на `bug` не було, міграції нема.
- **Тести:** `pipelines/src/bug/*` (2 файли) → `pipelines/src/work/test-first.test.ts` (15, разом із фічею, docs і порядком перевірок); `server/src/rules/bug-board-runtime.test.ts` → `work-board-runtime.test.ts` (наскрізний прогін бага через Work); у `default-handlers.test.ts` Bug-кейси change request тепер на власній тестовій дошці; новий `server/src/claude/bound-tools.test.ts` (справжній git: запис тесту, зміна тестового файлу блокує вихід, фікс проходить). `claude-work-board-runtime.test.ts`: план бага тепер `bug-plan`.

Новий режим, у v3 не було. `GithubTokenIntegration` — підклас `GithubIntegration`, де токен App замінено одним access token (`GITHUB_ACCESS_TOKEN`, лише коли група `GITHUB_APP_*` неповна); webhook-ів нема, лише опитування.

### Claude Code: тека на сесію і вхід Claude, який тримає сервер (2026-11-02)

У v3 і в upstream сесії Claude Code писали в спільний `~/.claude` сервера (транскрипти, автопам'ять, налаштування всіх сесій разом), а вхід був або токеном `claude setup-token`, або особистим логіном машини. Ні upstream, ні Paperclip не зберігають справжній логін Claude так, щоб він пережив кілька пісочниць чи реплік.

- **Тека на сесію:** `server/src/claude/config-dir.ts`. Кожна сесія (і Factory chat) отримує свій `CLAUDE_CONFIG_DIR` у `<storeDir>-config/<ім'я сесії>-<hash>` з `.claude.json` `{ hasCompletedOnboarding: true }`, сталий між ходами (`--resume`). Без `storeDir` чи `sessionConfigRoot` харнес не стартує: спільного `~/.claude` більше нема. Сесія, що ходила на `~/.claude` до цієї зміни, теж отримує свою теку; її `--resume` там не знаходиться, і харнес починає нову розмову Claude (`unknown_session` → fresh, `harness-claude-code`), тред Фабрики лишається. Видалення сесії видаляє теку: `SessionRetirementCoordinator` має хук `onSessionDeleted`, а `/web/user-sessions/:id` DELETE без координатора кличе `onSessionDeleted` маршрутів (збій прибирання лише логується).
- **Env:** `CREDENTIAL_ENV_KEYS` додатково не пропускає з env сервера `AWS_BEARER_TOKEN_BEDROCK` і `CLAUDE_SECURESTORAGE_CONFIG_DIR`. `harness-claude-code` ставить `CLAUDE_SECURESTORAGE_CONFIG_DIR` = тека сесії разом із `CLAUDE_CONFIG_DIR`: у CLI 2.1.316 непорожнє значення дає окремий запис Keychain `Claude Code-credentials-<sha256(тека)[:8]>` і `<тека>/.credentials.json`, тож стандартний логін (`~/.claude`, Keychain `Claude Code-credentials`) CLI не читає ніколи. Авторизація — лише з БД (акаунти й ключ організації); без них хід падає з «Sign in to Claude… under Settings → Models → Claude Code accounts», і локально теж: запасного особистого логіну (`LOCAL_LOGIN_CREDENTIAL_ENV`, фіча `claudeCodeLocalLogin`, рядок «Uses your `claude` login on this machine») більше нема. `localDevelopment` лишився тільки для входу через Claude.
- **Новий вид акаунта `claude_login`** (`store/src/credentials/accounts.ts`): особистий, як `subscription` (лише його власник; у ротації поруч із підписками). Шифрований секрет — `{ secret: accessToken, oauth: { accessToken, refreshToken, expiresAt, scopes, subscriptionType, email, accountUuid, organizationUuid } }`; без зміни схеми таблиці; підказки нема, бо токен міняється. `refreshAccountOAuth` оновлює пару під `updateAtomic` рядка й перечитує її під блокуванням, тож паралельні ходи й репліки оновлюють один раз.
- **Оновлення лише на сервері** (`server/src/claude/oauth.ts`): перед ходом, якщо до кінця access-токена менше 10 хв, `POST https://platform.claude.com/v1/oauth/token` (`grant_type=refresh_token`, `client_id=9d1c250a-e61b-44d9-88ed-5944d1962f5e`, form-encoded) — значення з бінарника CLI 2.1.316 і з Orca. Хід отримує лише `CLAUDE_CODE_OAUTH_TOKEN=<accessToken>`. 400/401 вимикає акаунт з «sign in to Claude again», хід іде на наступний акаунт; 5xx/мережа — хід падає, акаунт лишається.
- **Вхід** (`server/src/claude/sign-in.ts`): сервер запускає `claude auth login --claudeai` з `CLAUDE_CONFIG_DIR` = `CLAUDE_SECURESTORAGE_CONFIG_DIR` = тимчасова тека, читає пару (macOS: Keychain `Claude Code-credentials-<sha256(тека)[:8]>`, інакше `<тека>/.credentials.json`) і хто увійшов (`<тека>/.claude.json` `oauthAccount`), зберігає як `claude_login` (новий вхід у той самий акаунт Claude замінює пару). Завжди видаляє тимчасовий запис Keychain і теку; стандартний запис `Claude Code-credentials` читає до й повертає після, бо вхід може його перезаписати (як Orca). Маршрути `POST/GET/DELETE /web/config/providers/anthropic/accounts/sign-in[/:id]`; лише в локальній розробці (браузер відкривається на машині сервера), фіча `claudeSignIn` у `/web/config/features`.
- **UI:** «Увійти через Claude» в Налаштування → Моделі → Акаунти Claude Code і на кроці Claude Code при створенні Фабрики, коли акаунтів нема; стан входу опитується; акаунт показується як «Ваш вхід Claude», відмовлений — «Увійдіть знову».
- **Тести:** без запасного логіну — `credentials.test.ts` (три кейси переписано на «немає акаунта → помилка»), `harness.test.ts` +1 (без кореня тек не стартує), `config-dir.test.ts` і `harness.test.ts` (стара сесія отримує теку), `session.test.ts` (`CLAUDE_SECURESTORAGE_CONFIG_DIR`), `source-control-sessions.test.ts` +1 (DELETE без координатора), `CreateFactoryFlow.msw.test.tsx` (кейс про локальний логін переписано). `server/src/claude/sign-in.test.ts` (10), `credentials.test.ts` +6, `harness.test.ts` +3, `store/.../accounts.test.ts` +1, `credentials/.../credential-accounts.test.ts` +1, `api/src/credential-accounts.test.ts` +4, `harness-claude-code/src/cli.test.ts` +1, `sandbox/src/session-retirement.test.ts` +1, `ClaudeAccountsSection.msw.test.tsx` +3, `CreateFactoryFlow.msw.test.tsx` +1.
