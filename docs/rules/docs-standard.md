# Стандарт документації проєкту

Обов'язкове правило для кожного проєкту, з яким працює фабрика, і для документації самої фабрики. Рішення — [ADR-0005](../adr/0005-docs-standard.md). Як цей стандарт використовують дошки — [features/product-board](../features/product-board/design.md) і [features/work-board](../features/work-board/design.md).

## Принципи

1. **Одна папка на проєкт**: окремий репозиторій docs (кілька репозиторіїв коду) або одна папка в репозиторії (монорепо). Ніколи не ділиться на бек / фронт / мобілку — інакше ламаються зв'язки.
2. **Одна правда.** Потік лінійний: `blackbox` → дослідження → бриф → специфікація → задачі → код. Двох описів однієї речі нема.
3. **Правда — по областях системи, зміни — окремо** (модель [OpenSpec](https://github.com/Fission-AI/OpenSpec)): `features/<область>/design.md` описує, як область працює *зараз*; кожна зміна — дельта до неї, яка після реалізації вливається в правду.
4. **Документи як код**: гілка, коміт на коло правок, один чернетковий PR/MR на зміну до кінця Фаз; агент не мерджить; історія git = версії.
5. **Агенти «Розробки» бачать документацію**: репозиторій docs позначено «в середовищі» (`inEnvironment`).

## Розкладка

```
docs/
  README.md                       індекс + огляд системи
  blackbox/                       історія: звідки взялось, хто вирішив, коли. Лише додається
    README.md · TIMELINE.md
    events/                       подія докладно
    sources/                      дослівно: чати, листи, дзвінки, вигрузки (колишні raw/, requests/)
    artifacts/                    файли від клієнта / клієнту + MANIFEST.md
    registers/                    decisions.md (DEC-nnn), commercial.md, documents.md,
                                  scope-history.md, open-questions.md
  features/
    INDEX.md                      список областей
    <область>/design.md           ПРАВДА: як область працює зараз
  changes/
    <YYYY-MM-DD>-<зміна>/         одна зміна = одна картка «Продукту»
      research.md · requirements.md · feedback/ · design.md (дельта) · tasks.md
    archive/                      завершені зміни
    backlog.md                    відкрите й відкладене, що ще не стало зміною
  bugs/
    README.md                     індекс
    <id>.md                       симптом → причина → як знайшли → варіанти → виправлення → перевірка
    <YYYY-MM-DD>-qa-round-<n>/    QA-раунд
  audits/                         аудити з датою: безпека, логи, код, покриття
  rules/                          обов'язкові правила
  runbooks/                       як робити: деплой, реліз, інциденти, міграції
  client/                         що ми видаємо клієнту
    deliverables/                 брендовані PDF і сторінки, як видано
    to-sign/                      надіслано на підпис
    signed/                       підписане: заморожені транскрипції (оригінал — PDF у blackbox/artifacts)
  design/                         візуальний і UX-дизайн: вайрфрейми, Figma, прототипи, рев'ю дизайну
  tools/                          скрипти, що підтримують документацію
  repositories/                   огляд кожного репозиторію
  GLOSSARY.md
  adr/                            великі технічні рішення; посилаються на DEC-nnn
```

Розділ, якому нема чого містити, не створюється порожнім; `README.md` проєкту каже, яких розділів нема і чому.

## Хто куди пише

| Хто | Пише | Не чіпає |
| --- | --- | --- |
| «Продукт» | `changes/<зміна>/`, рядок своєї зміни в `features/INDEX.md` (без питань), нові файли в `blackbox/sources|artifacts`, рядки `TIMELINE`/`events`, `GLOSSARY.md`, `adr/`; записи в `registers/` — лише після підтвердження людини | `features/<область>/design.md` (крім відсутнього базового опису), `bugs/`, `audits/`, `rules/`, `runbooks/`, `repositories/`, `client/`, `design/`, `tools/`, наявні записи `blackbox/` |
| «Розробка»: задача docs-sync зміни | вливає дельту зміни в `features/<область>/design.md` з того, що реально збудовано, переносить зміну в `changes/archive/` (скіл `factory-docs-sync`) | усе інше в документації, код |
| «Розробка»: баг | розбір пише першу частину `bugs/<id>.md` (симптом, причина, як знайшли, що не встановлено, варіанти); виправлення дописує «Виправлення» і «Перевірку», рядок у `bugs/README.md`, інваріант у `bugs/INVARIANTS.md` | файли інших багів |
| «Розробка»: інші задачі | нічого в документації; відхилення від специфікації — розділом `## Deviations from design` в описі PR/MR | `features/`, `changes/` |
| «Аудити» | `audits/<дата>-<тема>.md` (коміт у гілку картки, без PR) | код, решта документації |

Виняток для «Продукту»: якщо в області ще нема `features/<область>/design.md` (проєкт без документації), специфікація спершу пише базовий опис області з коду (окремим комітом, `product-spec/references/area-baseline.md`), потім дельту.

## Формат дельти

Дельта в `changes/<зміна>/design.md`: розділ «Affected areas» і хоча б один із `ADDED / MODIFIED / REMOVED Requirements` (укр. `ДОДАНО / ЗМІНЕНО / ВИЛУЧЕНО вимоги`); вимоги — `### Requirement:` з SHALL/MUST і `#### Scenario:` GIVEN/WHEN/THEN; MODIFIED повторює вимогу повністю з «Previously», REMOVED — з причиною.

## Відповідність

Кожна папка документації має відповідати стандарту: якщо щось не лягає в наявні розділи, додається новий стандартний розділ сюди, а не «лишається як є».

Наявні репозиторії з іншою розкладкою (`raw/`, `requests/`, `qa/`, `specify/`, `features/<x>.md`) читаються як відповідні частини; скіли спершу дивляться, що є, і не створюють паралельну структуру й нічого не переносять без запиту.

Скіли тримають робочу копію розкладки в `packages/harness-mastra/factory-skills/product-enrich/references/docs-layout.md`; змінюючи стандарт, правте обидва місця.
