# Фабрика: питання і відповіді

Відповіді — за кодом `v4` (стан на 2026-10-27). Шляхи відносно `v4/`.

## Як фабрика задумана працювати?

Є різні задачі:

- розробка специфікації;
- розробка імплементації і поділ на задачі;
- додавання нових фіч;
- баг: прочитати логи, відтворити без доступу до коду, написати тест, який відтворює, відправити вже на виправлення, підготовка пул-реквеста, рев'ю;
- налаштування сторонніх сервісів залежно від специфікації (Apple, Google Firebase для деплою …). Можливо, потрібен браузер чи доступ до певних утиліт.

Можливо, різні агенти (ролі: девелопер, тестувальник).
Налаштування різних середовищ і доступи.

Досі не розумію: це різні фабрики, різні скіли чи воркфлоу? Як будувати пайплайни на різні задачі, щоб якісно виконували?

### Відповідь

Три рівні, кожен відповідає за своє:

| Рівень | Що це в коді | Відповідає за |
| --- | --- | --- |
| **Фабрика** | `FactoryProject` (`packages/store/src/projects/base.ts`) | *Де* працювати: набір репозиторіїв, пісочниця, setup-команди, модель і ключі за замовчуванням |
| **Дошка (пайплайн)** | `defineBoard()` (`packages/core/src/boards/define-board.ts`), дошки в `packages/pipelines/src/<board>/` | *Який процес*: фази, переходи, хто може рухати картку |
| **Роль + скіл** | `role` робочої фази + `invokeSkill` у `phase-rules.ts`, скіли в `packages/harness-mastra/factory-skills/<name>/SKILL.md` | *Що робить агент* у фазі: інструкції, інструменти |

Тобто: фабрика — середовище, дошка — процес (пайплайн), скіл — інструкція агенту на конкретному кроці.

**Фази.** Бувають трьох видів:

- `resting` — ніхто не працює, картка чекає;
- `working` — працює агент із певною роллю: його сесія веде картку і виконує задачу фази;
- `terminal` — сесії зупиняються, пісочниці звільняються.

Вхід у фазу (`onEnter`) повертає рішення: запустити скіл, надіслати промпт, перенести картку тощо. Runtime (`packages/runtime`) ці рішення виконує через dispatcher.

**Що є зараз:**

- **Work**: `intake → triage → planning → execute → review → done | canceled`.
  - Скіли по фазах: `factory-triage`, `factory-plan`, звичайний промпт «реалізуй план», `factory-self-review`, `factory-complete-issue`.
  - План затверджує людина, або увімкнено автозатвердження. Після `submit_plan` картка сама переходить у `execute`.
- **Review**: рев'ю PR/MR. Скіли `factory-review`, `factory-rereview` та їхні GitLab-варіанти.
  - Так, це окремі скіли саме для перевірки коду. Скіл — це файл інструкцій `factory-skills/<name>/SKILL.md`, який агент отримує на вході у фазу.
  - Для специфікації робиться так само: свій скіл (наприклад `factory-spec`: як писати специфікацію, структура, критерії готовності) і своя дошка, де робоча фаза запускає цей скіл. Такого скіла поки нема, його треба написати (пропозиція — у таблиці нижче).
- **Acceptance**: `queued → verifying (validator) → decision → accepted`. Прийняти картку може лише людина.

**Ролі** зараз: `triage`, `plan`, `work`, `review`, `validator`. Ролі «девелопер» чи «тестувальник» нема. Роль визначає, яка сесія агента (seat) веде картку і які спецінструменти вона має. Окремого системного промпта на роль нема: поведінку задає скіл чи промпт фази.

**Дошка і Mastra workflow — це різні речі.** І те, і інше — код, а відрізняються вони тим, де живе стан і хто його змінює.

| | Mastra workflow (`createWorkflow` / `createStep` з `@mastra/core/workflows`) | Дошка фабрики (`defineBoard` + `packages/runtime`) |
| --- | --- | --- |
| Що описує код | послідовність кроків одного прогону | правила: фази, дозволені переходи, policy, що запускати на вході |
| Де стан | snapshot прогону workflow | картка в базі (`work-items`): фаза, ревізія, метадані, сесії |
| Хто рухає | сам workflow, крок за кроком, від старту до кінця | будь-хто: людина в UI, агент інструментом, вебхук (issue закрили, PR змерджили), Supervisor |
| Скільки живе | один прогін | дні й тижні |
| Що відбувається на зміну | наступний крок | runtime перевіряє ревізію і policy, кладе рішення в чергу, dispatcher їх виконує |

Однією карткою справді керують і код, і база: правила дошки — код, стан картки — дані. Кожен, хто її рухає (людина, агент, вебхук), проходить через один `transition-service`. Ревізія картки (`expectedRevision`) не дає двом змінам затерти одна одну.

**Mastra workflows для карток не використовуються.** У фабриці є лише один Mastra workflow — збірка образу середовища (`harness-mastra/src/environment/build-workflow.ts`): запустити збірку шаблону пісочниці й дочекатися результату.

**Як будувати пайплайни під ваші задачі.** Одна задача — одна дошка; кожен крок — робоча фаза зі своєю роллю і своїм скілом. Якість дають три речі:

- вузький скіл на кожен крок;
- `transition-policy`, яка не пускає далі без артефакту (план, тест, вердикт);
- людські ворота (`resting`-фаза з рішенням людини).

| Задача | Дошка (пропозиція) |
| --- | --- |
| Специфікація | `spec`: intake → draft (`plan`, скіл `factory-spec`) → human review (resting) → done; вихід — документ або дочірні картки |
| Імплементація і поділ на задачі | `planning` у Work + інструмент створення карток (`work-item-tools.ts` уже вміє `createFactoryWorkItem`) |
| Нова фіча | існуюча Work |
| Баг | `bug`: intake → investigate (логи, без коду) → reproduce (написати падаючий тест) → fix (Work execute) → review → done. Policy: не пускати у fix без тесту, що падає |
| Налаштування сервісів (Apple, Firebase) | окрема дошка або фаза з людськими воротами; потрібні CLI (`firebase`, `fastlane`) у setup пісочниці й секрети |

**Чому «дошка», а не «воркфлоу».** Назва з UI: фази показуються колонками канбан-дошки, а картка — задача, що переїжджає між колонками (як у Jira чи Linear). За суттю це скінченний автомат станів: фази, дозволені переходи, правила на вході й виході. Тож «пайплайн» і «дошка» тут одне й те саме: у коді — `defineBoard`, у пакеті — `@factory/pipelines`.

**Як додати дошку:**

1. Створити `packages/pipelines/src/<board>/{board,phase-rules,transition-policy}.ts`; найзручніше копіювати `acceptance/`.
2. Експортувати її з `pipelines/src/index.ts`.
3. Підключити в `apps/server/src/mastra/index.ts` (`boards: [acceptanceBoard, ...]`).
4. Для нового скіла: додати `factory-skills/<name>/SKILL.md` і внести ім'я у `FACTORY_SKILL_NAMES` (`harness-mastra/src/workspace.ts`).

**Нові ролі.** Офіційна документація (`mastracode/factory/README.md`, «Execute a custom board») прямо дозволяє власні ролі на власних дошках, наприклад `release-preparer` і `release-publisher`. Роль — це лише назва «місця» на спільному Code Agent; окремих агентів і налаштувань на роль нема, інструкції ролі дає промпт або скіл фази. Обмеження: ручний старт запуску через API приймає лише `triage/plan/work/review` (`FACTORY_ROLE_STAGES`), а спецлогіка (класифікація тріажу, вердикт рев'ю) прив'язана до вбудованих ролей Work і Review. Для запусків правилами власна роль працює без правок core.

## Що робить кожен етап: скіли, методологія, де лежать результати

Скіли лежать у `packages/harness-mastra/factory-skills/<name>/SKILL.md`. Нижче: що агент робить на кожному етапі, за якою методикою і куди пише результат.

### Дошка Work

**1. Intake** (resting, агента нема). Сюди картки потрапляють за замовчуванням. Автоматично далі не рухаються: людина перетягує картку в Triage.

**2. Triage** — роль `triage`, скіл `factory-triage`.

- **Методика:**
  1. Зрозуміти issue і автора (історія внесків).
  2. Пошукати дублі й регресії серед issue і PR.
  3. Простежити код: `git log` / `blame`, архітектура, покриття тестами.
  4. Спробувати відтворити.
  5. Поставити діагноз причини, оцінити окремо *зусилля* й *вплив*, підібрати мітки за доменом.
  
  Кожна розвилка вирішується і записується як припущення.
- **Результат:**
  - **коментар в issue** з маркером `<!-- mastra-factory-triage -->` (лише через `github_upsert_factory_triage_comment`, тому оновлюється, а не дублюється): таблиця Type / Route / Severity / Confidence / Effort / Impact / Next step, потім Understanding, Assumptions, Open questions, Reproduction;
  - **мітки:** `status: auto-triaged`, `needs approval`, `effort:*`, `impact:*`, доменні;
  - необов'язковий файл `.artifacts/factory-triage/issue-<n>.md` у пісочниці;
  - той самий підсумок останнім повідомленням у треді сесії.
- **Класифікація** `triageType` обов'язкова при переході й пишеться в колонку картки `triage_type`; змінити її потім не можна. Значення: bug, feature request, docs, question/support, maintenance, duplicate, resolved, invalid, spam, out-of-scope, other.
- **Маршрути:** Plan fix, Await approval, Ask author for info, Close…, Answer provided, No transition. **Баг іде в Planning сам; решта стоїть, доки людина не перенесе.**

**3. Planning** — роль `plan`, скіл `factory-plan`.

- **Методика:**
  1. Перевірити розуміння з тріажу.
  2. Спроєктувати рішення за наявними патернами кодової бази.
  3. Написати план: **Goal, Scope, Phases** (для кожної — файли, тести, команди), **Risks, Assumptions, Open questions**.
- **Де план:** повідомленням у треді сесії і файлом `.artifacts/plans/issue-<n>.md` у пісочниці. **На картці план не зберігається**, і в issue не публікується.
- `submit_plan` скіл не викликає: це ворота лише для інтерактивних сесій. Щоб картка пішла в Execute, потрібне автозатвердження планів або людина.

**4. Execute (Building)** — роль `work`, **без скіла**, звичайний промпт одного з трьох видів:

- «реалізуй затверджений план»;
- «знайди причину і виправ з тестами» (баг без плану);
- «виправ зауваження self-review».

Результат — коміти в гілці картки. Без self-review агент сам відкриває PR. З self-review він пушить гілку і переносить картку в Review без PR. Відкритий PR переносить картку Work у Review і створює картку на дошці Review.

**5. Review (на дошці Work)** — роль `review`, скіл `factory-self-review`. Працює, лише коли self-review увімкнено і PR ще нема.

- **Методика** (частини `factory-review`):
  1. Захист від prompt injection.
  2. Спершу власний дизайн рішення, потім diff.
  3. Quality gate з тестами.
  4. Історія змін.
  5. Ворота вердикту плюс «адверсарна» перевірка.
- **Результат:** звіт (Result, head SHA, підсумок, таблиця Checks, пронумеровані зауваження) і вердикт `factory_record_review_verdict`. Вердикт — `approve` чи `request changes`; пишеться в **метадані картки**: `selfReviewVerdict`, `selfReviewedHeadSha`, `selfReviewFindings`, `selfReviewRounds`, `selfReviewNeedsHuman`.
- `request changes` повертає в Execute; кожен 3-й раунд картка йде людині в Intake. `approve` будить білдера, щоб відкрив PR саме з цього SHA зі звітом в описі PR.

**6. Done** — скіл `factory-complete-issue`: прибирає мітки тріажу, ставить `status: pending-close`, коментує «This issue has now been marked as done.». **Issue не закриває** — це робить людина.

### Дошка Review (PR / MR)

Фази: Intake → Reviewing → Done (змерджено) / Canceled. Перший прохід — `factory-review`, наступні — `factory-rereview`; для GitLab є свої варіанти.

- **Методика `factory-review`:**
  1. Власний дизайн до diff.
  2. Категорійні довідники.
  3. Почекати рев'ю ботів (до 10 хв) і класифікувати їхні знахідки.
  4. Quality gate.
  5. Історія.
  6. Вердикт з воротами й адверсарною перевіркою.
  7. Передача.
- **Результати:**
  - **commit check** `source_control_publish_test_check` і коментар у PR `## Factory test report`;
  - **PR review** з `Verdict: …` / `Reviewed head: <sha>`;
  - мітки `status:auto-approved` або `status:changes-requested`;
  - іноді окремий follow-up PR з дрібними механічними виправленнями;
  - метадані картки `reviewVerdict`, `reviewedHeadSha`, `reviewedAt`, скопійовані й на батьківську картку Work.
- Агент не може перенести картку Review у Done: це робить merge.

### Дошка Acceptance (наша)

Queued → Verifying (роль `validator`, **без скіла**, промпт: перевірити кожен критерій прийняття як pass, fail чи unverified з доказами) → Decision → Accepted (лише людина). Результат — повідомлення сесії; окремого місця для артефакту нема.

### Що з цього випливає для якості

- **План живе лише в пісочниці й треді.** Після закриття сесії файл зникає, а людині незручно його рев'ювати. Кандидат на покращення: публікувати план коментарем в issue чи на картці, як тріаж.
- **Execute не має скіла:** методика білдера — лише системний промпт Mastra Code плюс план. Для якості варто написати скіл `factory-build` (TDD, коміти по фазах плану, обов'язкові команди перевірки).
- **Скіли написано під репозиторій Mastra** (наприклад, тріаж відтворює на `weather-agent`). Під свої проєкти їх треба переписати або перекрити своїми в `.agents/skills` репозиторію.

## Репозиторії, пісочниця, воркспейс

- Як зберігаються репозиторії: це окрема папка з усіма репозиторіями, з різними git-деревами під картку, чи як це працює?
- Як запускається пісочниця і як її організувати під Flutter (macOS)? Як це організовують в інтернеті?
- Воркспейс — це група декількох репозиторіїв, чи можна налаштувати лише один репозиторій на один конвеєр?

### Відповідь: зберігання репозиторіїв

Git worktree не використовуються. **Кожна сесія агента має свою пісочницю зі своїм неглибоким клоном** (`--depth=1 --single-branch`): див. `packages/sandbox/src/github/sandbox.ts` і `internal-workspace/src/repo-clone.ts`.

- **Локально:** `~/.mastracode/web/sandboxes/<sessionId>/<repo>`. Корінь можна змінити змінною `MASTRACODE_LOCAL_SANDBOX_ROOT`.
- **Віддалена VM:** домашня тека VM або `sandboxWorkingDirectory` проєкту.
- **Гілка на картку:** `factory/issue-N`, `factory/pr-N`, `factory/gitlab-mr-N-…`, `factory/item-<id>`. Ручні сесії працюють у `user/session-<id>`. Усі сесії однієї картки ділять одну гілку (`pipelines/src/shared/work-item-branch.ts`).
- **Токени** передаються в кожну команду окремо і в `.git/config` не пишуться.
- **Маркери setup** лежать поруч із клоном у `.mastra-sandbox/`. Там зберігається sha256 команди, тож setup не перезапускається, якщо команда не змінилась.

**Чому кожна сесія клонує заново, і що з цим робити.** Так зроблено заради ізоляції: кілька агентів працюють паралельно на різних гілках і не заважають один одному, а локальний режим повторює модель віддаленої VM (одна сесія — одна пісочниця). Ціна — для кожної сесії свій клон і своє встановлення залежностей. Локальний провайдер шаблонів не має, тож environment build локально не допомагає. Маркер setup економить лише в межах тієї самої сесії.

Як здешевити локальну роботу (зараз нічого з цього не зроблено):

- **pnpm** вже майже безкоштовний при повторному встановленні: глобальний store і жорсткі посилання. npm і yarn так не вміють.
- **Спільне дзеркало репозиторію:** один локальний клон і `git worktree` або `git clone --reference` на сесію. Клон тоді триває секунди, а не хвилини.
- **Повторне використання пісочниці картки:** усі сесії однієї картки вже ділять гілку, тож можуть ділити й теку з установленими залежностями (треба врахувати паралельні сесії).

### Скільки живе пісочниця і як керується її життя

- **Пісочниця живе стільки, скільки сесія.** Сесія живе, поки картка не дійде до термінальної фази (`done`, `canceled`, `accepted`).
  - Тоді `SessionRetirementCoordinator` виконує `teardownCommand` і зупиняє або знищує VM (`packages/sandbox/src/session-retirement.ts`).
  - Між запусками однієї картки пісочниця лишається. Наступна фаза (план → збірка → self-review) працює в тій самій теці, на тій самій гілці, з уже встановленими залежностями.
- **Простій.** У E2B є `idleTimeoutMinutes` у `sandboxSettings`: VM засинає й прокидається на наступній команді. Локальна тека нікуди не дівається, поки сесію не закриють.
- **Ручне керування:** у панелі воркспейсу є «Recreate sandbox». Самозаміну пісочниці агентом зараз переносимо з upstream (див. розділ про upstream).
- **Межа на кількість:** dispatcher запускає до 25 карток одночасно на репліку. Ліміту живих пісочниць у v4 фактично нема: `MASTRACODE_MAX_SANDBOXES` описано, але не використано.

**«Образ з усіма налаштуваннями, що піднімається паралельно з обмеженням».** Саме так працює environment build:

1. Репозиторії й setup один раз «запікаються» в шаблон.
2. Кожна нова сесія стартує з копії шаблону: секунди замість хвилин.
3. Паралельно стільки копій, скільки дозволяє провайдер і dispatcher.

Обмеження: провайдер **Local шаблонів не вміє**, тут кожна сесія клонує й ставить залежності сама. Щоб мати це локально, потрібен провайдер на Tart чи Lume (для macOS) або Docker (для Linux) з образом-шаблоном і лімітом одночасних VM. Такого провайдера ще треба написати.

**Якщо потрібна лише відповідь (аналіз коду без змін).** Зараз будь-яка сесія клонує репозиторій. Неглибокий клон (`--depth=1`) — це секунди для звичайного репозиторію. Варіанти процесу:

| Варіант | Як | Коли |
| --- | --- | --- |
| Сесія без змін | звичайна сесія, фаза тільки читає й відповідає, PR не відкривається | зараз, без коду |
| Спільне дзеркало | один локальний клон на репозиторій, сесія отримує `git worktree` чи `clone --reference` | багато коротких аналізів; треба дописати провайдер |
| Без клону, через API | агент читає код через API GitHub/GitLab (`contents`, пошук) чи MCP | дрібні питання; повільно на великих репозиторіях |

Для дошки «аналіз» або «специфікація» найпростіше перше: фаза з роллю `plan` і скілом, який лише читає код і пише відповідь у картку чи issue.

### Мобільна розробка: великі SDK (iOS, Android, Flutter)

Xcode займає 40+ ГБ, Android SDK з емулятором — 10+ ГБ, Flutter — кілька ГБ. Ставити це на кожну сесію неможливо. Як це вирішують:

1. **SDK ставляться один раз в образ, а не в сесію.**
   - Linux: Docker-образ з Flutter і Android SDK (близько 3.5 ГБ стиснутого). Наприклад `ghcr.io/adrianjagielak/flutter`: колишній `ghcr.io/cirruslabs/flutter` не оновлюється з травня 2026.
   - macOS: образ Tart чи Lume з Xcode, Flutter і CocoaPods (`ghcr.io/cirruslabs/macos-*-xcode`).
2. **Кеші — окремо від сесії:** `~/.pub-cache`, `~/.gradle`, CocoaPods (`Pods/` за ключем `Podfile.lock`) лежать у спільному томі чи в шаблоні, плюс Gradle remote build cache.
3. **Розділення роботи:**
   - **Linux-пісочниця:** `flutter analyze`, unit- і widget-тести, `flutter build apk` — дешево й масштабується.
   - **Android-емулятор:** потрібен `/dev/kvm`. Серед хмарних пісочниць KVM документовано лише у Freestyle і Namespace; у E2B, Modal, Vercel не знайдено. Інакше — власне залізо.
   - **iOS** (`flutter build ios`, симулятор, підпис) — лише Mac: пул Mac mini з Tart/Lume, 2 VM на Mac, або CI (Codemagic, GitHub Actions macOS).
4. **Як роблять агентні платформи:** GitHub Copilot coding agent macOS не підтримує взагалі. Codex cloud, Devin, Cursor: macOS-пісочниць не знайдено. Звичний підхід — агент працює в Linux, а iOS-збірку віддає на Mac (CI чи SSH). Є XcodeBuildMCP (Sentry) — MCP-сервер, через який агент керує збіркою Xcode на Mac.

**Найпростіший старт для нас:** локальний режим на вашому Mac. Xcode, Android SDK і Flutter уже стоять на хості, і агент користується ними без копіювання. Ізоляції нема, тож лише для своїх тестових репозиторіїв. Наступний крок: macOS-провайдер на Tart чи Lume з образом-шаблоном.

### Відповідь: запуск пісочниці

Провайдера вибирають при старті сервера (`apps/server/src/mastra/index.ts`):

- Mastra Platform, якщо задані змінні `MASTRA_PLATFORM_*`;
- E2B, якщо задано `E2B_API_KEY`. [E2B](https://e2b.dev) — хмарний сервіс пісочниць для AI-агентів: на кожну сесію піднімається ізольована Linux-мікроVM (Firecracker), керується через API. Платний (є безкоштовні кредити на старт); macOS не дає;
- інакше Local, тобто сама машина сервера.

При кожному старті сесії виконується:

1. клон репозиторію;
2. checkout гілки;
3. `setupCommand` репозиторію;
4. `workspaceSetupCommand` проєкту;
5. встановлення `GH_TOKEN`.

Після закінчення для кожного репозиторію виконується `teardownCommand`, потім VM зупиняють або знищують (`sandbox/src/session-retirement.ts`).

Є також *environment build*: репозиторії й setup заздалегідь «запікаються» в шаблон провайдера. Збірку запускають вручну, за розкладом або на push (`harness-mastra/src/environment/`).

Docker- чи SSH-провайдера в коді нема.

### Відповідь: Flutter і macOS

Зібрати iOS чи macOS можна лише на Mac з Xcode, бо Linux-пісочниці (E2B, Platform) цього не вміють. Як це роблять у світі:

- **Свій Mac mini / Mac Studio як раннер.** Найпоширеніше для малих команд: агент ходить на машину по SSH, на ній уже стоять Xcode, Flutter, CocoaPods, fastlane.
- **Ізольовані macOS VM на Apple Silicon:**
  - [Tart](https://tart.run) (Cirrus Labs), безкоштовний для малих парків. Дає OCI-образи macOS: `tart clone` образу з Xcode, запуск, SSH усередину, після роботи VM видаляють. Найближче до моделі «пісочниця на сесію».
  - Anka (Veertu) та Orka (MacStadium) — комерційні аналоги.
- **Хмарні Mac:** AWS EC2 Mac (мінімальна оренда 24 години), MacStadium, Scaleway.
- **CI як виконавець:** GitHub Actions `macos-*` runners, Codemagic (спеціалізований на Flutter), Bitrise. Агент лише пушить, а збірку й тести робить CI. Найпростіше, але повільний цикл зворотного зв'язку.

Як вбудувати це у фабрику: написати свій `MastraSandbox` — клас із `start()` та `executeCommand()`, який виконує команди на Mac (SSH до хоста або до Tart VM). Його передають як `sandbox:` в `apps/server/src/mastra/index.ts`; приклад обгортки — `CallbackFactorySandbox` (`packages/sandbox/src/callback-factory-sandbox.ts`). Логіка клону, setup і teardown — звичайний shell, тому решту коду міняти не треба.

**Чи безкоштовний Tart і як ним користуватися.**

- **Ліцензія Tart у 2026 змінилась.** Близько 7 квітня 2026 Cirrus Labs оголосила, що переходить у команду Agent Infrastructure в OpenAI. Вона пообіцяла м'якші ліцензії для Tart, Vetu й Orchard і скасувала плату за ліцензії.
  - Репозиторій тепер `github.com/openai/tart`.
  - За стороннім джерелом, Tart 2.33.0 (липень 2026) переліцензовано під FSL-1.1-ALv2. Це ліцензія, що через певний час стає Apache 2.0, а до того забороняє лише конкурентні комерційні сервіси.
  - Платний поріг за кількістю ядер, схоже, зник. **Перевірити файл LICENSE в репозиторії**: я не підтвердив.
- **Це не «пробний період».** Tart — програма на вашому Mac: скільки завгодно VM-образів, запуск без обмеження в часі.
- **Головне обмеження ставить не Tart, а Apple:** ліцензія macOS дозволяє на одному Mac лише **2 macOS VM одночасно**. Тому кілька проєктів можна вести, але на одному Mac паралельно працюватимуть максимум дві macOS-пісочниці; решта чекатиме або піде на інший Mac.
- **Аналоги Tart:** усі вони стоять на Apple Virtualization.framework, тож те саме обмеження — 2 macOS VM на Mac.

  | Інструмент | Ліцензія | Для автоматизації |
  | --- | --- | --- |
  | Tart + Orchard (оркестратор парку Mac) | FSL → Apache, безкоштовно | так, CLI, OCI-образи |
  | **Lume** (trycua) | MIT, open source | так, CLI і API, створений для AI-агентів |
  | UTM | Apache-2.0 | слабо, переважно GUI |
  | VirtualBuddy | BSD-2 | ні, GUI |
  | Anka (Veertu) | комерційна | так |
  | Apple `container` | open source | лише Linux-контейнери, macOS-гостей не вміє |

- **Як вирішують в інтернеті:**
  - малі команди — 1–3 Mac mini з Tart чи Lume (2 VM на кожен) або напряму на хості;
  - середні — Orchard чи Anka для парку Mac;
  - решта — орендовані Mac: Scaleway M4 від €0.22/год (мінімум 24 год), AWS EC2 Mac ≈ $1.2/год (мінімум 24 год), MacStadium від $149/міс, MacinCloud;
  - CI: Codemagic (500 безкоштовних хвилин macOS на місяць), GitHub Actions macOS $0.062/хв;
  - Cirrus CI закрився 1 червня 2026.
- Базове використання: `brew install cirruslabs/cli/tart` → `tart clone ghcr.io/cirruslabs/macos-sequoia-xcode:latest flutter-base` → `tart run flutter-base` → `ssh admin@$(tart ip flutter-base)` (пароль `admin`). У фабрику це ще треба вбудувати своїм класом пісочниці: готового нема.

**Повністю безкоштовно і локально — вже зараз.** Сервер у режимі `dev:local` використовує *локальну* пісочницю, тобто цей самий Mac. Якщо на ньому встановлені Xcode, Flutter і CocoaPods, агент уже може збирати iOS прямо в `~/.mastracode/web/sandboxes/<sessionId>/`, без VM. Мінус — слабша ізоляція: агенти працюють на хості, від вашого користувача. Для своєї машини й тестових репозиторіїв це найпростіший старт; Tart потрібен, коли захочеться ізоляції.

Рекомендований шлях для Flutter:

1. Mac mini з Tart.
2. Базовий образ з Xcode і Flutter.
3. VM на сесію, `setupCommand` = `flutter pub get && cd ios && pod install`.

### Відповідь: воркспейс і кількість репозиторіїв

- **Фабрика (проєкт) може містити кілька репозиторіїв.** Кожен прив'язаний через `ProjectRepository` (`store/src/source-control/base.ts`) зі своєю гілкою, `setupCommand`, `teardownCommand` і порядком.
- **Ті, що мають `inEnvironment`, клонуються поруч в один корінь воркспейсу** (`harness-mastra/src/workspace.ts`). Агент отримує опис цієї розкладки (`sandbox/src/environment-state-processor.ts`).
- **Агент працює на рівні воркспейсу, а не одного репозиторію.** Робоча тека сесії — це корінь воркспейсу, під яким лежать усі репозиторії середовища (`<root>/<repo-a>`, `<root>/<repo-b>`…). Агент бачить і редагує всі; на старті він отримує опис цієї розкладки.
- **«Головний репозиторій» — це репозиторій картки.** На ньому створюється гілка сесії (`factory/issue-N`) і в нього цілять інструменти PR. Решта репозиторіїв клонуються поруч на своїх гілках, і агент може пушити й у них.
- **Дошки спільні для всього деплою** і до репозиторію не прив'язані. Репозиторій картки визначається з її метаданих: id репозиторію у провайдера, slug, або «єдиний прив'язаний».
- **Щоб конвеєр працював лише з одним репозиторієм**, заведіть окрему фабрику (проєкт) з одним репозиторієм.

## Харнес і авторизація

- Як працює харнес з авторизацією, наприклад Claude Code з різними акаунтами?
- Підміна API (деякі провайдери це вміють, наприклад DeepSeek). Питання ширше, ніж custom providers у Mastra: чи підтримують токени, ключі й авторизацію *інші* харнеси (Claude Code тощо). Частина провайдерів уміє це з коробки; Mastra Code уміє, а з іншими харнесами не пробували. Див. «Авторизація в інших харнесах» нижче.
- Mastra має великий список API (токени), а також sign-in у Codex, Anthropic, Grok.
- Яка є інтеграція?

### Відповідь

Моделі викликає `@mastra/code-sdk`, а фабрика вирішує, *чий* ключ використати (`packages/credentials`).

**Режими доступу до ключів:**

- **Local** (`dev:local`, без входу): ключі лежать у файлі SDK `auth.json`.
- **Tenant** (з входом): ключі в таблиці `model_provider_credentials`, зашифровані AES-256-GCM з ротацією. Ключ може бути особистим (`user_id`) або спільним на org (без `user_id`). На один провайдер у межах одного scope — один ключ.

**Scope моделі на проєкті** (`modelScope`):

- `factory` — працюють ключі фабрики;
- `user` — ключі користувача;
- `hybrid` — роботи по картках ідуть на ключах фабрики, інтерактивні сесії на ключах користувача.

Fallback на env-ключі сервера для тенантів вимкнено. Кожна відповідь агента позначена, який ключ її дав.

**OAuth-підписки** (`credentials/src/provider-credentials.ts`, `api/src/oauth.ts`):

| Провайдер | Вхід |
| --- | --- |
| `anthropic` | Claude Pro/Max (PKCE, вставити код) |
| `openai` | ChatGPT Plus/Pro (Codex), device code |
| `github-copilot` | device code |
| `xai` | SuperGrok / X Premium+, device code |

**Кілька акаунтів Claude.** SDK уміє кілька акаунтів на провайдера з ротацією при rate limit, але фабрика цього не використовує: тут один ключ на провайдер на scope. Різні акаунти можна мати лише так: особистий у кожного користувача плюс один на org.

**Підміна API (custom providers).** Задаються на рівні org: назва, URL, ключ, список моделей (`store/src/custom-providers/base.ts`).

- Підтримується **лише OpenAI-сумісний** endpoint (`createOpenAICompatible`). DeepSeek, OpenRouter, Together, локальні vLLM/Ollama працюють; Anthropic-сумісного режиму нема.
- Id моделі має формат `<provider>/<model>`, наприклад `deepseek/deepseek-chat`.

Каталог моделей бере SDK (`listAvailableModels`). Модель за замовчуванням: спершу проєкту, потім користувача, потім модель підключеного провайдера. Сабагентам (explore, plan, execute) ставиться та сама модель.

**Вхід у саму фабрику:**

- ~~`FACTORY_LOCAL_DEV_AUTH=1` — один локальний користувач~~ (прибрано, ADR-0030: єдиний вхід — Google);
- WorkOS (`WORKOS_*`);
- Mastra Platform (`MASTRA_SHARED_API_URL`).

### Авторизація в інших харнесах (відкрите питання, не перевірено)

Усе вище стосується **лише харнесу Mastra** (`harness-mastra`): ключі, OAuth-підписки й custom providers обробляє `@mastra/code-sdk`, а фабрика вирішує, чий ключ дати. Інших харнесів у v4 ще нема, порт харнесу в планах. Тому для інших харнесів нічого не пробували. Фіксуємо, що треба з'ясувати.

**Claude Code як харнес** має власну авторизацію, окрему від фабрики:

- **Вхід підпискою** Claude Pro/Max (`claude login`; для неінтерактивного запуску є довгоживучий токен `claude setup-token` → `CLAUDE_CODE_OAUTH_TOKEN`);
- **API-ключ** (`ANTHROPIC_API_KEY`), а також Bedrock і Vertex;
- **підміна API** через `ANTHROPIC_BASE_URL` (+ `ANTHROPIC_AUTH_TOKEN`) на **Anthropic-сумісний** endpoint. Частина провайдерів дає такий з коробки, наприклад DeepSeek. Це протилежність нашим custom providers, які вміють лише OpenAI-сумісні.

**Кілька акаунтів.** Сам Claude Code працює з одним акаунтом на теку конфігурації; кілька акаунтів зазвичай роблять окремими теками (`CLAUDE_CONFIG_DIR`) і перемиканням між ними. Сторонні інструменти показують, що це можна зробити зручно. Як це лягає на фабрику (акаунт на користувача, на фабрику, ротація при ліміті), треба вирішити.

**Що з'ясувати під час порту харнесу:**

1. Де зберігати облікові дані харнесу: у тій самій таблиці `model_provider_credentials` (зашифровано, scope user/org) чи окремо.
2. Як передавати їх у сесію: env-змінні процесу (`CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_*`) чи окрема тека конфігурації на сесію.
3. Чи підтримати Anthropic-сумісні custom providers (`ANTHROPIC_BASE_URL`), щоб DeepSeek і подібні працювали в Claude Code.
4. Кілька акаунтів: вибір акаунта на фабрику чи на користувача, ротація при rate limit (SDK Mastra уміє ротацію, фабрика її не використовує).
5. Перевірити на практиці: вхід підпискою, API-ключ і підміну endpoint — у кожному харнесі окремо.

Відповіді на частину цих питань і план — у розділі «Claude Code як другий харнес» нижче.

## Автоматизація

- Через інтервал (Mastra це вміє).
- Через різні чати.
- Вебхуки, різні тригери, які налаштовуються.
- Репозиторії — ті самі тригери; може, інтервальні, але по факту розширюють верхній функціонал.
- Задачі з різних менеджерів задач.

Як воно бере задачі з менеджера чи issue — одним словом, як це налаштовано і як працює?

### Відповідь

**Шлях будь-якої події:**

1. Подія провайдера потрапляє в rules інтеграції.
2. `selectEventRule` вибирає правило: спершу явний override на інтеграції, потім обробник дошки, потім дефолт інтеграції; `null` вимикає дефолт (`core/src/rules/event-rules.ts`).
3. Правило повертає рішення, наприклад `upsertLinkedWorkItem`.
4. Dispatcher (опитує щосекунди) створює або оновлює картку.
5. Вхід у фазу запускає агента.

**Тригери, що є:**

| Тригер | Де |
| --- | --- |
| Вебхук GitHub | `POST /web/github/webhook`: `issues`, `issue_comment`, `pull_request*`, `push` |
| Вебхук GitLab | `/web/gitlab/webhook`: Issue, Note, Merge Request |
| Інтервальні reconcilers | GitHub — 60 хв за замовчуванням (`MASTRACODE_GITHUB_*_RECONCILE_*`); GitLab — 5 хв; ловлять пропущені вебхуки, закриття, зміни |
| Polling Platform | кожні 20 с, коли фабрика працює через Mastra Platform |
| Ручне створення | UI або `POST /web/factory/projects/:id/work-items`; агент теж може створити картку інструментом |
| Розклад (cron) | лише для збірки середовища; для intake розкладу нема |
| Чати | механізм є (`channels()`, процесори в `packages/session`), але Slack прибрано, тож зараз жодна інтеграція чат не дає |
| Supervisor | кожні 5 хв health-check: застряглі рішення, сесії без власника, дрейф міток |

**Як GitHub-issue стає карткою:**

1. Репозиторій прив'язують до фабрики, і всі відкриті issue та PR імпортуються одразу.
2. Новий issue (`issueOpened`) створює картку на дошці `work`, фаза `intake`; новий PR — на дошці `review`.
3. **Мітки** вибирають дошку: label routes (`store/src/intake`, `/web/intake/label-routes`). Зміна мітки переносить картку на іншу дошку.
4. Редагування чи коментар в issue перезапускає `factory-triage`. Закриття issue переносить картку за мапою `sourceClosed` дошки.

GitLab суворіший: подія обробляється, лише якщо джерело увімкнено в intake config, проєкт є у `sourceIds` і існує прив'язка.

Зворотна синхронізація (картка → issue) обмежена: мітки прийняття, PR через інструменти агента, підписка сесії на події свого PR. Коментарі з фіду назовні не дзеркаляться.

### Що таке rules

**Rule (правило)** — це шматок довіреного серверного коду (TypeScript), який реагує на подію і повертає одне типізоване **рішення** (decision). Сам по собі він нічого не робить: рішення кладеться в чергу, а dispatcher його виконує з повторами (`core/src/rules/types.ts:554-683`).

**Які бувають рішення:**

| Рішення | Що робить |
| --- | --- |
| `transition` | перенести картку в іншу фазу |
| `upsertLinkedWorkItem` | створити чи оновити картку (наприклад, з issue) |
| `invokeSkill` | запустити агента: скіл або промпт, з певною роллю |
| `sendMessage` | надіслати повідомлення в сесію |
| `notify` | сповіщення |
| `dismissStaleReviews` | прибрати застарілі рев'ю |
| `reject` | відмовити (з кодом і причиною) |

Кожне рішення має ключ ідемпотентності: повтор не створить дубль. Рішення, що впало, можна повторити або відкинути (`factory_retry_decision` / `factory_dismiss_decision`).

**Чотири види правил:**

1. **Правила фаз** (`phases.<фаза>.onEnter` / `onExit`): що робити, коли картка входить у фазу чи виходить з неї, наприклад «на вході в Triage запусти `factory-triage`». Окремо для кожного **джерела** картки: `issue`, `pullRequest`, `gitlabIssue`, `gitlabPullRequest`, `manual` тощо.
2. **Правила подій** (`events.<інтеграція>.<подія>`): реакція на вебхук, наприклад `issueOpened` чи `pullRequestMerged`.
3. **Правила інструментів** (`tools.<інструмент>.onResult`): реакція на результат інструмента агента. Наприклад, `submit_plan` з «Plan approved.» переносить картку в Execute, а вердикт рев'ю «approve» запускає відкриття PR.
4. **Transition policy:** чиста перевірка «можна чи не можна» на кожен перехід, наприклад «без затвердженого плану в Execute не можна» чи «Done лише після merge».

**Дефолти інтеграції проти правил дошки** (`core/src/rules/event-rules.ts`). Кожна інтеграція має свої правила за замовчуванням (`integration-github/src/default-rules.ts`). Для події порядок такий:

1. Явний обробник у конструкторі інтеграції (`rules[подія]`) перемагає все.
2. Інакше працює обробник дошки (`events.github.issueOpened`). Якщо він нічого не повернув, лишається дефолт; якщо повернув `null` — дефолт вимкнено.

**Приклад: issue на GitHub → картка → план.**

1. Вебхук `issueOpened` → дефолтне правило повертає `upsertLinkedWorkItem` → картка Work у фазі Intake.
2. Людина перетягує картку в Triage → policy дозволяє → `onEnter.issue` повертає `invokeSkill(factory-triage)`.
3. Агент пише коментар тріажу і викликає `factory_transition_work_item(planning, triageType: bug)` → policy перевіряє → `onEnter` у Planning запускає `factory-plan`.
4. Новий коментар в issue → дефолт `retriageGithubIssue` (крім фаз Execute і Review).
5. Issue закрили → `sourceClosed` дошки → картка в Done чи Canceled.

**Менеджери задач.** Linear, Jira й incident.io у v4 прибрано: їхній код є в `v3/packages/factory/src/integrations/` і в git-історії v4 (коміт `1fe8435`). Словник подій для них у `core` ще лишився, тож повернути їх відносно легко.

## Розширення

Як пишуться розширення (додаються нові інтеграції) або замінюються старі?

### Відповідь

Інтеграція — це пакет `packages/integration-<x>`, який реалізує `FactoryIntegration` (`packages/integrations/src/base.ts`).

- **Обов'язково:** `id`, `routes(ctx)` (статус, вебхук), `diagnostics()`.
- **Опційно:**
  - `intake` — задачі (`capabilities/src/intake.ts`: `listSources`, `listItems`, `listIssues`, `getIssue`, `createComment`, `updateIssue`, `resolveIntakeDispatch`);
  - `versionControl` — PR/MR, рев'ю, коментарі, чеки;
  - `workers` — інтервальні reconcilers;
  - `agentTools` / `sessionTools` — інструменти агенту;
  - `channels` — чати;
  - `feedPublisher` — дзеркалити коментарі назовні;
  - `initialize`.

Інтеграція отримує `IntegrationContext`: auth, sandbox, controller, сховища, `runtime.workItems`, `boards`, hooks.

**Кроки, щоб додати нову** (Linear, Jira, Bitbucket…):

1. Скопіювати `packages/integration-gitlab`: він менший і загальніший за GitHub. Для Linear чи Jira взяти код з v3.
2. Реалізувати `FactoryIntegration` і `default-rules.ts`. Обробник вебхука будує контекст, викликає `selectEventRule`, а потім `commitRuleEvaluation`.
3. **Новий провайдер** (якого нема в core): розширити `WORK_ITEM_SOURCES`, `FACTORY_RULE_SOURCES`, події, rule context і actor у `core/src/rules/types.ts`, а також `BOARD_EVENT_NAMES` у `define-board.ts`. Linear і Jira в core вже описані.
4. Створити інтеграцію з env в `apps/server/src/mastra/index.ts`, додати її в `integrations` і в залежності `apps/server/package.json`.
5. Для VCS-провайдера виправити місця, де захардкоджено GitHub чи GitLab: `server/src/factory.ts`, `api/src/surface.ts`, `api/src/intake.ts`.
6. Запустити `pnpm verify` і оновити `migration/test-pairs.tsv`.

### ClickUp: що потрібно для інтеграції і що працюватиме

**Модель ClickUp:** Workspace → Space → Folder (не обов'язково) → List → Task → Subtask.

- Статуси задаються на Space, Folder чи List, і List може їх перевизначити.
- Є custom fields на List, коментарі (з тредами), Docs і Chat.

**Як лягає на фабрику:**

| ClickUp | Фабрика | Що зробити |
| --- | --- | --- |
| Workspace | org | один OAuth-застосунок на workspace |
| Space / Folder / List | джерело intake → прив'язка до фабрики (проєкту) і дошки | `listSources` повертає List-и; прив'язка через `/web/intake/bindings` |
| Task | картка (`upsertLinkedWorkItem`), source `clickupTask` | нове джерело в core (див. крок 3 у «Кроки, щоб додати нову» вище) |
| Статуси ClickUp | фази дошки | мапа статус ↔ фаза в правилах інтеграції |
| Tags / custom fields | мітки, label routes | вибір дошки за тегом, як мітки GitHub |
| Коментарі | ретріаж за коментарем, коментар тріажу агентом | `createComment` в `Intake` |
| Закриття задачі | `sourceClosed` дошки | подія `taskStatusUpdated` до closed |
| Вебхуки | вебхук-маршрут інтеграції | є події задач, коментарів, list/folder/space |

**Що працюватиме:**

- задачі → картки;
- оновлення, призначення, статуси, коментарі через вебхуки;
- reconciler на інтервал (ловить пропущені вебхуки);
- агент коментує й змінює задачу (`updateIssue`, `createComment`);
- маршрутизація за List або тегом.

**Що не працюватиме або буде слабко:**

- **Дошки ClickUp ≠ наші дошки.** Board view в ClickUp — лише вид на List. Ми не синхронізуємо налаштування колонок; рухаємо задачу, змінюючи статус.
- **Chat:** API v3 є, але позначене експериментальним («може змінитись будь-коли»), і **вебхуків на повідомлення чату нема**. Чат як канал (як був Slack) можливий лише опитуванням — ненадійно.
- **Docs:** вебхуків нема; читати й писати через API можна (не перевірено повністю).
- **Код ClickUp не дає** — PR лишаються на GitHub чи GitLab, а задача лише посилається на них.

**Нюанси:**

- вебхук належить користувачу, чий токен його створив, і тихо зникає, якщо цього користувача вимкнули — краще окремий сервісний акаунт;
- rate limit — 100 запитів на хвилину на токен на Free/Business, більше на дорожчих планах;
- є **офіційний MCP-сервер ClickUp** (`https://mcp.clickup.com/mcp`, beta, лише OAuth). Його можна дати агенту як інструмент без інтеграції. Задачі з нього не стануть картками автоматично.

**Обсяг роботи:** пакет `packages/integration-clickup` за зразком `integration-gitlab` (OAuth, вебхук з перевіркою підпису, reconciler, `Intake`, default rules) плюс нове джерело в `core`. За обсягом це схоже на колишню Linear-інтеграцію з v3 — її варто взяти за зразок.

**Зроблено (2026-10-28): ClickUp через polling** — `packages/integration-clickup`, без вебхука.

- **Env:** лише `CLICKUP_API_TOKEN` (personal token `pk_...`) і, за потреби, `CLICKUP_POLL_INTERVAL_SECONDS` (мін. 15, за замовчуванням 60). Без токена інтеграція не підключається. *Змінено 2026-11-12 ([ADR-0032](adr/0032-integration-tokens-belong-to-organization.md)): токен — організації, його підключає адміністратор у «Підключеннях»; `CLICKUP_API_TOKEN` більше не читається (один раз переноситься в `factory-local-org`).*
- **Налаштування в UI** (Settings › Intake › ClickUp): стан токена, перемикач синхронізації, вибір Lists, маршрутизація List → фабрика + дошка, маршрути тег → дошка на фабрику, перемикач «Автоматично запускати триаж».
- **Intake:** `listSources` повертає Lists (`Space / Folder / List`), `listItems`/`listIssues`/`getIssue`, `createComment`, `updateIssue` (статус за типом чи назвою).
- **Поллер:** нова задача → картка через `upsertLinkedWorkItem` (ідемпотентно, ключ `clickup:task:<id>:created`), джерело `clickup-task`. Дошка: маршрут за тегом, інакше дошка прив'язки List. List без прив'язки й дошки ігнорується. Задача, закрита в ClickUp, переносить картку за `sourceClosed` її дошки. Метадані наявної картки оновлюються.
- **Автозапуск:** лише для задач, створених після старту сервера, на дошках із фазою `triage`. Решта чекає в Intake.
- Фази дошок трактують `clickup-task` як `manual`. Текст задачі лежить у метаданих `description` і потрапляє в промпт скілів як untrusted.
- **Межі:** токен лише в env (UI його не вводить); коментарі й статуси назад автоматично не пишуться (лише інструментами агента через Intake); чат не опитується.

**Замінити інтеграцію:** прибрати її з `integrations` у хості і поставити нову з тим самим набором capabilities. Поведінку дошки можна змінити без заміни інтеграції: обробник подій на дошці (`events`) перекриває дефолт інтеграції.

**Інші розширення:**

| Що | Як |
| --- | --- |
| Нові скіли | `factory-skills/` або в самому репозиторії: `.claude/skills`, `.agents/skills`; файли `AGENTS.md` і `CLAUDE.md` теж підхоплюються |
| Нові CLI в пісочниці | `setupCommand`, `workspaceSetupCommand`, образ шаблону |
| MCP для агента | `.mcp.json` / `~/.mastracode/mcp.json` — зараз на рівні хоста, а не проєкту |
| Браузер | у продакшн-коді не налаштований, лише фейковий у e2e-тестах |

## База знань (Knowledge)

Як формується база знань (Knowledge)? Чи можна підключати аналоги (які є аналоги і як їх підключити)? Як вона інтегрована з кодовим агентом — через MCP?

### Відповідь: як формується

Knowledge — це **експериментальна** функція Mastra («subconscious»), а не код фабрики. Фабрика лише показує граф у UI (`packages/api/src/knowledge.ts`, усі маршрути тільки GET) і задає scope.

**Вмикання.** За замовчуванням вимкнено. Потрібні дві речі:

- `MASTRACODE_EXPERIMENTAL_SUBCONSCIOUS=1` (або передати свій `knowledge` у `MastraFactory`, `packages/server/src/factory.ts:804`);
- vector store: `PgVector`, коли є `DATABASE_URL`, інакше локальний файл `mastra-vectors.db` поруч із базою (`apps/server/src/mastra/local/local-vector.ts`).

**Хто пише.** Ніхто вручну. Поруч з агентом працює фоновий агент-куратор (`Subconscious` з `@mastra/memory`, підключений у `@mastra/code-sdk/dist/agents/memory.js`). Після розмов він сам витягає стійкі факти й складає з них граф:

- **вузли:** рішення, вподобання, люди, файли, репозиторії, картки;
- **записи** про ці вузли, зі зв'язками через `[[wikilinks]]`;
- **закріплені (pinned)** записи.

Для фабричних сесій куратор робить до 25 кроків. Він працює поверх Observational Memory: спостереження та рефлексія над історією сесії.

**Scope (ієрархія видимості).**

- `org` → `resource` (= **проєкт фабрики**: один граф на проєкт, спільний для всіх його сесій) → `thread`.
- Org сесія отримує при створенні (`packages/session/src/org-seed.ts`). Без org запис вимикається повністю, тобто fail closed.
- Локальний TUI пише під org `local`.

**Зберігання:** домен `knowledge` у сховищі Mastra (libsql/pg) плюс вектори для семантичного пошуку.

### Відповідь: як агент нею користується

Через MCP — **ні**. Це вбудовані інструменти агента, які SDK реєструє, коли Knowledge увімкнено (`agents/prompts/tool-guidance.js`):

| Інструмент | Що робить |
| --- | --- |
| `knowledge_search` | лексичний + семантичний пошук факту |
| `knowledge_read` | відкрити вузол і записи про нього |
| `knowledge_browse` | список вузлів за типом чи префіксом, зв'язки й backlinks |
| `ask_memory` | асинхронне питання «помічнику пам'яті»; відповідь приходить пізніше повідомленням `<remind-answer>` |
| `recall` | пошук по минулих розмовах (а не по фактах) |

Крім того, куратор сам підкладає агенту в контекст нагадування (`<remembered>`) і закріплені знання.

MCP-сервер фабрики (`packages/mcp`, `/web/factory/projects/:projectId/mcp`) — інша річ. Він працює в зворотний бік: віддає інструменти фабрики зовнішнім клієнтам (ChatGPT, Claude, Claude Code). Knowledge він поки не відкриває; у дизайні системи знань (розділ «Система знань») саме через нього знання мають віддаватись будь-якому харнесу.

### Відповідь: аналоги і як підключити

Три способи, від найпростішого:

1. **Статичні знання в репозиторії.** `AGENTS.md`, `CLAUDE.md` і скіли в `.claude/skills` або `.agents/skills` агент підхоплює сам. Це найнадійніше для правил, архітектури й конвенцій.
2. **Через MCP як окремий інструмент агента.** Додати сервер у `.mcp.json` або `~/.mastracode/mcp.json`; зараз це конфіг рівня хоста (сервера), а не проєкту. Кандидати:
   - пам'ять і граф: **Graphiti / Zep**, **mem0 / OpenMemory**, **Cognee**, **Letta**;
   - документація бібліотек: **Context7**;
   - база знань команди: **Notion**, **Confluence**, **Obsidian** (MCP-сервери);
   - код: Sourcegraph, Greptile.
   
   Агент побачить їх як звичайні MCP-інструменти, але куратор Mastra туди писати не буде.
3. **Замінити рушій Knowledge.** Передати свій екземпляр `Knowledge` з `@mastra/core/knowledge` через `MastraFactory({ knowledge: { key, instance } })` (`packages/server/src/factory.ts:215`). Він може мати власне сховище. Інструменти `knowledge_*` і UI працюватимуть поверх нього. API позначене `@experimental`, тому може змінитись.

Рекомендація: правила й архітектуру тримати в `AGENTS.md` і скілах; Mastra Knowledge увімкнути для автоматичної пам'яті проєкту; зовнішню документацію (Context7, Notion) підключати через MCP.

> **Оновлено 2026-10-27:** після обговорення ця рекомендація переглянута. Subconscious не підходить на роль канонічної системи знань (неперевірені факти в БД, працює лише з Mastra-харнесом). Новий дизайн — у розділі «Система знань: дизайн» нижче.

## «Ваші моделі» і «Моделі фабрики»

Чому є «Your models» і «Factory models»? Як вони використовуються? Я думав, простіше: якщо відповідь не подобається — перемкнути модель.

### Відповідь

Перемикати модель в чаті можна, і це працює: `ModelPicker` у статус-рядку чату. Дві вкладки відповідають не на питання «яка модель», а на питання **чиї ключі й хто платить**:

| | Factory models | Your models |
| --- | --- | --- |
| Ключі | спільні для org (адміністратор), зокрема OAuth-підписка org | особисті ключі або підписка конкретного користувача |
| Модель за замовчуванням | `defaultModelId` фабрики | особиста за замовчуванням (`user_default_models`) |
| Навіщо | автономні запуски по картках: агент працює вночі з вебхука, коли людини поруч нема | інтерактивний чат користувача на його власному акаунті (Claude Pro/Max, ChatGPT) |

Хто чим користується, визначає `modelScope` проєкту (`store/src/projects/base.ts:17`):

- `factory` — усе йде на моделях фабрики;
- `user` — усе на моделях користувача;
- `hybrid` — картки на моделях фабрики, чат на моделях користувача.

Навіщо розділяти:

- **автономні запуски** не повинні залежати від того, чи підключив конкретна людина свій ключ, і не повинні з'їдати її особистий ліміт;
- **у команді** кожен може працювати у своїй підписці;
- кожна відповідь агента позначена, який ключ її дав.

Якщо працюєте сам, це зайва складність: поставте `modelScope = user` (або `factory`) і користуйтесь однією вкладкою.

### Як лишити тільки моделі фабрики

Логіка «фабрика належить організації; працюєш у їхній фабриці — їхні ключі і їхні моделі» — це саме scope `factory`. Upstream назвав це «exclusive scope» (#26934): фабрика бере один scope і ніколи не переходить на інший.

**Що можна вже зараз, без коду:** Settings → Factory models → «Model scope» = **Factory** (або `PATCH /web/factory/projects/:id` з `modelScope: 'factory'`). Змінювати може лише адміністратор org. Після цього:

- чат, картки й Supervisor працюють лише на ключах і моделях org;
- у виборі моделі тільки моделі, для яких у org є ключ;
- посилання «Login» ведуть у налаштування фабрики.

**Що лишиться зайвим:** пункт «Your models» у налаштуваннях і в пошуку (`SettingsNavigation.tsx:64`). Його сторінка покаже «This Factory uses organization credentials only», але далі показує особисті замовчування й ключі (`PersonalModelsSettings.tsx`).

**Щоб прибрати повністю** (код, ще не зроблено):

1. Зробити `factory` значенням за замовчуванням (зараз за замовчуванням `hybrid`) або прибрати `user` / `hybrid` з налаштувань.
2. Ховати «Your models» з навігації й пошуку, коли scope = `factory`.
3. Перенести з upstream #28402: кожен чат бере замовчування лише зі своєї картки, без змішування.

Пункт 2 зачіпає UI, де зараз ідуть переклади, тож краще робити після них.

Обмеження перемикання:

- у scope `factory` скинути модель на «особисту за замовчуванням» не можна (`ModelPicker.tsx:83`);
- у списку лише моделі провайдерів, для яких є ключ у відповідному scope;
- модель, яку обрали для картки, береться з налаштувань фабрики, а не з вашого чату.

## Керування агентом під час роботи

### 1. Що агент робить сам, а що питає в людини?

Інструменти поділено на категорії `read`, `edit`, `execute`, `mcp` (`code-sdk/dist/permissions.js`).

- **Без yolo:** `read` дозволено, решта — питати людину.
- **Yolo:** дозволено все.
- **Завжди дозволено:** `ask_user`, `task_*`, `submit_plan`, `request_access`.
- **Пріоритет:** правило на інструмент → дозвіл, виданий у сесії → категорія → «питати».

SDK стартує з `yolo: true`, і фабрика це не перекриває (`packages/server/src/factory.ts:1405`). Тому сесії карток, найімовірніше, працюють у yolo — не перевірено до кінця.

Інструменти фабрики належать до `mcp`. Частина з них дозволена явно (`harness-mastra/src/tools/permissions.ts`), а на старті запуску дозволяється `factory_transition_work_item`.

Якщо виклик чекає схвалення:

- сповіщення йде туди, звідки прийшла сесія (`tools/reports.ts`);
- відповісти може лише залогінена людина (`factory_answer_approval`);
- правила на категорії налаштовуються в Settings → Behavior.

### 2. Затвердження плану і людські ворота

- **`autoApprovePlans` вимкнено** (за замовчуванням): агент не перейде planning → execute без затвердженого `submit_plan` (`pipelines/src/work/transition-policy.ts:21-38`).
- **`autoApprovePlans` увімкнено:** dispatcher сам затверджує план, до 3 разів. Далі план чекає людину як attention «Plan waiting for review».
- **Людина обов'язкова:**
  - прийняти не-баг картку в Planning чи Execute;
  - перевести картку в `accepted` на Acceptance.
- **Агенту заборонено:**
  - закрити картку з відкритим PR або після того, як рев'ю попросило змін;
  - рухати картку, яку self-review відклав для людини.

### 3. Чи можна втрутитись у запущену сесію?

Так. Сесію картки можна відкрити з UI (`RelatedFactorySessions.tsx`) і писати в неї. SDK уміє:

- `steer` — повідомлення агенту посеред ходу;
- `abort` — перервати;
- `followUp` — поставити наступне повідомлення в чергу;
- створювати, перейменовувати й видаляти треди.

Dispatcher перериває потік, коли рішення має `cancelInFlight`. Якщо картка тим часом перейшла далі, запуск закривається як «superseded», а не як помилка. Як ручний steer посеред запуску впливає на dispatcher — не перевірено.

### 4. Goal loop

`GoalManager` у SDK тримає мету на тред. Він крутить ходи, поки модель-суддя не скаже «досягнуто», максимум 50 ходів. У фабриці мету можна поставити лише з UI (slash-команда). **Фази дошок його не використовують**: їх рухають правила і скіли.

Ідея для якості: робоча фаза з метою на кшталт «тест X проходить», щоб суддя перевіряв результат замість агента.

### 5. Як агент питає людину (ask_user, request_access)?

Обидва інструменти призупиняють запуск і чекають на відповідь.

- У запусках карток dispatcher фіксує призупинення, і сесія з'являється в attention як `agent-waiting`.
- Людина відповідає, відкривши сесію. Звіт про завершення запуску позначає його як `blocked`.
- Скіл self-review прямо забороняє чекати людину.

## Нагляд і якість

### 6. Supervisor

Health worker запускається кожні 5 хв (`packages/supervisor/src/health.ts`) і шукає:

| Проблема | Що означає |
| --- | --- |
| `decision-stuck` | рішення не виконується |
| `start-stalled` | старт запуску завис |
| `seat-orphaned` / `seat-missing` | сесія без картки чи картка без сесії |
| `held-waiting` | картка довго чекає |
| `label-drift` | мітки в issue і стан картки розійшлись |

**Виправляти сам не може.** Усі його write-інструменти питають людину (`requireApproval: true`):

- повторити або відкинути рішення;
- перенести картку;
- вирівняти мітки;
- відкликати сесію;
- надіслати сигнал сесії.

Кожна дія потрапляє в аудит від імені людини з `cause: 'supervisor'`.

### 7. Де подивитись, що зробив агент?

- **Аудит:** кожен запуск пише `factory.run.started` і `factory.run.ended` з токенами на кожен крок (`runtime/src/run-audit.ts`). Решта дій — `work_item.*`, `git.*`, `agent.*`, `intake.*` (`store/src/audit/actions.ts`).
- **Де читати аудит:** `GET /web/factory/projects/:id/audit` і таймлайн картки в UI (`WorkItemActivity.tsx`).
- **Звіт про запуск** (done / failed / blocked): сповіщення тому, хто стежить за запуском.
- **Повний запис:** транскрипт сесії.

### 8. Сповіщення, коментарі, attention

- **Сповіщення** мають пріоритет `low` / `medium` / `high` / `urgent`. `high` і `medium` будять тред, у якому агент зараз нічого не робить.
- **Коментарі:** `/web/factory/work-items/:id/comments`, зі згадками. Живі оновлення приходять через pubsub `factory.feed.<org>.<project>`.
- **Attention** («потребує уваги») має 6 типів: `automation-failed`, `automation-proposed`, `mention`, `activity`, `supervisor-finding`, `agent-waiting`.

Upstream 2026-10-23 прибрав сторінку Activity і сповіщення (#28257) — див. розділ про upstream нижче.

### 9. Self-review: як налаштувати якість?

- Вмикає дошка, а не проєкт: картка проходить self-review, коли на її дошці є фаза self-review (робоча фаза в контексті `review`, що дає лише `factory_record_review_verdict`). Перемикач `selfReviewEnabled` прибрано (upstream `d5d36fd813`); проєкти, де він був вимкнений, втратили цю фазу на своїх дошках один раз при міграції `self-review-switch-v1`.
- Ліміт — `SELF_REVIEW_ROUND_LIMIT = 3`, захардкоджено (`pipelines/src/work/phase-rules.ts:69`). Кожен третій «request changes» відкладає картку в Intake з `selfReviewNeedsHuman`. Якщо людина поверне її в роботу, агент отримає ще 3 раунди.
- **Критерії якості — лише текст скіла** (`factory-self-review/SKILL.md`, бере фази 3–5 з `factory-review`). Налаштування на проєкт нема. Щоб змінити критерії, треба правити скіл або покласти свій у репозиторій (`.agents/skills`).

## Пам'ять і контекст

### Скільки витрачено токенів: де це було і чи повернути

Окремої сторінки токенів **не було ні в v3, ні в v4, ні в upstream**: у старих версіях Overview її теж нема. Мабуть, мова про одне з цього:

- команда чату **`/cost`**: prompt, completion і total токенів поточної сесії (`useChatCommandRegistry.ts:177-184`);
- бюджет токенів пам'яті в статус-рядку чату (`OperationalMemoryStatus.tsx`);
- сторінка **Activity**, групування None → Details події `factory.run.ended`: там сирий JSON з `usage`.

**Дані вже збираються.** Кожен запуск пише в аудит `factory.run.ended` поле `metadata.usage` з загальними сумами і розбивкою по кроках: prompt, completion, total, reasoning, cached input, cache creation (`runtime/src/run-audit.ts:63-125`). Плюс роль і картка. **Ціни в доларах нема.**

**Як повернути (зробити) сторінку витрат:**

1. API-агрегація над подіями `factory.run.ended` за днем, роллю, карткою й моделлю — поруч із `packages/api/src/metrics.ts`.
2. Таблиця цін моделей для доларів (каталог моделей SDK, models.dev).
3. Сторінка в UI (маршрут `metrics` зараз перенаправляє: `router.tsx:160`).

Це невелика окрема задача, але це UI, тож після перекладів.

### 10. Observational Memory і що агент бачить на старті

**Пороги за замовчуванням:** observation — 30 000 токенів, reflection — 40 000 (`session/src/memory-settings-hydration.ts`).

- Пороги зберігаються на (org, user); особисте значення перекриває проєктне.
- Поріг observation має бути більшим за 2000.
- Нижчий поріг: спостерігач і рефлектор запускаються частіше (дорожче), зате контекст довгих сесій лишається малим.

**На старті агент бачить:**

- `<factory-phase>`: дошка, фаза, роль, ревізія, інструкція викликати `factory_transition_work_item` з `expectedRevision`;
- рядок «Target repository»;
- розкладку репозиторіїв: один репозиторій — робоча тека і є клоном; кілька — корінь із теками, кожна зі своїми `AGENTS.md`, `CLAUDE.md` і скілами;
- скіл або промпт фази.

## Безпека

### 11. Чужий (ненадійний) код

Сесія вважається untrusted, якщо картка прийшла з PR або має `externallyAuthoredWorkItem` (`harness-mastra/src/rules/start-coordinator.ts:250-273`). Що обмежено:

- **Пам'ять:** окремий ресурс пам'яті. Сесія не читає спостереження довірених запусків і не може підкинути свої.
- **Інструкції:** `AGENTS.md` і `CLAUDE.md` беруться лише з базової гілки PR, не з коду PR.
- **Метадані PR** в промпті позначено «лише дані».
- **Push** від чужих не запускає збірки чи рев'ю.

Довірені автори: ті, хто має доступ admin, maintain або write, плюс боти з `MASTRACODE_GITHUB_AUTHORIZED_BOTS` (за замовчуванням coderabbitai і devin).

### 12. Секрети в пісочниці (Firebase, Apple)

- **Локальна пісочниця** отримує від хоста лише allowlist змінних: `HOME`, `USER`, `SHELL`, `LANG`, `TZ`, `GIT_*`, `SSL_CERT_*` тощо (`apps/server/src/mastra/index.ts:222-249`).
- **`GH_TOKEN`** вставляється окремо через `setEnv` і оновлюється.
- **Сховища секретів на проєкт нема.** `sandboxSettings` містить лише CPU, пам'ять і idle timeout; сховище credentials — лише для ключів моделей.

Варіанти для Firebase чи Apple:

1. Отримувати секрети в `setupCommand` із зовнішнього менеджера (1Password CLI, Doppler, gcloud secrets). Найчистіший варіант.
2. Додати свій `setEnv` у харнесі. Це потребує коду, зате працює для будь-якого провайдера.
3. Розширити allowlist. Працює лише локально, і **секрети потраплять і в untrusted-сесії**.

Секрети для untrusted-сесій потрібно вимикати окремо.

## Розгортання і масштаб

### 13. Що потрібно для продакшну

| Що | Навіщо |
| --- | --- |
| `DATABASE_URL` (Postgres + PgVector) | основна база і вектори; без неї libSQL-файл |
| `REDIS_URL` | шина подій і leases між процесами; обов'язкова для більш ніж однієї репліки |
| `MASTRACODE_DISTRIBUTED_LOCK` (увімкнено за замовчуванням) | Postgres advisory lock для git-запису; потребує Postgres |
| Провайдер пісочниці | Platform, E2B або local (явно) |
| `FACTORY_CREDENTIAL_ENCRYPTION_KEY` | шифрування ключів |
| Вхід | WorkOS або Platform |
| GitHub App | змінні `GITHUB_APP_*` |

`apps/server/docker-compose.yml` — лише для локальної розробки (pgvector і redis). `MASTRACODE_MAX_SANDBOXES` є в схемі, але в коді v4 використання не знайдено.

### 15. Збірки середовища

- **Тригери:** `manual`, `schedule` (cron на проєкт), `push` у гілку за замовчуванням (якщо `buildOnPushEnabled`). Push і розклад пропускають збірку, коли HEAD репозиторіїв не змінились.
- **Провайдери:** E2B і Platform уміють; Local — ні.
- **Коли потрібно:** setup довгий (`pod install`, `flutter pub get`, великі залежності). Тоді образ «запікається» один раз, і сесії стартують швидко.

## Налаштування без коду

### 16. Чи можна налаштовувати дошки й правила з чату або з ChatGPT/Claude?

**Ні, лише кодом.** Скіл `configure-factory-rules` прямо каже: правила — це довірений серверний код. Агент редагує TypeScript (`defineBoard`, опції `MastraFactory`, `rules` інтеграцій), і після цього потрібен redeploy. Тобто «з чату» означає: кодовий агент правит код фабрики.

MCP-сервер фабрики (`/web/factory/projects/:projectId/mcp`, OAuth для ChatGPT і Claude) дає інструменти:

- створювати, оновлювати, переносити, переглядати картки;
- запускати сесії й надсилати їм сигнали;
- схвалення;
- підписки;
- `search` / `fetch`.

Інструментів для правил і дошок там нема.

**Наскільки повна інтеграція з Claude (ChatGPT) через MCP.** Це не повний доступ до фабрики, а набір інструментів роботи з картками і сесіями.

- **Вхід:** OAuth bearer-токен від провайдера входу фабрики. Відповідь 401 містить `WWW-Authenticate` з посиланням на метадані (RFC 9728). Виклики йдуть від імені користувача, як з веб-UI; потрібна org.
- **Обмежень нема:** ні OAuth scopes, ні rate limits.
- **Сесія:** кожен користувач отримує приватну connector-сесію.
- **Що дає:**
  - картки: список, перегляд, створення, оновлення, перенесення, підписка;
  - attention: список; рішення: повтор, відкидання; пропозиції: схвалення;
  - сесії: запуск, сигнал, список і підписка на під-сесії, зміна моделі;
  - відповідь на запит схвалення;
  - `search` і `fetch` за назвами карток.
- **Чого не дає:** база знань (Knowledge), транскрипти сесій, налаштування, моделі й ключі, правила, аудит, метрики, усі інструменти `source_control_*` (PR, рев'ю).
- **Перенесено з upstream #28019 (2026-10-27, коміт `fe465cb`, новий пакет `packages/mcp`):**
  - CORS-заголовки для браузерних клієнтів (Claude connectors);
  - stateless-режим для старих клієнтів (VS Code, Cursor, Claude Code) — через патч `patches/@mastra__mcp@2.5.0.patch`, бо опція `legacy` є лише в `@mastra/mcp` 2.6 (прибрати патч після оновлення);
  - текст `instructions` для клієнта;
  - подія `factory.activity` (поки лише опитуванням; Claude і ChatGPT її не використовують);
  - картка «MCP-клієнти» в Налаштування → Підключення з URL та кроками для Claude, Claude Code і ChatGPT.
- **Локальний режим (наш, не з upstream; прибрано разом із local dev auth, ADR-0030):** з `FACTORY_LOCAL_DEV_AUTH=1` ендпоінт працював без OAuth-сервера (`mcp: { tokenless: true }`).
- **Вхід MCP-клієнтів (ADR-0030, доповнення 3):** сервер з `FACTORY_AUTH=google` сам є OAuth-сервером (better-auth `@better-auth/oauth-provider` під `/auth/api`): реєстрація клієнта без облікового запису (RFC 7591), authorization code + PKCE, вхід — наш Google, згода на сторінці `/oauth/consent`. Підключення Claude Code:
  ```
  # сервер на Mac mini (Tailscale)
  claude mcp add --transport http factory https://factory.tail5c61c7.ts.net/web/factory/projects/<projectId>/mcp
  # dev:local на своїй машині
  claude mcp add --transport http factory-local http://localhost:5874/web/factory/projects/<projectId>/mcp
  ```
  Далі в Claude Code — `/mcp` → `factory` → Authenticate: відкривається браузер, вхід через Google (якщо ще не ввійшли), сторінка «Дозволити доступ до Factory» → «Дозволити»; Claude Code отримує токен сам. `<projectId>` — id Factory (Налаштування → Підключення → MCP-клієнти показує готову адресу). Адреса має бути тією, що в `MASTRACODE_PUBLIC_URL` сервера: метадані й токени видаються для неї, тож до сервера на Tailscale через `localhost` не підключитись.
  Claude.ai і ChatGPT підключаються так само, але їм потрібна публічна HTTPS-адреса (Tailscale Funnel чи власний домен), бо вони ходять зі своїх серверів.
- **Як влаштовано:** MCP — окремий канал взаємодії поруч з веб-UI та HTTP API (`@factory/api`). Інструменти ті самі, що в агентів (`createFactoryTools` передає сервер), тож MCP не залежить від рушія агентів і не дає нічого понад права користувача в UI.

### 17. Чи можна додати дошку конфігом?

Ні. Тест `custom-board-runtime.test.ts` будує дошку `release` у TypeScript і передає її в `MastraFactory`; «runtime» у назві означає поведінку дошки під час роботи. Дошок у базі чи в API конфігу нема.

Для вас це означає: дошки «Spec» чи «Bug» — це код у `packages/pipelines`, деплой разом із сервером.

## Claude Code як другий харнес

Обговорення 2026-10-27. Питання: чи можна додати Claude Code всередину фабрики як окремий харнес (рушій агентів), поруч з Mastra.

### Навіщо

**Головна мотивація — підписка Claude Pro/Max.** Вхід Anthropic у Mastra-харнесі не дає працювати на підписці; підписка працює лише в самому Claude Code (офіційному клієнті Anthropic). Тобто Claude Code-харнес — це спосіб запускати агентів фабрики на підписці. Без цієї причини таку складність не варто було б братися.

### Коротко

Можливо, але не все переноситься 1:1, і спершу треба відв'язати ядро фабрики від Mastra. Окремо від цього Claude Code уже працює як **клієнт** фабрики через MCP (див. питання 16): людина в Claude Code керує картками. Тут мова про інше: щоб агенти фабрики (розбір, план, реалізація) працювали на Claude Code.

### Що заважає зараз

Типи `@mastra/core/agent-controller` (сесія, події агента) використовують не лише `harness-mastra`, а й `runtime` і `session`, усього ~40 файлів у 12 пакетах. У `runtime` залежність невелика: 4 файли (`dispatcher.ts`, `run-audit.ts`, `skills/service.ts`, `skills/rescan.ts`).

Тому крок 1 — **контракт харнесу**: власний опис того, що фабрика робить з агентом, без типів Mastra. Mastra-харнес стає першою реалізацією, Claude Code — другою. Цей крок потрібен за будь-якого рішення і вже стоїть у плані v4 («відв'язати харнес від Mastra»).

### Сесії: що відбувається в одній, що в різних

Перевірено в коді (`inheritEarlierSession`, `packages/api/src/surface.ts`):

| Етап | Роль | Сесія |
| --- | --- | --- |
| Розбір | `triage` | нова сесія картки (гілка, пісочниця, тред) |
| Планування | `plan` | **та сама** — агент пам'ятає розбір |
| Реалізація | `work` | **та сама** — пам'ятає план, навіть якщо план затвердила інша людина |
| Перевірка, самоперевірка | `review` | **окрема** сесія, щоб рецензент не був упереджений контекстом автора |

Повернення на етап продовжує ту саму сесію коротким «продовжуй» (`resume`), без повторного скіла.

**Правило для двох харнесів:** харнес вибирається при старті картки (замовчування фабрики або дошки), закріплюється за сесією і не міняється до кінця. У межах харнесу можна міняти модель і рівень міркування.

### Що лягає добре

| Фабрика | Claude Code (Agent SDK або `claude -p --output-format stream-json`) |
| --- | --- |
| Скіл етапу | промпт + скіли в `.claude/skills` (Claude Code їх розуміє нативно) |
| Інструменти фабрики `factory_*` | через MCP — пакет `@factory/mcp` |
| Одна сесія на розбір → план → реалізацію | `--resume <sessionId>` |
| Модель, рівень міркування | `--model`, `--effort` між ходами однієї сесії |
| Авторизація | env на сесію: `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL` (DeepSeek та інші Anthropic-сумісні), Bedrock/Vertex |

### Що складно

1. **Чат в UI.** UI бере історію з треду в сховищі (`MastraDBMessage`) і живі події (`message_*`, `tool_*`, `agent_end`) з потоку AgentController. Готового рішення нема: `@mastra/claude` (upstream `agent-sdks/claude`) віддає лише текст, без викликів інструментів, без пам'яті і навіть без `sessionId`. Тож харнес має сам: (а) після кожного ходу писати повідомлення в той самий тред, (б) перекладати потік Claude у наші події. Тоді UI не помітить різниці. Paperclip робить так само (свій формат транскрипту + парсер `stream-json`), тобто перевірено практикою.
2. **Пісочниця.** Claude Code працює з локальними файлами, тож процес `claude` має жити всередині пісочниці (Node + CLI в образі), а події — стрімитись на сервер.
3. **Затвердження плану й інші людські ворота.** Зараз `submit_plan` — пауза інструмента з відновленням (механізм Mastra). Для Claude Code обрано **«завершити хід і продовжити сесію»**:
   - `submit_plan` одразу відповідає «план подано»; харнес бачить виклик і зупиняє хід (`interrupt()`);
   - картка чекає затвердження, пісочницю можна приспати;
   - після рішення харнес продовжує ту саму сесію (`resume`) повідомленням «план затверджено, реалізуй» або «потрібні зміни: …».

   Варіант «блокувати інструмент до рішення» відкинуто: таймаути MCP, процес і пісочниця живуть годинами, перезапуск сервера все губить. Paperclip теж не блокує, а будить агента після відповіді людини.
4. **Акаунти.** Сесія Claude — файл `<CLAUDE_CONFIG_DIR>/projects/<cwd>/<id>.jsonl`, до акаунта не прив'язана. Paperclip при відновленні перевіряє лише cwd, набір інструкцій і місце запуску. Отже, сесію можна продовжити під іншим акаунтом (наприклад, коли один уперся в ліміт). На практиці не перевірено. Блокування не буде, якщо на сесію одночасно працює один процес (диспетчер це гарантує). Слабке місце: файл сесії живе в пісочниці — треба копіювати JSONL у наше сховище після кожного ходу. Ліміти: розпізнавати 429 і «usage limit… resets at», повторювати після скидання; ротацію акаунтів робимо самі (у Paperclip її нема).
5. **Підписка Claude Pro/Max** (`claude setup-token` → `CLAUDE_CODE_OAUTH_TOKEN` для неінтерактивного запуску). Запускається офіційний `claude` CLI під власною підпискою людини — саме тому харнес і потрібен. Обмеження, які треба поважати (перечитати актуальні умови Anthropic перед запуском для команди):
   - кожна людина працює під **своєю** підпискою (credential scope `user`: сесія картки йде під токеном власника сесії);
   - не віддавати одну підписку як сервіс іншим людям і не «пулити» чужі підписки для своєї роботи;
   - для спільних фабричних запусків (scope `factory`) — API-ключ, Bedrock або Vertex.

   Звідси наслідок для запуску: харнес викликає саме CLI `claude` (`-p --output-format stream-json --resume`), як Paperclip, а не підставляє токен підписки у власний HTTP-клієнт.
6. **Дозволи.** Paperclip за замовчуванням вмикає `--dangerously-skip-permissions`. Нам так не можна: у пісочниці явний `allowedTools` або колбек дозволів.

### Пам'ять і знання в Claude Code-харнесі

- **Observational memory** не обов'язково живе в агентному циклі Mastra. Є окремий API: `observe({ threadId, messages })`, `reflect()`, `buildContextSystemMessage()`; його вже використовує upstream-інтеграція `@mastra/opencode`. Для Claude Code: після ходу писати повідомлення в тред → `observe`; на старті чи `resume` додавати спостереження в системний промпт (`--append-system-prompt`). Втрачається лише робота посеред ходу; частково повертається хуком `UserPromptSubmit`.
- **Знання** — див. наступний розділ. Висновок: знання мають бути сервісом фабрики, незалежним від харнесу, і віддаватись через MCP + контекст на старті сесії.

### Рішення по відкритих питаннях (2026-10-27)

Пам'ять OM і Knowledge у нинішньому вигляді — внутрішня частина харнесу Mastra; у Claude Code свій харнес зі своєю пам'яттю. Різниця саме в цьому. Синхронізувати їх не будемо: Paperclip теж не синхронізує, а при перезапуску сесії вставляє в промпт нової сесії короткий підсумок (handoff markdown).

**1. Один харнес на фабрику чи різні?**

Рекомендація: один харнес на фабрику, вибирається при її створенні.

- Стан сесії (пам'ять, тред, скіли, формат подій) у кожного харнесу свій, тож перенести картку з одного харнесу в інший посеред роботи не вийде.
- Один харнес на фабрику дає одну модель пам'яті, одну поведінку агентів і простіші налаштування.
- Виняток на майбутнє: Перевірка іншим харнесом або моделлю. Рецензент і так працює в окремій сесії, а інший погляд (наприклад, Codex рецензує код Claude) корисний. Тобто харнес задається на фабрику, з можливим перевизначенням для ролі `review`.

Пам'ять між харнесами живе не в харнесі, а у фабриці:

- артефакти картки: план, коментарі, `implementation-notes`;
- знання в репозиторії (розділ «Система знань»);
- підсумок при перезапуску сесії, як у Paperclip.

Пам'ять харнесу (OM, auto memory Claude) лишається приватною.

**2. Кілька акаунтів і перемикання при лімітах**

Рекомендація: пул облікових даних у фабриці, спільний для всіх харнесів.

- Пул задається на провайдера: кілька ключів Anthropic, кілька DeepSeek тощо. Харнес на кожен хід отримує один ключ через env.
- Коли ключ вперся в ліміт, харнес повертає «ліміт до 14:30», а диспетчер вирішує:
  - є інший ключ того самого провайдера — продовжити ту саму сесію з ним;
  - нема — чекати скидання (так робить Paperclip).
- Продовжити сесію з іншим ключем можна, бо стан сесії не прив'язаний до акаунта:
  - у Mastra тред лежить у нашій БД;
  - у Claude Code це JSONL-файл.

  Для Claude Code це ще треба перевірити на практиці.
- Блокування не буде, якщо на одну сесію одночасно працює один процес. Диспетчер це вже гарантує.
- SDK Mastra вже вміє ротацію кількох акаунтів, фабрика її просто не використовує. Почати можна з неї, але правильніше одразу зробити пул у шарі облікових даних фабрики, щоб він працював і для Claude Code.
- **Для підписок Pro/Max** ротація — лише між власними обліковими даними тієї самої людини, якщо умови Anthropic це дозволяють; чужі підписки в пул не додаються (див. п. 5 у «Що складно»). Для API-ключів пул без цього обмеження.

**Стан (2026-10-28, гілка `feat/claude-accounts`): зроблено для Claude Code-харнесу.**

- Акаунти Anthropic організації лежать у таблиці `model_credential_accounts`, секрети в ній зашифровані.
- Є два види акаунтів:
  - **ключ API організації** додає адміністратор, і ним користуються всі прогони;
  - **підписку** (`claude setup-token`) кожен додає сам, і вона працює лише на прогони свого власника.
- Порядок вибору:
  1. акаунт, на якому сесія працювала минулого разу (так зберігається кеш промптів);
  2. власні підписки людини;
  3. ключі організації.

  Усередині кожної групи вирішує пріоритет, а за рівного пріоритету — вік акаунта.
- Коли акаунт уперся в ліміт, він відкладається до скидання. Якщо час скидання невідомий, то на 1 годину.
- Хід продовжується в тій самій сесії Claude з наступним акаунтом: `--resume` і промпт «продовжуй». За хід перемикань не більше 10.
- Якщо ключ відхилили, акаунт вимикається, доки його не виправлять.
- Якщо вичерпались усі акаунти, хід падає з помилкою `rate_limit` і часом найближчого скидання.
- Якщо акаунтів нема, працює старий єдиний ключ організації, а в локальній розробці — власний `claude` login.
- API:
  - `GET` і `POST /web/config/providers/anthropic/accounts`;
  - `PATCH` і `DELETE /web/config/providers/anthropic/accounts/:id`.

  Сторінка в налаштуваннях: «Моделі → Акаунти Claude Code».
- **Ще не зроблено:**
  - чекати скидання й автоматично повторювати хід, коли всі акаунти в ліміті;
  - пул для харнесу Mastra;
  - показувати перемикання акаунта в чаті.

**3. Підміна моделі (харнес Anthropic, модель DeepSeek)**

- Mastra: будь-яка модель нативно, тут проблем нема.
- Claude Code: технічно працює через `ANTHROPIC_BASE_URL`, бо DeepSeek має Anthropic-сумісний endpoint. Але промпти й інструменти Claude Code налаштовані під Claude, тож інші моделі можуть гірше викликати інструменти. Кожну таку пару треба перевіряти на реальних задачах.
- Правило для фабрики: харнес оголошує, яких провайдерів підтримує (Claude Code: Anthropic, Bedrock, Vertex, Anthropic-сумісні endpoint). UI показує тільки сумісні моделі. Модель міняється в межах харнесу, харнес — ні.

**4. Чи робити Claude Code-харнес?**

Так. Причина — підписка (див. «Навіщо»). Попередня пропозиція спершу провести експеримент «Mastra проти Claude Code на 5 картках» знята: вона виходила з хибного припущення, що підписка доступна і через Mastra. Порядок: контракт харнесу → Claude Code-харнес (етапи з таблиці «План»).

### Як це в Paperclip (`lab/ai/paperclip`)

- Запускає `claude` CLI підпроцесом (`--print - --output-format stream-json --resume`), не Agent SDK. Місця запуску: локально, SSH, пісочниці (E2B, Daytona, Modal, Kubernetes…).
- Спільний інтерфейс адаптера (`ServerAdapterModule`): `execute(ctx)` → результат з `sessionId`, `usage`, помилкою й часом повтору; плюс `sessionCodec`, список моделей, квоти. Адаптери є для Claude, Codex, Cursor, Gemini, OpenCode та інших.
- Одна сесія Claude на (компанія, агент, задача); `sessionId` у БД, транскрипт у JSONL Claude.
- UI: сирий stdout іде через WebSocket, парситься в браузері в спільний формат транскрипту.
- Знання: файли інструкцій агента, скіли (зокрема PARA-пам'ять у файлах), звітність через REST API курлом з короткоживучим JWT. MCP-сервер у них є, але до Claude не підключений.

### Що змінити в архітектурі фабрики

1. **Пам'ять і знання — сервіс фабрики, не частина агента.** Джерело — транскрипт у нашому сховищі та документи в репозиторії.
2. **Сервіси фабрики віддаються будь-якому харнесу через MCP** (інструменти фабрики — уже є; знання; затвердження) + контекст у промпт (скіли, спостереження).
3. **Людські ворота однакові для всіх харнесів:** «завершити хід і продовжити сесію».
4. **Контракт харнесу будується навколо ходу, а не навколо об'єкта сесії Mastra** (приблизно як адаптер Paperclip):
   - виконати хід (новий або продовження);
   - потік нормалізованих подій;
   - збереження параметрів сесії (codec);
   - список моделей;
   - класифікація помилок і лімітів;
   - методи людських воріт за змістом, а не за механізмом: `answerPlan({ approved, feedback })`, `answerQuestion(...)`. Mastra виконає їх як відновлення інструмента, Claude Code — як продовження сесії з повідомленням.

### План

| Етап | Що | Орієнтовно |
| --- | --- | --- |
| 1 | Контракт харнесу на основі ходу; `runtime` без Mastra; Mastra — перша реалізація; усі тести зелені | 1–2 тижні |
| 2 | `@factory/harness-claude-code`: один запуск на дошці Work, інструменти через `@factory/mcp`, запис у тред і події для UI | 2–3 тижні |
| 3 | Затвердження плану, `ask_user`, дозволи | ~1 тиждень |

## Система знань: дизайн

Обговорення 2026-10-27. Чернетка для доопрацювання, ще не реалізовано.

### Вимоги

Система знань — найважливіше в агенті; її треба правильно вести, підтримувати і лінкувати. Що в неї має входити:

- знання про код: швидко знаходити зв'язки;
- історія багів: що знайшли, як виправили;
- чому прийняті ті чи інші рішення (журнал рішень, «black box»);
- специфікація проєкту і задачі (список, бажано зі станом реалізації);
- листування з замовником;
- генерація специфікації з сирих матеріалів.

### Головний висновок

**Знання і пам'ять агента — різні речі.**

- **Observational memory** стискає контекст довгої сесії. Це кухня харнесу, а не система знань.
- **Subconscious у Mastra** автоматично витягає факти з розмов у БД. Їх ніхто не перевіряє, їх не видно в PR, вони працюють лише з Mastra-харнесом. Канонічною системою знань це бути не може, максимум джерелом пропозицій.

Тому окрема інфраструктура з observational memory **для знань не потрібна**. OM лишається пам'яттю сесії в харнесі, знання живуть у репозиторії.

### Три шари

| Шар | Що | Де | Правило |
| --- | --- | --- | --- |
| 1. Канонічний | специфікація, рішення, баги, задачі, глосарій, сирі джерела від замовника | md у репозиторії | версіонується з кодом, змінюється через PR, читається будь-яким харнесом |
| 2. Похідний | граф зв'язків, карта коду, пошук (повнотекстовий, згодом векторний або Graphiti) | індекси фабрики | можна видалити й перебудувати з git; руками не редагується |
| 3. Сесійний | OM, auto memory Claude Code, handoff | харнес | тимчасовий; цінне переходить у шар 1 через пропозицію |

### Шар 1: що, де, хто пише

Формати — з PostAirborne (`PostAirborne/post-airborne/docs`), бо там вони пройшли реальний проєкт:

| Тип | Файли | Хто і коли пише |
| --- | --- | --- |
| Сирі джерела (листування, транскрипти, брифи) | `docs/raw/` (у PostAirborne `blackbox/sources/`), дослівно, append-only | імпорт з CRM, пошти, Fireflies |
| Журнал рішень | `decisions.md`: `DEC-nnn`, статус `live/superseded/reversed/disputed/open`, `Supersedes`, дослівна цитата, джерело з таймкодом; «chain index» по темах | агент витягує з джерел, людина затверджує |
| ADR (великі технічні рішення) | `docs/adr/NNNN-slug.md`; критерії mattpocock: важко скасувати, неочевидне без контексту, справжній компроміс | Планування; затверджує людина |
| Специфікація | `docs/spec/<feature>/{requirements,design,tasks}.md`, `AC-x.y`, `T-nn`; premortem з воротами | скіл spec із сирих джерел → людські ворота DoR |
| Задачі | `tasks.md` — джерело правди, картки фабрики — проєкція («Change the plan here first») | статус пише фабрика зі стану картки й комітів |
| Історія багів | `docs/bugs/<id>.md`: вердикт, fix SHA, симптом, причина, виправлення, «caused by», «перевірено поруч», червоний тест | Реалізація на картці-баг; Перевірка контролює |
| Інваріанти | `bugs/INVARIANTS.md`: що вирішили, чому, що зламається, якщо скасувати | з багів і рішень |
| Відхилення від дизайну | `implementation-notes.md`: «Deviations from design, and why» | кінець Реалізації — замикає петлю код → специфікація |
| Глосарій | `GLOSSARY.md` (mattpocock `domain-modeling`) | Розбір і Планування |

Уроки з багів, де можливо, стають правилами лінтера (у PostAirborne 11 правил у `pa_lints`), а не прозою.

### Лінкування

Цього бракує і в PostAirborne, і в `lab/Skils`:

- **Стабільні ID, які ніколи не перенумеровуються** (у PostAirborne `gen2.py` перенумеровує UC при кожному запуску).
- **Frontmatter у кожному артефакті:** `id, type, status, supersedes, relates: [...], touches: [paths], source`.
- **`touches:`** зв'язує знання з кодом: для будь-якого файлу видно, які баги, рішення й задачі його стосуються. Агент отримує це перед правкою (у PostAirborne це ручне правило «прочитай DECISIONS перед змінами» в `mobile/CLAUDE.md`).
- **Валідатор у CI:** мертві посилання, неіснуючі ID, шляхи в `touches:`, яких уже нема (у PostAirborne 18 задач посилаються на видалену теку `admin/`).
- **Статус виводиться, а не редагується руками** — з карток, комітів і тестів. Головна хвороба PostAirborne: 14 з 15 фіч досі «draft», хоча вже збудовані.

### Шар 2: знання про код і пошук

Тут інфраструктура потрібна, але похідна:

1. **Граф зв'язків** з ID і frontmatter — без LLM, дешево, детерміновано.
2. **Карта коду:** залежності й символи з AST, перебудова на кожен коміт (як repo map в Aider); плюс зв'язок «файл → баги, рішення, задачі» через `touches:`.
3. **Пошук:** спершу повнотекстовий; вектори або RAG — якщо не вистачатиме.
4. **Graphiti** (getzep) — пізніше і опційно, для питань на кшталт «що замовник казав про X і як це змінювалось»: часовий граф (епізоди, сутності, факти з `valid_at/invalid_at`, старі факти не видаляються, а закриваються). Мінуси: Neo4j або FalkorDB, кілька викликів LLM на кожен запис, екстракція не перевіряється в PR, MCP-сервер без авторизації. Тільки як похідний індекс, ніколи як джерело правди.

Віддається будь-якому харнесу через `@factory/mcp`: `knowledge.get(id)`, `knowledge.related(file|id)`, `knowledge.search(q)`. Сторінка «Знання» в UI показує цей граф, а не БД subconscious.

### Як фабрика веде знання по етапах

| Етап | Читає | Пише |
| --- | --- | --- |
| Розбір | глосарій, пов'язані баги й рішення | класифікацію, посилання на `AC`/`T` |
| Планування | специфікацію, ADR, інваріанти для `touches:` | план з розділом «Рішення»; ADR, якщо виконано критерії |
| Реалізація | план, інваріанти | код, `implementation-notes`, запис бага |
| Перевірка | усе вище | request changes, якщо документи не оновлено (правило вже є у Reviewer у `lab/Skils`) |
| Готово | — | фабрика оновлює статус у `tasks.md`; суть рішення — в журнал з посиланням (патерн wayfinder у mattpocock); індекси перебудовуються |

**Запис назад:** агенти не пишуть у знання напряму в main, лише через PR задачі. ADR і специфікації затверджує людина; статуси й записи багів мерджаться автоматично, якщо CI зелений. Текст, згенерований AI, позначається (як у mattpocock `triage`). Заміна ADR не редагує старий, а додає новий із `supersedes`.

### Що вже є і що прибрати (`lab/Skils`)

- **Є добре:** конвеєр специфікацій (`eclipt-ai/.../pipeline`, `spec`, `decomposition`, `bug-intake`; `eclipt-skills/product/spec-driven-planning`, `trace-requirements`, `plan-premortem`, `document-project`), mattpocock `domain-modeling` (ADR + глосарій), `wayfinder`, `to-spec`, `to-tickets`, `triage`.
- **Дублі:** 3 конвеєри специфікацій, 3 конвенції ADR, 4 формати багів, 2 системи документації коду.
- **Нема:** журналу рішень, історії багів у репозиторії, сховища листування (є окремий плагін `crm-memory`), індексу коду, єдиної схеми ID і frontmatter.
- **Рішення:** зібрати один набір «eclipt knowledge kit» з форматів вище і зробити його скілами фабрики.

### Порядок

1. **Конвенції:** структура `docs/`, ID, frontmatter, шаблони + CLI-валідатор. Без цього все інше дрейфуватиме.
2. **Скіли на кожен етап** — зібрати з `lab/Skils` і PostAirborne.
3. **Граф зв'язків, пошук і MCP-інструменти**; сторінка «Знання» на них.
4. **Двостороння проєкція задачі ↔ картки** зі статусом, який виводить фабрика.
5. **Карта коду**; потім, за потреби, вектори або Graphiti.

Це окремий напрям, паралельний харнесу: контракт харнесу від нього не залежить, бо знання приходять через MCP і промпт.

Порада: червоні й помаранчеві брати зараз, поки розрив малий (тиждень). Щотижня переглядати `git log 4c22623ea3..upstream/main -- mastracode/factory mastracode/factory-ui` і позначати в `MIGRATION.md`, до якого коміту upstream ми дійшли.

## Знання організації: вікі, правила, скіли, рішення

У нас є вікі як система пам'яті, і вона часто використовується (глобальна). Можливо, потрібна система пам'яті на рівні організації. Це правила чи скіли? Як це організувати? Там будуть рішення, які ми реалізували, бест-практики, можливо стандарти. Це можуть бути й скіли. Як це організовують інші?

### Відповідь

Це не одна річ, а **чотири види знань**. Їх по-різному підвантажують агенту, і тому їх варто тримати окремо:

| Вид | Що це | Коли агент його бачить | Формат | Хто пише |
| --- | --- | --- | --- | --- |
| **Правила** (rules) | короткі обов'язкові обмеження: «pnpm лише через corepack», «не пушити в main», мова коду, стиль комітів | **завжди**, в кожній сесії | `AGENTS.md` / `CLAUDE.md` — коротко, десятки рядків | люди, через PR |
| **Скіли** (skills) | процедури «як зробити X»: як писати специфікацію, як робити реліз, як налаштувати Firebase | **за потреби**: агент бачить назву й опис, повний текст читає, коли задача підходить | `skills/<name>/SKILL.md` + файли поруч | люди; агент пропонує через PR |
| **Стандарти й рішення** (ADR, бест-практики) | чому зроблено так: «обрали Firestore, бо…», «API версіонуємо так…» | **за пошуком**: коли агент натрапляє на тему | `docs/adr/NNNN-*.md`, сторінки вікі | люди й агент, через рев'ю |
| **Автоматична пам'ять** | факти, які агент сам помітив у роботі | підкладається сама (`<remembered>`), пошук `knowledge_*` | Mastra Knowledge (граф, на проєкт) | агент-куратор, без рев'ю |

Головне правило: **правила — коротко і завжди; усе довге — у скіли й документи, які читаються за потреби.** Якщо все запхати в `AGENTS.md`, контекст роздувається, і агент гірше виконує саме правила.

### Як це роблять інші

- **Claude Code:** ієрархія `CLAUDE.md` — enterprise (керована політика на всю організацію) → користувач → проєкт → тека. Плюс скіли (`.claude/skills`, плагіни з маркетплейсу організації). Скіли — саме формат «знання, що вантажиться за потреби».
- **AGENTS.md** — відкритий стандарт, який читають Codex, Cursor, Copilot, Mastra Code; один файл на репозиторій.
- **Cursor:** правила `.cursor/rules/*.mdc` з умовами (завжди / за glob файлів / на вибір агента) плюс Team Rules на всю команду.
- **GitHub Copilot:** інструкції на рівні організації в налаштуваннях org плюс `.github/copilot-instructions.md` у репозиторії.
- **Devin:** «Knowledge» на рівні організації — окремі записи з описом, коли їх застосовувати. Devin сам підтягує потрібні й пропонує нові після сесій; людина затверджує. По суті це скіли з рев'ю.
- **Вікі:** Notion, Confluence, Outline тощо підключають через MCP як пошук; агент читає, але правила туди не кладуть.

Спільне в усіх: **короткі правила завжди в контексті, решта за пошуком; нові знання від агента йдуть через рев'ю людини.**

### Як зробити у фабриці

**Варіант 1 — працює вже зараз, без коду (раджу почати з нього).** Окремий репозиторій організації, наприклад `eclipt/engineering`:

```
AGENTS.md                 правила для всіх проєктів (коротко)
skills/
  write-spec/SKILL.md     як писати специфікацію
  flutter-release/SKILL.md
  firebase-setup/SKILL.md
docs/
  adr/0001-firestore.md   рішення
  standards/api.md        стандарти
  practices/testing.md    бест-практики
```

Його додають у кожну фабрику як **репозиторій середовища** (`inEnvironment`). Він клонується поруч із кодом проєкту, а фабрика вже вміє підхоплювати `AGENTS.md`, `CLAUDE.md` і скіли з **кожного** репозиторію в середовищі (`harness-mastra/src/workspace.ts`). Агент бачить правила організації, скіли і може шукати по `docs/`.

- Плюси: версіонування в git, рев'ю через PR, той самий механізм, що й для коду.
- Мінус: його треба додати в кожну фабрику, плюс неглибокий клон на кожну сесію (секунди).
- Скіли йдуть **у репозиторій**, а не в `factory-skills` фабрики. `factory-skills` — це скіли самого конвеєра (тріаж, план, рев'ю), а не знання організації.

**Варіант 2 — рівень організації в самій фабриці (потрібен код).** Налаштування org «репозиторій знань» (або кілька), який фабрика автоматично додає в кожне середовище org. Плюс правила рівня org (як enterprise `CLAUDE.md`), що додаються до інструкцій кожної сесії. Невелика фіча поверх варіанту 1.

**Вікі.** Якщо вікі вже є і нею користуються люди, лишити її для людей і підключити агенту через MCP як пошук. Правила й скіли тримати в git-репозиторії: їм потрібні версія, рев'ю і точний текст, а вікі цього не дає. Як варіант, вікі може бути «джерелом», з якого затверджені речі переносяться в репозиторій.

**Як нові рішення потрапляють у базу.** Агент наприкінці роботи пропонує ADR або оновлення скіла **PR-ом у репозиторій знань**, людина затверджує. Mastra Knowledge лишається автоматичною пам'яттю проєкту без рев'ю, а не джерелом стандартів.

**Пропонований порядок:**

1. Створити `engineering`-репозиторій зі структурою вище, перенести туди правила з вікі (коротко) і перші 2–3 скіли (специфікація, Flutter-реліз).
2. Додати його в середовище фабрики як другий репозиторій, перевірити, що агент бачить правила й скіли.
3. Додати в скіли конвеєра крок «запропонуй ADR / оновлення скіла PR-ом», якщо в роботі ухвалено нове рішення.
4. За потреби — варіант 2 (автоматичне підключення на рівні org) і вікі через MCP.

### «LLM wiki»: що це і навіщо, якщо є правила й скіли

Під «LLM wiki» зазвичай мають на увазі одне з двох (за пам'яттю, деталі не перевіряв):

1. **LLM Wiki за Карпаті** (2026, «LLM knowledge bases»). Базу знань **веде сама модель**, а людина лише додає джерела і ставить питання. Три шари:
   - `raw/` — незмінні джерела (статті, нотатки, транскрипти, PR);
   - `wiki/` — markdown-сторінки, які LLM пише й оновлює: сутності, теми, зв'язки `[[...]]`, `index.md`, журнал змін;
   - схема (`AGENTS.md` / `CLAUDE.md`) — як вести вікі.
   
   Операції: **ingest** (нове джерело → оновити 10–15 сторінок), **query** (відповідь з вікі; корисну відповідь зберегти як нову сторінку), **lint** (знайти суперечності, сироти, застарілі твердження). Ідея: знання **накопичуються**, а не шукаються щоразу заново, як у RAG. Часто ведуть в Obsidian.
2. **DeepWiki** (Cognition) і open-source аналоги (deepwiki-open, OpenDeepWiki): **автоматична вікі по кодовій базі** — архітектура, модулі, діаграми, генеровані з репозиторію.

**Навіщо, якщо є правила й скіли.** Вони не замінюють одне одного, а закривають різні шари з таблиці вище:

| | Правила / скіли | LLM wiki |
| --- | --- | --- |
| Що | **як треба робити** (норма) | **що ми знаємо** (факти, рішення, історія, контекст) |
| Хто пише | людина, точний текст | модель, з джерел |
| Зміни | рідко, через рев'ю | постійно, після кожного джерела |
| Помилка коштує | дорого: агент буде робити неправильно | дешевше: це довідка, її перевіряє lint і людина |

Тобто LLM wiki — це **шар «рішення, практики, контекст»**: те, що я раніше пропонував як `docs/adr` і `docs/practices`, але яке веде модель, а не люди вручну. А правила й скіли лишаються короткими і перевіреними людьми. Затверджене з вікі може «підніматись» у скіл або правило.

**Порівняно з Mastra Knowledge** (наша автоматична пам'ять): обидва — пам'ять, яку веде модель. Але Mastra Knowledge — це граф у базі, на один проєкт, без рев'ю і майже невидимий людям. LLM wiki — markdown у git, читабельний, з історією й PR. Для знань організації LLM wiki краща.

**Як це лягає на фабрику:**

- Репозиторій знань організації (`engineering`) = LLM wiki: `raw/`, `wiki/`, `AGENTS.md` зі схемою, плюс `skills/` і короткі правила.
- Окрема дошка «Knowledge» у фабриці: картка = нове джерело (завершена картка, PR, нотатки зустрічі). Фаза **ingest** (скіл `wiki-ingest`) оновлює сторінки PR-ом; **lint** — за розкладом; людина мерджить.
- Агенти інших дошок бачать вікі як репозиторій середовища і шукають по ній. Це і є «пам'ять організації».
- Вікі для коду (DeepWiki-подібна) — окремо, на кожен репозиторій, за потреби.

## Автоматизації на проєкт: cron, вебхуки, моніторинг

Кейс: для конкретного проєкту налаштовуємо автоматизації, що спрацьовують за розкладом (cron), вебхуком або іншою подією. Приклади:

- читати логи бекенду, робити звіти, а якщо помітили помилки — повідомити;
- стежити за новими версіями бібліотек і вразливостями;
- стежити за провайдерами API: наприклад, Meta змінює ціни на продукт чи інші умови;
- ресерч і збір інформації: сформувати тікети чи щось, на що треба звернути увагу.

### Що вже є у фабриці

| Можливість | Стан |
| --- | --- |
| Розклад (cron) | **для intake нема.** Mastra Schedules використовується лише для збірки середовища (`harness-mastra/src/environment/build-schedule.ts`), але механізм cron на проєкт уже є |
| Вебхуки | лише GitHub і GitLab (issue, PR, push, коментарі) |
| Створити картку ззовні | є: `POST /web/factory/projects/:id/work-items`; зовнішній cron (GitHub Actions schedule, systemd timer) може створювати картки вже зараз |
| Агент створює картки й issue | є: `factory_create_work_item`, інструменти GitHub/GitLab |
| Сповіщення | є, всередині фабрики (attention, notifications); назовні — лише через коментарі в issue/PR (Slack прибрано) |
| Браузер для ресерчу | є після перенесення #28057 (`FACTORY_BROWSER=agent-browser`) |

### Як це має виглядати

**Автоматизація = тригер + дошка + скіл + куди звітувати.**

1. **Тригер:**
   - розклад на проєкт (cron), наприклад «щодня о 9:00», «щопонеділка»;
   - загальний вхідний вебхук на проєкт (`/web/factory/projects/:id/hooks/<name>`, з підписом): Sentry, Grafana/Alertmanager, Datadog, Stripe, uptime-монітор, будь-що з HTTP;
   - подія репозиторію (push, реліз, тег), яка вже є через GitHub/GitLab.
2. **Дошка «Monitor»** (або «Routine»): Intake → Run (агент зі скілом) → Report → Done.
   - **Кожен запуск — картка.** Так є історія, аудит, токени, і видно, що знайдено.
   - Якщо нічого не знайдено, картка закривається сама; якщо знайдено — йде людині або створює дочірні картки на Work.
3. **Скіл на кожен тип автоматизації:** `logs-review`, `deps-audit`, `vendor-watch`, `research-digest`. Він каже, що перевірити, як оцінити серйозність і в якому форматі звітувати.
4. **Куди звітувати:** коментар або нова картка на дошці Work (баг, оновлення залежності), issue в GitHub/GitLab, сторінка в LLM wiki (`raw/` → ingest), лист чи месенджер (окрема інтеграція, зараз нема).
5. **Пам'ять між запусками:** що вже бачили, щоб не дублювати тікети. Ключ ідемпотентності на знахідку (наприклад, хеш помилки чи CVE-id) і файл стану в репозиторії знань або в метаданих картки.

**Чого бракує в коді:**

- cron-тригер, що створює картку на дошці за розкладом (поверх наявних Mastra Schedules);
- загальний вебхук-intake з підписом і мапою «подія → дошка/скіл»;
- секрети на проєкт (ключі до логів, Sentry, API провайдерів) — див. «Секрети в пісочниці»;
- канал сповіщень назовні (email, Telegram, Discord чи інше).

### Варіанти, які варто додати до списку

**Експлуатація:**

- **Розбір алертів:** Sentry чи Grafana шле вебхук → агент групує, шукає причину в коді й логах, створює картку-баг з відтворенням.
- **Ранкова зведена довідка:** помилки за добу, повільні запити, падіння конверсії, нові скарги.
- **Перевірка після деплою:** smoke-тести, порівняння метрик до і після, автоматичний відкат-пропозиція.
- **Витрати хмари й LLM:** тижневий звіт, аномалії, прогноз.
- **Термін дії** сертифікатів, доменів, токенів, ключів API, підписок Apple/Google.

**Код і залежності:**

- **Оновлення залежностей** з PR і прогоном тестів (як Renovate/Dependabot, але агент читає changelog і виправляє breaking changes).
- **CVE і ліцензії** залежностей.
- **Нестабільні тести:** знайти flaky-тести з історії CI, створити картки.
- **Технічний борг:** TODO, мертвий код, дублікати, зростання розміру бандла.
- **Документація проти коду:** README, API-доки, `AGENTS.md` розійшлися з кодом → PR.

**Мобільна специфіка:**

- **Рев'ю й відгуки в App Store / Google Play:** категоризувати, знайти баги, відповіді-чернетки.
- **Краші** (Firebase Crashlytics): групувати, шукати причину, картки.
- **Політики сторів:** зміни правил Apple/Google, нові вимоги до SDK, target API level, privacy manifests.
- **Нові версії** Xcode, Flutter, Android SDK: перевірка збірки на новій версії.

**Зовнішній світ:**

- **Провайдери API:** зміни цін, лімітів, deprecations, нові версії API (Meta, Stripe, OpenAI, Firebase).
- **Конкуренти:** нові фічі, ціни, релізи.
- **Ресерч-дайджест** за темою: статті, репозиторії, обговорення → сторінки в LLM wiki.
- **Юридичне й compliance:** GDPR, умови використання сервісів, які ми використовуємо.

**Процес і команда:**

- **Застарілі картки й PR:** нагадати, закрити, перепризначити.
- **Підсумок спринту чи тижня:** що зроблено, що застрягло, що далі; реліз-ноути з комітів.
- **Наповнення LLM wiki:** завершені картки й PR → `raw/` → ingest.
- **Знання з розмов:** нотатки зустрічей → рішення → ADR чи картки.
- **Supervisor уже робить частину цього** для самої фабрики (застряглі рішення, дрейф міток) кожні 5 хв.

### Порядок впровадження

1. Без коду: зовнішній cron (GitHub Actions `schedule`) викликає `POST /work-items`, створюючи картку на Work з промптом. Перевірити цінність на 1–2 кейсах (логи, залежності).
2. Дошка «Monitor» + 2–3 скіли в репозиторії знань.
3. Cron-тригер і загальний вебхук у фабриці, секрети на проєкт.
4. Канал сповіщень назовні.

## Для чого дошка Work і скільки пайплайнів потрібно

### Work — це загальний конвеєр «задача → зміна коду → PR»

Work не про один тип задач. Він веде **будь-яку задачу, результат якої — зміна коду в репозиторії**: фіча, баг, документація в репозиторії, рефакторинг, оновлення залежностей.

Тип задачі визначає **тріаж**: `triageType` = bug, feature request, docs, maintenance, question/support, duplicate тощо. Далі шлях залежить від типу:

| Тип після тріажу | Що далі |
| --- | --- |
| bug | сам іде в Planning, план затверджується, Execute «знайди причину і виправ з тестами» |
| feature request, docs, maintenance | чекає людину: вона вирішує, чи брати, і переносить у Planning |
| question/support | агент відповідає в issue, коду нема |
| duplicate, invalid, spam, out-of-scope, resolved | закривається з поясненням |

Тобто **Work = фіча, баг, документація в коді — один конвеєр**, а різниця між ними — у тріажі й промптах фаз, а не в окремих дошках.

Review — окремий конвеєр для **рев'ю PR**: і тих, що відкрив агент, і тих, що відкрили люди. Acceptance — перевірка критеріїв прийняття людиною.

### Скільки пайплайнів будувати

**Не купу.** Новий пайплайн потрібен лише тоді, коли **процес принципово інший**: інший результат (не PR), інший тригер (розклад), інші ворота. Усе, що закінчується PR, — це Work, можливо з додатковою фазою.

| Пайплайн | Результат | Тригер | Чому окремо, а не Work |
| --- | --- | --- | --- |
| **Work** (є) | PR зі зміною коду | issue, ручна картка | — |
| **Review** (є) | вердикт і коментарі до PR | відкритий PR | — |
| **Acceptance** (є, наш) | прийнято / не прийнято | ручна картка | — |
| **Spec** (новий) | документ специфікації і дочірні картки на Work | ручна картка | результат — документ і план робіт, а не код; людські ворота на кожному кроці |
| **Monitor** (новий) | звіт, нові картки чи issue | cron, вебхук | запускається за розкладом, найчастіше нічого не змінює |
| **Knowledge** (новий, за потреби) | PR у репозиторій знань (LLM wiki) | завершена картка, нове джерело | інший репозиторій і інший формат |
| **Ops / налаштування сервісів** (за потреби) | налаштований сервіс (Firebase, App Store, Google Play) | ручна картка | браузер, секрети, людина підтверджує кожну дію в чужій консолі |

**Баг-конвеєр, який ти описував** (прочитати логи → відтворити без коду → тест, що падає → виправлення → PR → рев'ю), — це **не окрема дошка, а Work з додатковою фазою** для багів: `triage → reproduce (тест, що падає) → planning → execute → review`. Policy: не пускати в Execute без тесту, що падає. Новий скіл — `bug-reproduce`.

### Що робити зі скілами

На кожну робочу фазу — один скіл. Для Work це означає:

- переписати під наші проєкти **наявні**: `factory-triage`, `factory-plan`, `factory-self-review` (зараз вони під репозиторій Mastra);
- **додати** `factory-build` для Execute (зараз там лише промпт) і `bug-reproduce`;
- скіли знань проєкту (як у нас робиться реліз, міграції, стиль) — у репозиторії проєкту чи організації, а не в пайплайні.

**Разом:** 3 наявні дошки + 2 нові (Spec, Monitor) + 1–2 за потреби, і приблизно 10–15 скілів фаз. Решта знань — скіли в репозиторіях.

## Різні технології (Flutter, Node) і звідки беруться скіли

**Рішення 2026-10-27:** Monitor і Knowledge відкладено. Зараз робимо Spec і доробляємо Work (баги).

### Як фабрика зараз шукає скіли (перевірено в коді)

| Звідки | Що там | Хто може змінити |
| --- | --- | --- |
| `harness-mastra/factory-skills/` (бандл фабрики) | скіли фаз: `factory-plan`, `factory-triage`, `factory-review`… | лише код фабрики |
| `apps/server/src/mastra/public/factory-skills/` (сервер) | **перекриває** бандл за назвою; можна додати свої | той, хто деплоїть сервер; **одне на весь сервер** |
| репозиторії середовища: `.agents/skills/`, `.claude/skills/`, плюс `AGENTS.md` / `CLAUDE.md` | скіли знань проєкту | команда проєкту, через PR |

**Важливо:** скіл у репозиторії з назвою скіла фази (наприклад `factory-plan`) **ховається**: репозиторій не може підмінити скіл фази (`#reservedNames`, `workspace.ts:239-254`). Це зроблено навмисно, заради безпеки: чужий PR не повинен переписувати поведінку конвеєра.

Тобто зараз скіли фаз **одні на весь сервер**, для всіх фабрик і всіх технологій. Upstream це не «вирішував» як налаштування на фабрику: у них скіли фаз — частина продукту, а знання проєкту — у репозиторії.

### Що пропоную: три шари

1. **Скіли фаз — загальні, без технології.** Вони описують *процес* (як тріажити, як планувати, як рев'ювити) і **делегують технологію репозиторію**: «прочитай `AGENTS.md`; знайди скіли проєкту; запусти команди перевірки з `AGENTS.md`». Це один набір на весь сервер, і це нормально: процес у нас однаковий, різна лише технологія.
2. **Технологія — у репозиторії проєкту.** Flutter-репозиторій має свій `AGENTS.md` (команди: `flutter analyze`, `flutter test`, як запускати збірку) і скіли (`flutter-testing`, `flutter-release`). Node-репозиторій — свої (`pnpm test`, міграції, стиль). Агент бере їх сам, бо працює в цьому репозиторії.
3. **Спільне для технології між проєктами — у репозиторії організації** (`engineering/skills/flutter/*`, `engineering/skills/node/*`), підключеному в середовище кожної фабрики. Тоді Flutter-стандарти пишуться один раз.

**Як дати проєкту доповнити скіл фази без ризику** (без коду, лише текстом скілів): домовленість «розширення фази». Скіл фази наприкінці каже: «якщо в репозиторії є скіл `project-<фаза>` (наприклад `project-plan`, `project-build`, `project-review`) — виконай і його». Проєкт додає свої вимоги до плану чи рев'ю, а основний процес лишається нашим. Для PR від чужих це безпечно: інструкції в такій сесії беруться лише з базової гілки.

**Налаштування на фабрику в UI** (вибір скілів фаз, редагування з інтерфейсу) потребує коду: зберігати скіли в базі чи в репозиторії знань, показувати їх у налаштуваннях. Поки це не потрібно. Шари 1–3 і `project-<фаза>` закривають різні технології без цього. Повернемось, якщо з'явиться потреба в різних процесах для різних фабрик.

### Spec: як реалізувати

Нова дошка `spec` у `packages/pipelines/src/spec/` (за зразком `acceptance/`), ролі — наявні, без нових:

| Фаза | Вид | Що відбувається | Скіл |
| --- | --- | --- | --- |
| Intake | resting | картка: ідея чи запит («потрібна оплата підпискою») | — |
| Research | working, роль `plan` | вивчити код, наявні рішення, обмеження; зібрати відкриті питання | `factory-spec-research` |
| Questions | resting | людина відповідає на питання в картці | — |
| Draft | working, роль `plan` | написати специфікацію за шаблоном: мета, користувачі, сценарії, нефункціональні вимоги, критерії прийняття, поза межами, ризики | `factory-spec` |
| Review | resting | людина рев'ює PR зі специфікацією | — |
| Breakdown | working, роль `plan` | розбити на задачі: створити дочірні картки на Work з критеріями прийняття і залежностями | `factory-spec-breakdown` |
| Done / Canceled | terminal | — | — |

- **Де лежить специфікація:** PR у репозиторій проєкту, `docs/specs/<id>-<slug>.md`. Так вона версіонується, рев'юється і доступна агентам Work як контекст. Посилання — в метаданих картки.
- **Policy:** у Draft не можна без відповідей на питання; у Breakdown — лише після злиття PR зі специфікацією; Done — коли створено дочірні картки.
- **Дочірні картки** йдуть у Work з `parent_work_item_id` (поле вже є), щоб бачити, з якої специфікації вони.
- **Що треба в коді:** сама дошка (3 файли), 3 скіли, підключення в `apps/server/src/mastra/index.ts`. Перевірити, чи `plan`-роль може робити PR (зараз PR відкриває роль `work`); якщо ні — Draft із роллю `work`.

### Решта

- **Баг:** фаза `reproduce` у Work для `triageType = bug` + скіл `bug-reproduce` + policy «без тесту, що падає, у Execute не можна».
- **Execute:** скіл `factory-build` замість промпту (TDD, коміти по фазах плану, команди перевірки з `AGENTS.md`).
- **Переписати під нас** `factory-triage`, `factory-plan`, `factory-self-review`: прибрати специфіку репозиторію Mastra, додати делегування в `AGENTS.md` і `project-<фаза>`.
- **Ops (Firebase, стори)** — потім, коли буде секрети на проєкт.

## QA: якісне тестування

Як якісно протестувати (QA)? Це окремий пайплайн чи періодична задача? Як це має працювати: задача на вечір, після рев'ю, рефакторинг (пошук багів)? Чи може картка переходити з одного пайплайна в інший?

### Review і QA — різні речі

| | Review (є зараз) | QA (нове) |
| --- | --- | --- |
| Що перевіряє | **код** у PR: дизайн, правильність, ризики, чи є тести, чи проходять тести й лінт | **поведінку** запущеного застосунку: зібрати, запустити, пройти сценарії як користувач |
| Як | читає diff, ганяє тести, публікує commit check «Factory test report», ставить вердикт approve / request changes | браузер (адмінка), симулятор чи емулятор (мобілка), запити й логи (сервер) |
| Результат | вердикт і коментарі в PR | звіт «пройшло / не пройшло» + нові картки-баги |
| Хто мерджить | **ніхто з агентів**: агент не може перенести картку Review у Done; PR мерджить людина в GitHub чи GitLab, і подія merge переносить картки в Done | — |

Тобто Review відповідає на питання «чи добре написано», QA — «чи працює як треба».

### QA — окремий пайплайн з кількома тригерами

Дошка QA: **Intake → Prepare** (зібрати збірку, підняти середовище) **→ Test** (агент тестує) **→ Report → Done**. Скіли: `qa-prepare`, `qa-test`, `qa-report`. Як тестувати кожну платформу — у скілах платформ у репозиторії (браузер для адмінки вже є після #28057).

| Тригер | Що тестує | Як з'являється картка |
| --- | --- | --- |
| Після рев'ю PR (перед merge) | конкретну зміну на preview-збірці | правило на Review: вердикт approve → картка на QA |
| Після merge | регресію на main / staging | правило на Work і Bug: PR змерджено → картка на QA |
| Щовечора (cron) | повний регрес, e2e, дослідницьке тестування | cron створює картку (cron-тригера ще нема, див. «Автоматизації на проєкт») |
| Вручну | вказаний модуль: «пошукай баги в оплаті», аудит після рефакторингу | людина створює картку на QA |

### Перехід між пайплайнами

Сама картка на іншу дошку **не переходить** (обмеження Mastra: «Existing cards cannot be reassigned to another board»). Натомість правило створює **пов'язану картку** на іншій дошці (`upsertLinkedWorkItem`, `parent_work_item_id`):

```
Work/Bug картка ──(PR approved / merged)──► QA картка ──(знайдено баг)──► Bug картка
       └ батьківська                          └ дочірня                     └ дочірня від QA
```

Кожна картка живе на своїй дошці, ланцюжок видно через батьківські зв'язки. Знайдені QA баги автоматично стають картками на Bug.

### Відкрите рішення

- **QA перед merge (ворота):** PR не мерджиться без зеленого QA. Якість вища, але повільніше; потрібна preview-збірка на кожен PR.
- **QA після merge (перевірка):** швидше, але баги вже в main, і QA лише знаходить їх для Bug.
- Можна обидва: перед merge — коротка перевірка зміни, щовечора — повний регрес.

### Що потрібно зробити

1. Дошка QA і три скіли.
2. Правила «approved / merged → картка QA» на Review, Work і Bug.
3. Скіли платформ у репозиторії: як тестувати адмінку, мобілку, сервер.
4. Cron-тригер для вечірнього регресу.

### QA як фаза пайплайна: без QA задача не «Done»

Якщо фіча чи баг не вважаються готовими без QA, то QA — **фаза всередині Work і Bug**, а не лише окрема дошка:

```
… → Review → PR змерджено → QA → Done
                              └ не пройшло → назад в Execute (або нова картка на Bug)
```

- подія merge переносить картку в **QA**, а не одразу в Done (зараз — одразу в Done);
- фаза QA: роль `validator`, скіл `qa-test` — зібрати, запустити, пройти сценарії з критеріїв задачі;
- policy: у Done — лише після зеленого QA;
- варіант «QA до merge»: фаза між Review і merge, потрібна preview-збірка на кожен PR.

Окрема дошка QA лишається для вечірнього регресу (cron) і ручних аудитів.

### 1. Проблема: код більше не вузьке місце

- [00:40] Пост @v0xium у X (20.09.2026, мільйони переглядів): у великій компанії спеки, код, тести, PRD, тікети, звіти пише Claude Code; люди по 12–13 годин «просто тиснуть Enter», ніхто нічого не читає. Керівництво: «пушити код — не вузьке місце, чому ми повільні?» Відповідь Маска: «Yikes».
- [00:56] **Meat proxy** («шкіряний проксі») — людина, яка пересилає роботу одного агента іншому і лише тисне Enter. Схема на слайді: агент → `code` → людина → `spec.md` → агент → звіт.
- [00:08] Автори BMAD самі визнали (docs.bmad-method.org/existing-codebases/set-and-maintain-project-context): `bmad-document-project` генерував документацію по репозиторію, «а так робити не треба» — вона застаріває одразу і робить агентів гіршими.
- [01:36] Згенеровано 1 000 000 рядків — «✓ готово», а релізи швидше не виходять, якість скоріше навпаки.
- [05:52] CMU + Stanford, «AI Writes Faster Than Humans Can Review: A Longitudinal Study of an Enterprise 2x Mandate», arXiv 2607.01904 (02.07.2026): **802 розробники, 196 212 PR**. PR на інженера — удвічі більше; читати швидше не стали. [07:04] Частка PR, які бачив живий рев'юер: **89% → 68%**; автоматичне AI-рев'ю: **~19% → ~84%**.
- [06:08] SmartBear × Cisco, 2006 (вендор інструменту рев'ю): хто читає **повільніше 400 рядків/год** — знаходить дефекти краще середнього; **швидше 450** — у 87% випадків гірше. [06:24] Один PR на **5000 рядків = 20 годин** чистого читання.
- [06:48] Агент ще й додає функціональність, якої не просили → прочитав → виправ → знову (по колу).
- Висновок: вузьке місце — **увага людини**, яка підтверджує, що код правильний, і налаштовує процес.

### 2. Навіщо фази: між фазами передається артефакт, а не сесія

- Схема RPI (research → plan → implement), може розширюватись (design тощо). SDD, BMAD — те саме.
- **Кожна фаза — окреме контекстне вікно.** Причини:
  - context rot: що більше в контексті, то гірше модель працює; майже повний контекст — критична деградація;
  - траєкторія: контекст про одну задачу дає кращий результат, ніж усе підряд в одному вікні.
- **Фаза породжує артефакт** (md-файл, шматок коду, PR) — і в наступну фазу передається **лише артефакт**, не історія сесії. Наступна фаза стартує з чистого контексту + свій системний промпт + артефакт.
- У кожної фази — свій ключовий промпт, своя траєкторія, свій артефакт.
- [03:20] Слайд: `SYSTEM PROMPT · research` → `research.md` → `SYSTEM PROMPT · plan` → … → `SYSTEM PROMPT · implement` → `code.diff`.
- Помилка в ранньому артефакті каскадом множиться в наступних фазах — тому початок (research, design) важливіший за кінець. [04:24] Цитата HumanLayer, ACE-FCA 2025 (github.com/humanlayer/advanced-context-engineering-for-coding-agents): «погана строка коду — це погана строка коду; погана строка плану — сотні поганих строк коду; погана строка research — тисячі».
- [04:56] Проблема: план розрісся довше за код — слайд: план 720 → 2946 → **3800 рядків** проти коду **1200**. Рев'ю плану стало дорожчим за рев'ю коду. Тому план має бути **розбиттям на фази**, а не готовою реалізацією в md. [05:20] Питання: що рев'юїти — план, код чи дизайн? Куди йде «сеньйорська увага».

### 3. Перевірка між фазами (quality gate)

Перехід у наступну фазу — лише після перевірки артефакту. Не пройшло — назад агенту, у циклі. Три варіанти:

1. **Людина.** Дорого: агенти пишуть багато й гарно, читати втомлює. Не кожен gate потребує людини.
2. **Детермінована перевірка кодом — на кожному переході, без токенів.** Формат артефакту, обов'язкові розділи й посилання; для design — є діаграми; для code — є PR, є diff, лінтери запускались, усі тести зелені. [09:52] Слайд: `PR ✓ diff ✓ lint ✓ tests ✗` → gate червоний → «↺ доробка» назад у фазу.
   - [10:16] Приклад: агент запустив 3/24 тести — «вроде работает, всё, готово», «это же не продакшн, можно не всё». Gate запускає `./gate.sh --all-tests --lint` → 8/24, частина червоні → агент доробляє → 24/24 зелені.
   - [21:20] Gate для design: `DESIGN.md` → ✓ діаграма C4, ✓ sequence, ✓ усі потрібні розділи, ✓ правильний формат — «кодом, а не токенами на суддів».
3. **Агент-суддя** — де помилка ймовірна і дорога. Краще **інший клас моделі**, ніж той, що писав. Може перевіряти артефакт або траєкторію, один суддя або кілька.

Промптам агента-виконавця довіряти не можна: [12:32] слайд «вимоги з промпту агента» — ✓ запустити всі тести, ✓ прогнати лінтери, ✗ усі вимоги задачі (закреслено), ☐ правила з memory.

[08:32] Кількість фаз неважлива (2 чи 22) — gate стоїть на кожному переході. [08:56] Якщо всі gate — людина, читати 12, потім 42 md-файли.

[12:08] Контекст: автор спалює ~**50 млрд токенів на місяць** (Claude Code `/stats`: 21,3 тис. сесій, 30/30 активних днів) — тому важливо, щоб токени не горіли на дефектних артефактах.

### 4. Його процес фічі — фази по черзі (приклад, не рецепт)

Вхід: задача вже є (можливо, з PRD і тікетом). Схема:

```
Task → Enrich → Research → Design → QA plan → Plan → Code → QA check → Deploy → QA
```

**Enrich — наповнити контекст знаннями інженера (людина в циклі).**
- Навіщо: інженер, отримавши задачу, одразу знає, як влаштована система, як би він це зробив, де підводні камені. Агент цього не знає (навіть з доступом до вікі).
- Як: замість одразу research — розмова агента з інженером. Скіл **`grill-me`** («підсмаж мене»): агент ставить питання по задачі, інженер відповідає і докидає: як би він зробив, на що звернути увагу, відомі проблеми системи. Скіл краще адаптувати під себе.
- [14:24] Приклад діалогу зі слайда:
  - агент: «Які підводні камені в цієї задачі?»
  - інженер: «Кеш інвалідується у двох місцях — врахуй обидва»
  - агент: «Як би ти це зробив? На що дивитись?»
  - інженер: + контекст з голови
- [13:28] Що в голові інженера (слайд): як влаштована система, як виконати, легасі, кеш, API, що буде добре/погано, підводні камені, обриси архітектури — «✗ агент цього не знає».
- Чому важливо: стара проблема SDLC — у продакшн їде не те, що хотів клієнт, а те, як розробник зрозумів. [14:40] Цитата Alberto Brandolini (автор EventStorming): «It's developer's (mis)understanding, not expert knowledge that gets released into production». Тут інженер доносить своє бачення агенту **до** будь-якої роботи.
- Результат: задача + знання з голови інженера в контексті/артефакті.

**Research — звузити контекст.**
- Навіщо: кодова база і база знань більші за контекстне вікно; навіть якщо влізуть — займуть місце і коштують грошей/лімітів.
- Як: агент вибирає з бази знань і з коду лише ті місця, що відповідають задачі **і результату Enrich**.
- Результат: короткий артефакт з потрібними фрагментами знань і коду.

**Design — як фіча вбудовується в систему (людина/команда рев'ює завжди).**
- Як: архітектурні документи, знайомі команді — у нього C4, sequence-діаграми, data flow-діаграми.
- Вимога: високорівнево; з одного погляду зрозуміло, як фіча встроюється, ще до коду.
- Чому важливо: «втрата відчуття коду» з агентами найчастіше через пропущений design і design-review. Обговорити з командою — знання розходиться по головах.
- Gate: детерміновано перевірити, що всі потрібні діаграми є; потім людина.

**QA plan — план тестування до плану реалізації.**
- Як: на основі design — які інтеграційні тести додати/змінити, як перевірити фічу як чорну скриньку. Прописати контракти і всі інтеграційні тести, які проженуться в кінці.
- Чому до плану: без інтеграційних тестів важко довіряти коду агента; тести з design, а не з коду.

**Plan — розбиття на фази, не готова реалізація.**
- Мета: поділити design на завершені частини, які легко перевірити. Наприклад, за clean architecture: домен → use cases → interface adapters…
- Частина фаз паралельно, частина послідовно (залежні). Кожну рухати і рев'ювати окремо.
- Не робити: гігантський документ з усім кодом і місцями вставки (так агенти пишуть плани самі — там уже майже вся реалізація).
- Маленька фіча (10 рядків, одне вікно) — весь цикл не потрібен.

**Code — реалізація за фазами плану.** Gate: CI з усіма перевірками (розділ 5) + агент рев'ю архітектури.

**QA check — звірити план тестів з реальним кодом.**
- Навіщо: під час реалізації могли змінитися контракти, додатися/зникнути функціональність.
- Як: привести план тестування у відповідність до написаного коду; можливо повернутись у Code і щось виправити.

**Deploy — розгорнути.** Локальне середовище, кластер, dev, feature-branch environment — що є у вашому SDLC. Одразу видно, чи запускається.

**QA — прогнати тести за планом.** Перевірити, що зроблене відповідає плану тестування, складеному з design.

[20:24] Для багфіксу в нього інший, коротший процес (на слайді ~4 фази проти 10 у фічі), фронт/бек — ~5 (кількість зі слайда приблизна). Набір фаз — не срібна куля, підганяти під SDLC команди. Фази ділити як домени в DDD: мінімальний coupling, максимальний cohesion — тоді артефакти легко перевіряти.

### 5. Якість коду до PR — без токенів

- Unit-тести від агента часто погані: підганяє код під тести або видаляє кейси.
- **Mutation testing**: змінюємо код (`>` на `<` тощо), тести мають впасти. Не впали — тест нічого не ловить. Обов'язково в CI.
- [25:28] Приклад зі слайда: `if (total > limit) { return discount; }`, тести 12/12 зелені → міняємо на `if (total < limit)` → тести знову 12/12 → «мутант вижив». Тисячі мутантів; вижилі = непокритий код.
- [26:40] **CRAP** (change risk anti-patterns): `CRAP = comp² × (1 − cov)³ + comp`, де `comp` — цикломатична складність функції, `cov` — покриття тестами. Високий — знижувати складність або підвищувати покриття.
- [27:12] «Жорсткий CI до PR»: цикломатична, когнітивна складність, CRAP, мутаційне тестування, покриття, лінтери, SAST, DAST — «токенів: 0, працює у фоні».
- Cognitive / cyclomatic complexity, maintainability index, лінтери, SAST, DAST.
- [28:08] Окремий **агент-суддя архітектури**: метрики в нормі — а архітектура? Промпт «перевір архітектуру» не працює (✗) — модель пише і перевіряє «як навчена». Потрібна **база знань: наші принципи**, яку описувати, оновлювати, покращувати. Лише після судді — PR → прод.
- [29:52] **Нюанс**: пайплайн `RES → DESIGN → PLAN → CODE → JUDGE`. Суддя червоний, помилка десь раніше. Варіанти: назад агенту в CODE або назад до DESIGN. **Вирішує інженер, а не модель**: ✗ агент сам міняє дизайн; ⏸ стоп → human in the loop → кнопки [↻ реворк пайплайна] / [✎ правка коду].

### 6. Де людина

- Human **in** the loop: Enrich і Design.
- Решта — human **on** the loop: спостерігає, може зупинити; основна перевірка — детермінована + судді.
- [31:04] Слайд «де людина»: 👤 над ENRICH, 👥 над DESIGN (дизайн — кілька документів, сам або з командою; «тепер усі — сеньйори»), 👁 над RES, PLAN, CODE, REVIEW. Між усіма шістьма фазами (ENRICH, RES, DESIGN, PLAN, CODE, REVIEW) на слайді стоять іконки агентів-суддів, тобто gate на кожному переході; + агенти-судді на ризикованих переходах; інакше гірший код і спалені токени/ліміти.
- [33:36] Правило для PR за DDD-типом:
  - **CORE** — глибина рев'ю 100%, 1+ інженер, досконально;
  - **SUPPORTING** — ~50%, може сам автор, без запуску у себе;
  - **GENERIC** — ~15%, пролистати очима (бо дизайн перевірено + тести).
- [34:32] CMU, «3100 Opinions on Code Review in an AI World», arXiv 2607.07908 (08.07.2026): знак ефекту задає не AI, а команда — експертиза людей і устрій рев'ю.
- [34:56] Послаблення рев'ю — лише якщо метрики продакшну в порядку: **CFR** (частка релізів з аварією), **MTTR** (час на полагодження), **MTTF** (час між збоями). Просіли — посилювати спершу CI, потім рев'ю.
- [36:08] Антипатерн «гей, усі пишемо з агентами»: беріть спеки (SDD), качайте скільки завгодно скілів, мільйон фіч у прод → здоров'я кодової бази 82% → 40% → 10%: важче підтримувати (і агенту теж), палить ліміти, більше дефектів, користувачі йдуть.
- [37:12] Підсумок: ~~код — вузьке місце~~ → вузьке місце — **людина**. Задача — знати, де дивитись самим, де керувати процесом, де довіряти, де посилити чи послабити.

### Що з цього для нас

- **Артефакт, а не сесія.** У нас runtime може перевикористати одну сесію агента для різних ролей (tester бачить контекст Execute). Відео — аргумент за зміну: кожна фаза — нова сесія, вхід — лише артефакти (план, тест, PR). Відкрите питання вище.
- Перевірки між фазами: є `rules/reproduction-test.ts` у Bug (детермінована) і approval плану (людина). Можна узагальнити: на кожному переході — перевірка артефакту фази кодом.
- Суддя на іншій моделі — через маршрутизацію моделей по ролях.
- План тестів до плану реалізації — лягає в дизайн Implement.
- Mutation testing, CRAP — у CI репозиторіїв проєктів, не у фабриці.

## Нотатка по відео 2: як тестувати AI-агента, щоб йому можна було довіряти

Джерело: Д. Березницький, «Как тестировать AI-агента, чтобы ему можно было доверять», 37 хв, 2026-10-09 — https://www.youtube.com/watch?v=bFHCK6PB0hA. Нотатка за субтитрами, текстом слайдів і списком джерел з опису відео. Позначка `[мм:сс]` — час у відео. Слайди тут майже без тексту: дошка з маркером (Harness / Model / Memory / Tools, сітка прогонів, pass@k / pass^k) і скриншоти статей, тому цифри — зі слів автора, статті я не читав.

Продовження першої нотатки («фази, артефакти, перевірки між фазами»): там — як організувати фази і gate, тут — як перевірити, що сам агент (і reviewer-агент) працює правильно.

### 0. З чого почалось

- [00:00] Він зібрав систему, де роботу агента на кожній фазі (research, design, код, тести, деплой) перевіряє **інший агент на іншій моделі**; reviewer повертає звіт або автоматично повертає фазу в цикл.
- Під час тестування reviewer на кожній фазі казав «все чудово, йдемо далі», хоча автор точно знав, що це не так. Причина: reviewer отримував **не повний diff і не артефакти, а короткий переказ фази** — за переказом усе виглядало добре.
- Це урок і для нашого Review/суддів: **суддя має бачити сирі артефакти (diff, файли, логи), а не розповідь агента про них.**
- Загальна теза: «треба більше тестів» нічого не каже, поки не відповіли, **що саме тестуємо**.

### 1. Агент — це чотири об'єкти тестування

[02:08] Дошка: `Agent = Harness + Model + Memory + Tools`. Кожен має свої методи, метрики і пастки. Приклад у відео — агент підтримки, що оформляє повернення товару: шукає замовлення, перевіряє політику повернення, оформлює refund, відповідає клієнту, пам'ятає попереднє звернення.

Порядок діагностики, **ззовні досередини**: чи правильний результат → чи працює harness (код) → чи стабільна модель → лише потім пам'ять і tools. Так швидко видно, де зламалось, і не лізеш в налагодження моделі, поки парсер не з'їв пів відповіді.

### 2. Чому звичайні тести не працюють: pass@k і pass^k

- Звичайний тест тримається на контракті «той самий вхід → той самий вихід». LLM його не тримає, і **не тому, що вона «ймовірнісна»**: при температурі 0 береться найімовірніший токен. Недетермінізм виникає на боці провайдера: запити рахуються **батчами**, GPU-ядра поводяться по-різному залежно від розміру батча, змінюється порядок додавання чисел з плаваючою комою (помітно при BF16). Чим довша генерація, тим імовірніше розходження; у reasoning-моделей розходиться майже завжди. Джерело: Yuan et al., https://arxiv.org/html/2506.09501v2.
- Тому **одна задача = кілька прогонів**, і між прогонами **нічого не міняти** (промпт, порядок tools, температура). Якщо щось змінити — вимірюється вже власна правка, а розкид моделі змішується з нею в одну цифру. Стійкість до перефразувань і перестановок — окремий тест (розділ 9).
- Приклад: «хочу повернути замовлення 12345» ×5: у 4 прогонах агент знайшов замовлення і перевірив політику, в одному одразу полетів оформлювати refund без перевірки. Такий розкид ловиться лише повторами.
- Критерій «задача виконана» — детермінований: **викликано правильний tool і правильна сума refund**.

Таблиця з дошки: 4 задачі × 5 прогонів. A — 5/5, B — 4/5, C — 1/5, D — 0/5.

- **pass@k** — чи вирішив агент задачу **хоча б раз** за k прогонів. Тут: A, B, C → **75%**.
- **pass^k** — чи вирішив **усі k разів** (метрика з τ-bench, https://arxiv.org/abs/2406.12045). Тут: лише A → **25%**.
- Для продакшну важливий **pass^k**: той самий запит приходить від сотень клієнтів, є ретраї. 25% означає, що 75% задач клієнтів провалиться.
- Читання метрик: **pass@k високий, pass^k низький → нестабільний harness** (треба більше детермінованих частин, менше «модель вирішує сама»). Задача, що не пройшла жодного разу (D), — системний клас проблем (наприклад, інша валюта, дуже довга історія звернень).
- [06:56] Zhou et al., «Accuracy, Stability, and Repeated-Run Reliability of LLMs on Deterministic Programming Tasks», https://arxiv.org/abs/2606.00920: 16 моделей × 5 прогонів; рейтинг за середнім успіхом і за стабільністю **різний**.
- [07:12] Принстонський HAL (https://hal.cs.princeton.edu/reliability/): за 24 місяці розвитку моделей **стабільність майже не виросла**; модель, що бере майже 80% задач, нестабільна.
- Цей набір задач (по одному прогону змін промпта чи harness) дає «знімок» метрик, з яким порівнюємо після кожної правки.

### 3. Harness — це код, і його тестують як код

- [09:52] Harness = routing, orchestration, парсинг відповідей, retry-логіка, виклики tools, guardrails, промпти, описи tools і скілів. Частина — звичайний код у git. У прикладі: роутер типу звернення, парсер номера замовлення, retry при таймауті, guardrail на суму (refund вище порога — тільки з апрувом менеджера).
- [10:40] **Harness впливає на результат сильніше за модель.** Змінити harness без зміни моделі — розкид більший, ніж від зміни моделі; різні harness міняють рейтинг моделей. Stop Comparing LLM Agents Without Disclosing the Harness, https://arxiv.org/abs/2605.23950.
- [11:20] **Промпти між моделями не переносяться.** Приклад: Opus добре слухав заборони («не роби X»), а на іншій моделі вони працювали погано — допомогла позитивна форма («роби так»). Особливо важливо для нових фронтирних моделей Anthropic з їхніми правилами написання промптів.
- [11:44] **Слот 1 (без LLM): записані відповіді (record/replay).** Підставляємо зафіксовані відповіді моделі й перевіряємо harness. Дешево, детерміновано, **$0**, можна на кожен коміт. Фікстури «тухнуть» (змінили промпт, модель або порядок викликів) — їх треба перезаписувати.
- **Слот 2 (з живою моделлю): дорого.** Коли запускати — залежить від бюджету: на кожен PR, перед релізом або як A/B на частині трафіку. Не ставити виклики LLM «на кожен чих».
- **Retrieval** — теж harness: подали запит, отримали релевантні документи. Детерміновано, якщо один раз розмітили, які документи релевантні; відповіді retrieval можна теж записати.

### 4. Модель: змінюється, навіть якщо ви її не чіпали

- [14:32] Flip rate (https://arxiv.org/pdf/2608.13607, «No Universal Signal Predicts Sample-Level LLM Regression under Version Updates»): 6 пар оновлень; **flip rate** — частка відповідей, що були правильні, а стали неправильні. MMLU-Pro: від чверті до третини; математика: від 5% до половини; код тримається краще — 10–25%. Середня точність при цьому виросла від пари пунктів до ~30. Універсального сигналу, що заздалегідь покаже, який кейс зламається, **не знайшли** — лише прогнати свої тести.
- [15:28] **Пін моделі.** Dateless ID у Anthropic — pinned snapshot: ваги під цим ID не змінюються (https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions, розділ «Model weights versus serving infrastructure»), але **може змінитись стек навколо ваг**: роутер, safety-класифікація, семплінг. Ознака: вчора модель це робила, сьогодні «не можу».
- [15:52] **OpenRouter**: під однією назвою моделі — десятки вендорів з різним квантуванням і налаштуваннями; без вибору провайдера він вибирає сам. Його тест: 8 запитів пішли до 6 різних хостерів, і той самий запит витрачав на «роздуми» від ~10 до 300–1000+ токенів. Не закріпили вендора — міряєте середнє по чужому залізу.
- У всіх трьох випадках (змінили самі / змінив провайдер / OpenRouter) — **regression suite за розкладом**: [16:56] у нього **30–50 реальних задач з домену** (для прикладу — 30 реальних звернень, де відомі правильні відповіді). Змінили модель чи промпт — прогнали.

### 5. Пам'ять

- [17:36] AgentMemBench (https://arxiv.org/abs/2608.00009, червень): 5 стратегій пам'яті. Зовнішнє KV-сховище шукає краще за всіх, але платить контекстом — **приблизно у 20 разів більше токенів**. Решта чотири (від довгого контексту до summarization) майже нічого не знаходять, якщо потрібний факт лежить багато сесій назад.
- Що перевіряти — відкрите питання. «Запам'ятав/забув» — не головне. Дослідження «From Recall to Forgetting» (https://arxiv.org/html/2604.20006v1): у задачі рекомендацій майже **дві третини помилок — через застарілий факт, який не забули**. Він називає це **дрейфом пам'яті**.
- **Тест 1 — застаріла пам'ять.** Клієнт звертався місяць тому, політика повернення була 30 днів, тепер 14. Змінюємо політику в джерелі, питаємо агента: чи відповідає за новою політикою і пояснює, що правила змінились. Іноді правильна поведінка — перевірити факт у джерелі.
- **Тест 2 — обмеження не переживає стиснення контексту.** З його відео про продакшн-агента (пошта директора, правило «не діяти без мого ok» зникло після compaction). Тест: забити контекст до compaction і перевірити, чи заборона вціліла в новому вікні.
- Загалом: виділити критичні речі, які агент бере з пам'яті, і під кожну написати тест.

### 6. Tools

- [19:28] Для кожної тестової задачі вказуємо **очікуваний tool**. Текст відповіді **не порівнюємо** — дивимось, чи викликано потрібний tool з правильними параметрами (детермінована перевірка). Якщо шляхів кілька — очікуване описується множиною: які **обов'язкові**, які **заборонені**; жорстка послідовність ламається на першому ж валідному обході.
- [20:00] «Invocation-Level Reliability of Tool-Using Agents» (https://arxiv.org/abs/2608.26189): помилки в параметрах tools **накопичуються по ланцюгу**; до шостого кроку агент втрачає **~70%** здатності, яку показує на чистому контексті, хоча задача не ускладнилась — він спотикається об власні ранні помилки.
- Приклад: `getOrderById` з переплутаним ID → агент отримав чуже замовлення → перевірив політику → оформив refund **чужого** замовлення. Кожен tool окремо відпрацював правильно, гроші пішли не туди.
- Тому перевіряти tools по одному мало — потрібна **перевірка всього ланцюга (траєкторії)**: запит, кожен виклик з аргументами, кожна відповідь моделі, усе, що пройшло через контекстне вікно. Але **жорстку послідовність кроків у траєкторії не тестувати** (крихкі тести). Три перевірки (дошка, [21:52]): ① аргументи tools, ② обов'язкові tools викликано, ③ заборонені не викликано.
- [22:08] Суддя, що дивиться **лише на результат**, ловить ~**45%** збоїв (https://arxiv.org/abs/2609.00038, «What Outcome-Only LLM Judges Miss on Agent Trajectories»). Тихий збій: refund оформлено правильно, але по дорозі агент заглянув у чуже замовлення або пообіцяв компенсацію, якої нема в політиці.
  - Інваріант (`search_order` лише з ID із запиту чи історії цього клієнта) ловиться кодом.
  - «Пообіцяв компенсацію, якої нема в політиці» кодом виразити важко — це ловить **суддя, що читає траєкторію**; він значно дорожчий за суддю результату. **Тестувати треба і результат, і траєкторію — одне іншого не скасовує.**
- Приклад з практики: агент-когорти мав 5 tools; додали ще 2 (фільтри за атрибутами профілю), а агент їх не викликав і відповідав текстом. Причина — у system prompt лишився рядок зі старої версії: «за атрибутами профілю когорти не будуємо». Модель слухала промпт. Ловиться suite-ом з очікуваними tools на етапі розробки.

### 7. Хто виставляє оцінку: код → суддя LLM → людина

[23:52] Три рівні (дошка: ① Код, ② Суддя (LLM), ③ Людина, стрілки вгору).

1. **Детермінований код — найдешевший рівень.** Чи викликано правильний tool, чи валідна схема, чи не витекло заборонене, чи вклались у бюджет токенів, інваріанти. Безкоштовно, миттєво; **за його словами, так знаходиться приблизно половина всіх багів агентів із його практики.**
2. **LLM-суддя** — те, що кодом не перевірити: якість, повнота, тон.
   - Пишуть, що судді збігаються з людьми на 80+%. Це частка точних збігів, частина випадкова. Поправка на випадковість — **коефіцієнт Коена (κ)**: беремо відповіді, розмічені людьми, віддаємо суддь, дивимось, наскільки частіше збігається, ніж «монеткою»: 0 = монетка, 1 = повний збіг.
   - [25:20] Norman et al., «Reliability without Validity» (https://arxiv.org/abs/2606.19544, червень 2026): 21 суддя від 9 провайдерів, ~півмільйона суджень. На MTB ті самі судді з 80+% збігу мають κ ≈ **0,45**; на інших наборах до 0,9 — залежить від того, що судимо.
   - Орієнтир з іншої роботи: посадити **двох людей**, розмітити той самий набір і порахувати κ між ними — у авторів вийшло **0,8**. Від судді вимагати, щоб він був не набагато гірший за людей.
   - [26:00] «Catching One in Five: LLM-as-a-Judge Blind Spots in Production Multi-Turn Transaction Agents» (https://arxiv.org/abs/2606.10315): продакшн-агент приймання замовлень, суддя проти розмітки людей: з **9** системних проблем, знайдених людьми, суддя знайшов **2**; бойовий gate пропустив усі **100 раундів** у партії, де люди нарахували **23 дефекти**. Майже в кожній своїй нотатці суддя сам описував поломку (підтвердження замовлення/кошика), а бал ставив за рубрикою «тон бренду» — **поломку бачив, а оцінку за неї не знижував**.
   - Три відомі перекоси (MT-Bench, https://arxiv.org/abs/2306.05685): **позиція** (залежить від порядку відповідей), **довжина** (любить довгі), **власне сімейство** (завищує оцінку своїй моделі — найспірніший). У його замірах: у ~3 випадках із 4 перше місце діставалось найдовшій відповіді, переможець у середньому **більш ніж удвічі довший**; коли оцінку розклали на перевіряване (наприклад, чи збирається код), порядок моделей перевернувся.
   - **Протидія:** усе, що можна перевірити, — у детерміновані перевірки; при парному порівнянні **міняти відповіді місцями**; суддя з **іншого сімейства**; **коротка шкала — він бере 1–4**. Ціна: 1000 оцінок — від ~$0,5 на дешевих моделях до ~$20 на Opus.
3. **Людина над суддею — калібрування.** [27:28] 20–30 випадкових сесій з продакшну розмічають за **письмовою рубрикою**; частину — двоє людей (κ між людьми). Потім суддя проганяється по тих самих сесіях; якщо стабільно ставить 4, де люди 2 — правимо промпт/рубрику (даємо приклади «ось так виглядає 2, а ось 4») і повторюємо по колу, поки не зійдеться. Людська розмітка теж шумить (розмітники штрафують відповіді з застереженнями, а користувачі довіряють відповіді незалежно від застережень) — **«останньої інстанції нема»**.
   - **Agent-as-a-Judge** (https://arxiv.org/abs/2410.10934): суддя — окремий агент із власними tools і циклом: може запустити код, смикнути API, подивитись, що повернув tool. На бенчмарку DevAI він обійшов звичайного LLM-суддю і вийшов на рівень людей. У прикладі: звичайний суддя читає лог і бачить «refund оформлено»; агент-суддя піде в базу й перевірить, чи лягла правильна сума. Дорожчий, потребує підтримки.
   - Суддю можна поставити в пару з **агентом-критиком**: агент відповів → критик написав, що не так → суддя ставить оцінку з урахуванням критики (https://arxiv.org/abs/2605.27483, «Debate Helps Weak Judges Reward Stronger Models»: один критик дає майже всю користь від багатораундового спору моделей, але дешевше). Людину над суддею це не скасовує.

### 8. Регресія чи шум? Звідки брати тест-кейси

- [29:46] Його випадок: після правки дві перевірки повтору репліки стали дивитись на різне (одна на весь текст, друга лише на звернення), і нормальна репліка іноді йшла у відбій. Гнали кожну версію по **14 разів**: до правки відмов нуль, після — приблизно **кожен третій** прогін, після наступної правки — **більше половини**. Одним прогоном не відловити. Після виправлення — 30 прогонів підряд, жодної відмови.
- Правило: **набір, якого стосувалась правка, — 20 прогонів; звичайний smoke на кожен PR — по 5.**
- **Пара версій:** той самий набір входів на **старій версії (еталон/baseline)** і на **кандидаті** одночасно. Еталон теж падає через раз → **шум**: тест — у окремий список на розбір, щоб не фарбував PR. Еталон проходить усі прогони, а кандидат жодного → **регресія**.
- **Порівнювати кожну задачу окремо з її базою на main, а не середній pass rate** — одна зламана задача в середньому тоне і виглядає як трохи більше шуму. Smoke: до десятка найкритичніших задач × 5 прогонів; PR червоний, якщо задача дала 0/5, а на main давала 5/5.
- **Ціна пари:** еталон на main змінюється рідко — гнати його **раз на добу**, класти результат як артефакт CI і порівнювати PR із ним. За добу провайдер може щось змінити «мовчки» — це ловить regression suite за розкладом.
- **Звідки брати кейси — з failure taxonomy, з реальних логів, не з голови** (пробував з голови — нічого доброго). Hamel Husain і Shreya Shankar (навчили 2000+ інженерів і продуктів; https://www.lennysnewsletter.com/p/building-eval-systems-that-improve): «приберіть усе, що заважає дивитись на дані». Процес: відкрити **100 логів агента з продакшну**; Google-таблиця з трьома колонками (**trace ID, тег, один рядок нотаток**); кожен збій — коротким тегом («не той tool», «галюцинація політики», «втратив контекст на п'ятому ході»); після перших десятків груп тегів у категорії; з кожної — 3–4 конкретні кейси. Зупинитись, коли нові логи перестають давати щось нове. Результат — **~20 реальних входів**, кожен = запит клієнта + очікуваний набір tools + очікуваний результат. Займає приблизно півдня, без цього тестам нема на чому виконуватись.
- [32:24] Далі (теги на слайді): **двадцять входів → gate CI/CD → інструменти → метаморфічні тести.** Який би інструмент не обрали, потрібен **трейсинг** — вони працюють поверх логів. Повний лог = запит клієнта, усі виклики tools з аргументами, усі відповіді моделі, токени. Звичайний CI на LLM-фічах ламається: відповідь від прогону до прогону різна, падає мовчки, кожен прогін коштує грошей.

### 9. Що ще ламає агентів

- **Метаморфічне тестування** (не входить в pass^k): правильну відповідь знати не обов'язково, достатньо знати, як співвідносяться два прогони. Перефразували запит / переставили документи в контексті / спитали іншою мовою → агент має викликати **той самий tool з тими самими аргументами**. Практика: до кожного кейсу додати по **3 перефрази** і перевірити, що набір tools і параметри не змінились.
- **Eval awareness** (https://www.lesswrong.com/posts/TeLLtMjtcoB9qCoL3, «Better evals are not enough to combat eval awareness»): моделі вчаться розпізнавати, що їх тестують, тож пройдений eval ще не означає, що в продакшні буде так само. Є й інша проблема — модель знаходить короткий шлях до метрики.
- **Суд у Німеччині** ([33:52] OLG Hamm, 4 UKl 3/25, 12.05.2026, https://nrwe.justiz.nrw.de/olgs/hamm/j2026/4_UKl_3_25_Urteil_20260512.html): чат-бот клініки естетичної медицини сказав клієнтам, що директори клініки — лікарі-спеціалісти з пластичної та естетичної хірургії; такої кваліфікації вони не мали, а двох спеціальностей, які назвав бот, **не існує — він їх вигадав**. За рішенням суду чат-бот — інструмент компанії, його слова **вважаються словами оператора**; галюцинувала модель чи неправильно обробила правильні дані — суду однаково; те, що боту дали лише правильні дані, не рятує. Оператор мусить **до запуску** перевірити, що бот не бреше про кваліфікацію. Рішення ще не остаточне. На його думку, у компанії не було тестів на відповіді, за які вона відповідає: кваліфікація, ціни, гарантії.
- **Безпека** (витік персональних даних, зламування) — окреме майбутнє відео, тут не розбирається.
- **Chaos engineering** [35:36]: перевірка на збої інфраструктури навколо агента. ReliabilityBench (https://arxiv.org/abs/2601.06112, січень 2026): 4 види відмов — таймаути API, rate limits, часткова відповідь, зсув схеми; 1000+ епізодів; найсильніше б'є rate limit (успіх на 2,5% нижчий, ніж при суміші відмов); якщо перефразувати самі задачі — успіх з першої спроби падає майже на 9 пунктів. [36:00] AgentChaos (https://arxiv.org/abs/2608.06790): перехоплює HTTP між агентом і LLM API і ламає відповідь програмно — API не відповідає, частина відповіді зникає, або відповідь повна, але значення зіпсовані; код агента не чіпається; частка задач, що проходять з першого разу, падає **до 50%**. Одразу показує, наприклад, відсутність retry-логіки в harness.

### 10. Висновок автора

Eval — не цифра, а **система**: агент = harness, модель, пам'ять, tools; зламатись може кожен по-своєму, і зрозуміти, що працює, а що ні, можна, лише тестуючи їх окремо. Чим раніше почати вимірювати, тим кращий агент у продакшні — і тим менша ймовірність опинитись перед судом.

### Що з цього для фабрики

Це **мої висновки, не з відео**.

1. **Суддя має бачити сирі артефакти, не переказ.** Зараз self-review (`factory-self-review`) і Review-фаза читають те, що вирішить показати агент. Для Spec/Implement/Bug варто в gate між фазами подавати суддям diff, плани й логи напряму, а не summary фази. Це прямий урок з розділу 0 (і з першої нотатки про gate).
2. **Суддя на іншій моделі, ніж та, що писала.** У нас вже є карта маршрутизації моделей по ролях (#28100); потрібно лише закласти правило «роль `reviewer`/`validator` — не з того ж сімейства, що `work`». Спорідненість з перекосом «суддя завищує свою модель».
3. **Калібрування суддів по розмітці людей.** Коли з'являться агенти-судді в пайплайнах — вести невеликий набір людьми розмічених сесій (20–30) і міряти κ судді проти людей, а не довіряти «80% збігу». Дані для цього вже є: аудит запусків, транскрипти, рішення людей на Review (approve / request changes).
4. **Evals для самої фабрики.** Pass^k для фаз і скілів: прогнати той самий набір задач (наприклад, 10 тікетів з тестового репозиторію) по 5 разів на Bug/Work/Spec і дивитись не середнє, а стабільність. Regression suite на 30–50 реальних задач перед зміною моделі чи редагуванням скіла — зараз `scripts/compare-tests.sh` порівнює лише юніт-тести, а не поведінку агентів.
5. **Record/replay уже частково є.** Тести harness з підставленими відповідями моделі — те, що він називає слотом 1 ($0, на кожен коміт). Це наш звичайний `corepack pnpm verify`. Слот 2 (жива модель) у нас відсутній; вирішити, коли його ганяти (перед релізом чи на PR).
6. **Перевірка траєкторії tools правилами дошки.** «Обов'язкові / заборонені tools», аргументи tools — це те саме, що наші детерміновані rules (`rules/reproduction-test.ts`). Можна узагальнити: правило на переході читає журнал викликів сесії (з аудиту `factory.run.*`) і блокує, якщо, наприклад, у Review не було запущено тестів.
7. **Пін моделі й провайдера.** Для моделей у картці «моделі фабрики» фіксувати dateless/dated ID і, якщо йде через gateway типу OpenRouter, **вказувати вендора** — інакше результати плавають між хостерами.
8. **Дрейф пам'яті.** Наші організаційні знання (rules, ADR, auto-memory, Knowledge) теж можуть застаріти; бажано, щоб запис мав дату й джерело, а агент перевіряв факт у джерелі, якщо він старший за N днів. Тест «змінили правило → агент відповів за новим».
9. **Правило «20 прогонів на правку, 5 на PR»** і порівняння з baseline на main раз на добу — готовий регламент для оцінювання змін у скілах і промптах фабрики.
10. **Юридичний ризик** (розділ 9): відповіді агента клієнтові (коментарі в issue, повідомлення в чат) — слова оператора; для тих, що стосуються цін, гарантій, кваліфікації, потрібні тести й, можливо, людина на виході.

Статус: нотатка, не взято в роботу.


## Мульти-репо: робоче середовище з кількома репозиторіями і картки

Потреба: одна фабрика працює над продуктом, що живе в **кількох репозиторіях** (наприклад, backend + web + mobile + shared-пакет). Одна задача часто зачіпає **декілька репозиторіїв одразу**, і картка на дошці має це відображати: які репозиторії вона торкається, де гілки, де PR.

Нижче: як це працює зараз (за кодом v4, не запускав), чого бракує і що з цього потрібно. Розділи «як зараз» — факти з коду; «чого бракує» — мої висновки.

### Як зараз

**Середовище (воркспейс) вже багаторепозиторне.**
- Фабрика містить кілька репозиторіїв через `ProjectRepository`: гілка, `setupCommand`, `teardownCommand`, порядок, прапорець `inEnvironment` (`packages/contracts/src/contracts.ts`, налаштування в `apps/ui/.../settings/components/environment/RepositoriesBlock.tsx`).
- Репозиторії з `inEnvironment` клонуються **поруч в один корінь** пісочниці: `<root>/<repo-a>`, `<root>/<repo-b>` (`packages/harness-mastra/src/workspace.ts`, `resolveEnvironmentRepositories` у `packages/session`). Агент отримує опис розкладки.
- Якщо два репозиторії мають однакове ім'я теки, **другий мовчки пропускається** (лише `console.warn`).
- Позиція 1 у середовищі — «якір»: під цим репозиторієм зберігається рядок сесії.

**Картка прив'язується до репозиторію слабо, через метадані** (`resolveWorkItemRepository`, `packages/session/src/work-item-repository.ts`). Порядок:
1. Картка з issue провайдера: id репозиторію з метаданих (`githubRepositoryId` / `gitlabProjectId`), переживає перейменування.
2. Картка з `metadata.repository` (slug `owner/name`): ставиться вручну (діалог `RepositoryPickerDialog`) або агентом через `factory_create_work_item` / `factory_update_work_item`.
3. Нічого не вказано, у фабриці **один** репозиторій: береться він.
4. Нічого не вказано, у фабриці **кілька**: картка працює **на все середовище**. Жоден репозиторій не головний, **кожен отримує гілку сесії і свій change request** (коментар у коді).
5. Якщо середовище порожнє, а репозиторіїв кілька: помилка `source_repository_ambiguous` («Choose a repository for this work item»).

**Сесії однієї картки ділять гілку** `factory/item-<id>`; сесія, прив'язана до іншого репозиторію, ніж картка, відхиляється (`workItemRunsInLink`).

**Дошки спільні для деплою** і до репозиторію не прив'язані.

### Чого бракує (мої висновки)

1. **Картка — це «один репозиторій» або «усе середовище», середини нема.** Не можна сказати «ця задача торкається backend і web, але не mobile». Метадані мають одне поле `repository` (рядок), а не список. Наслідки: зайві клони/гілки/PR у репозиторіях, яких задача не стосується, і ризик, що агент полізе туди, куди не треба.
2. **Невідповідність підказок і поведінки.** Опис tool `factory_create_work_item` каже «runs refuse to start on a card that doesn't say which» (при кількох репозиторіях), а код у п. 4 дозволяє запуск на все середовище. Треба вирішити, яка поведінка правильна, і вирівняти текст або код.
3. **Видимість на картці.** На картці бачимо один репозиторій (`boardRepository.ts`, `BoardCardParts.tsx`). Для картки на все середовище незрозуміло: які репозиторії зачеплені, у яких вже є зміни, яка гілка і PR де. Є групування змін по репозиторіях у viewer (`RepositoryChangesGroup.tsx`), але не на самій картці.
4. **Кілька PR на одну картку.** Фази Review / PR / Acceptance задумані навколо одного PR. Що таке «картка пройшла Review», якщо PR три і один з них вимагає змін? Чи блокує один PR закриття картки? Не перевірено, як це зараз зведено в статус.
5. **Залежність між репозиторіями.** Потрібен порядок: спершу змерджити shared-пакет, потім backend, потім web. Зараз порядок середовища (position) впливає лише на розкладку і якір, але не на порядок злиття PR.
6. **Верифікація між репозиторіями.** Setup/teardown задаються на репозиторій, а перевірка «зібралось і тести пройшли» для задачі, що чіпає два репозиторії разом (контракт API ↔ клієнт), окремо не описана. Питання, хто і де запускає інтеграційну перевірку.
7. **Різні гілки і базові гілки.** У `ProjectRepository` є своя гілка, але гілка сесії `factory/item-<id>` однакова в усіх репозиторіях. Якщо в репозиторії немає змін, чи створюється гілка/PR порожнім? Не перевірено.
8. **Імена тек.** Конфлікт імен тек (`repositoryDirectoryName`) має бути видимою помилкою в налаштуваннях, а не `console.warn`.
9. **Різні провайдери в одній фабриці** (частина на GitHub, частина на GitLab): `listLinkedRepositories` фільтрує з'єднання за `integrationId` поточного source control, тож для змішаної фабрики потрібне окреме розв'язання; не перевірено, чи це працює.
10. **Агенти й токени.** Токени передаються на кожен репозиторій окремо; для картки на всі репозиторії варто перевірити, що в сесії є доступ до кожного і що відмова в одному дає зрозумілу помилку (`repository_clone_failed` не каже, який саме).

### Що потрібно (пропозиція)

- Поле картки **`repositories: string[]`** (підмножина середовища) замість одного `repository`; сумісність: старе значення = список з одного елемента, порожній список = усе середовище (як зараз).
- **Вибір репозиторіїв на картці** в UI (мультивибір замість `RepositoryPickerDialog`), і те саме в tools для MCP/чату.
- **Картка показує по кожному репозиторію:** гілка, чи є зміни, PR/MR і його статус.
- **Статус картки з кількох PR:** правило агрегації (картка зелена, лише коли всі PR зелені) і блок злиття за порядком залежностей.
- Агент у сесії **бачить лише репозиторії картки** як «робочі», решта середовища доступна лише на читання.
- Явна помилка для конфліктів імен тек і для змішаних провайдерів.

Статус: нотатка, не взято в роботу. Нічого не запускав, лише прочитав код (`packages/session`, `packages/store`, `packages/harness-mastra`, `packages/contracts`, `apps/ui`).


## Claude Code: чому в чаті не видно міркувань моделі

У чаті сесії Claude Code блоків міркувань (thinking) нема, хоча в інтерактивному `claude` у терміналі їх видно.

### Відповідь

**Це обмеження самого Claude Code в режимі `-p`, а не помилка фабрики.** Перевірено на `claude` 2.1.316 (`-p --output-format stream-json --verbose --effort high`):

- простий запит: у відповіді лише блок `text`, блоку міркувань нема;
- складніший запит на Opus: блок `thinking` є, але його поле `thinking` **порожнє** (довжина 0), лишається тільки `signature`.

**Наш код нічого не губить.** Розбір блоків `thinking` є в `packages/harness-claude-code/src/events.ts`, проєкція в повідомлення тред-чату в `packages/harness-claude-code-ui/src/projector.ts`, відображення в UI (`MessageBubble`, `ModelThinkingGroup`). Порожній блок пропускається (`events.ts:227`), бо показувати нічого. Якби CLI віддав текст, він з'явився б у чаті.

**Paperclip робить так само.** `temp/paperclip/packages/adapters/claude-local/src/ui/parse-stdout.ts:71` показує `block.thinking`, лише якщо він непорожній, і передає тільки `--effort`. Тож у ньому міркувань теж нема.

**Що кажуть документи Claude Code** (за відповіддю агента-довідника, повністю не перевірено):

- Інтерактивний режим показує міркування через `Ctrl+O` (verbose) і налаштування `showThinkingSummaries`. Обидва задокументовані лише для інтерактивних сесій.
- `showThinkingSummaries` через `--settings` у `-p` не діє: я перевірив, поле лишилось порожнім.
- `MAX_THINKING_TOKENS`, `alwaysThinkingEnabled`, `--effort` керують тим, чи міркування є і скільки, а не чи показується їхній текст.
- `--forward-subagent-text` віддає текст і міркування лише субагентів, не головної сесії.
- `--include-partial-messages` описаний лише для потокових токенів.
- Сторонні джерела (не документація) пишуть, що в headless показ міркувань вимкнений і що запит на опцію відкритий: https://claudeissues.com/issue/82896-allow-display-summarized-extended-thinking-in-print-output-format-stream-json-he

Документи: https://code.claude.com/docs/en/settings-reference.md, https://code.claude.com/docs/en/model-config.md#extended-thinking, https://code.claude.com/docs/en/headless.md#follow-subagent-messages.

**Висновок:** поки Claude Code не віддасть текст міркувань у `-p`, побачити їх у фабриці на Claude Code неможливо. На Mastra-харнесі міркування видно, бо модель викликається напряму через API.

### Що можна зробити (не зроблено)

1. У чаті показувати примітку на кшталт «Claude Code не віддає міркування в цьому режимі», щоб відсутність не виглядала поломкою.
2. Перевірити, чи Agent SDK має опцію показу міркувань (не перевіряв, це окрема документація).
3. Відкрити запит у Claude Code з відтворенням (`/feedback`).

Статус: нотатка, не взято в роботу.
