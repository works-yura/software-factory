## Маршрути надходження

- Події ClickUp у порт подій (`work_item.state_changed` зараз бачить лише опитувач ClickUp, не подійні тригери).
- Підказка статусів у редакторі маршруту: для умови «ClickUp List» пропонувати статуси цього списку (`/web/clickup/lists/:id/statuses`) замість вільного тексту.
- Прибрати прив'язки списків ClickUp (`intake_source_bindings`) і вибір `sourceIds` зовсім, коли старих правил статусів не лишиться (зараз їх читає лише міграція `ClickUpIntegration.migrate`). Умова `source.list` поки не каже, чий це список: коли з'явиться другий трекер зі списками, маршрут має називати й інтеграцію.
- Розмови в коментарях ClickUp зараз працюють лише для Lists, названих маршрутами (раніше — за самою прив'язкою List).

- Тригери-події: порт `IntakeEventSource` і `eventTriggerKind` готові (ADR-0016); бракує адаптера, що публікує події провайдерів (PR відкрито/змерджено/закрито, картка перейшла у фазу, нова таска чи коментар у ClickUp) з їхніми id, і самих видів тригерів із формами.
- Дії після аудиту: `notify` (лист / Slack для термінових знахідок безпеки), `create-follow-up-cards` (картки на «Розробці» зі знахідок) — коли буде безпечно.
- Шаблони маршрутів за розкладом і аудитів (готові «Щотижневий аудит безпеки», «Залежності щопонеділка»).
- Невдале спрацювання маршруту за розкладом показувати в «Потребує вас» (зараз — лише в історії маршруту).
- Ворота «MR документів змерджено» в коді: поки це текст у картках «Розробки» й питання людині наприкінці Фаз; дошка злиття не перевіряє.
- Перевірка документа не помічає змін файлу після перевірки.
- Крок специфікації «збудувати чи взяти бібліотеку».

## Агенти

- Інструменти ClickUp для агента: коментар і статус таски (зараз ClickUp лише створює картки).
- Чи підхоплює нову мову агентів уже запущена сесія Claude Code (CLI при продовженні може повторювати системний промпт першого ходу) — перевірити; якщо ні, виправити підказку в UI.
- Перевірити на живому PR, що CLI дотримується `attribution` (без «Generated with Claude Code»).

- OpenCode (ADR-0043): перевірити від імені агента на Mac mini (`FACTORY_AGENT_USER`, профіль Seatbelt; `opencode` у `agent-tools`); MCP-інструменти з «ask» для OpenCode (хаб зараз їх прибирає, як для Codex); вкладення-зображення в хід; steer без зупинки ходу; ротація облікового запису OpenCode посеред ходу (зараз наступний запис бере лише наступний запуск); час повернення безкоштовного ліміту (OpenCode його не каже); продовження власної сесії OpenCode на рідній розмові OpenCode (`opencode import`) замість handoff історії.
- Непогано було б зробити харнес ACP (Agent Client Protocol): один модуль харнесу для будь-якого агента з реєстру ACP (`cdn.agentclientprotocol.com/registry/v1/latest/registry.json`) замість окремого пакета на кожного. Джерело для перенесення — `temp/t3code/packages/provider-acp` і `provider-acp-registry` з тестами; приклад у paperclip — `@agentclientprotocol/claude-agent-acp`. Після рефакторингу модулів харнесів. Агентів з реєстру вмикає людина в налаштуваннях (це сторонній код), дозволи лише з налаштувань Factory, запуск у пісочниці від імені агента.

## Логи й креші

- Кілька провайдерів в одній Factory (Firebase + Sentry): агрегатор над `ObservabilityProvider`, інакше назви інструментів конфліктують.
- Другий адаптер крешів через BigQuery-експорт Crashlytics, якщо альфа-API зміниться чи забракне полів.
- Перевірити на живому проєкті: Cloud Logging і Crashlytics v1alpha відповідають так, як у тестах (тести — лише на підробленому Google); чи приймає Crashlytics ID проєкту замість номера.
- Профіль аудиту «логи» для щоденного аналізу — частково закрито профілем `stability`; вирішити, чи потрібен окремий щоденний.
- Лічильник за полем структурованого лога (`jsonPayload.<field>:*`, напр. `teamNotified` у Syncta): `observability_log_groups` фільтрує лише текстом, сервісом, рівнем і HTTP-статусом.

## Пісочниці

Пропозиція (2026-11-11). Присипляння, відновлення, швидкість і невдалий WIP-пуш (папку не видаляти) — рішення й реалізація в [ADR-0039](../adr/0039-local-environment-template-mirrors-and-session-work.md) (позначено ✅). Як зараз — [features/sandbox](../features/sandbox/design.md).

- ✅ **Присипляння замість паузи** ([ADR-0039](../adr/0039-local-environment-template-mirrors-and-session-work.md): refs `refs/factory/wip/heads|tree/<гілка>` у дзеркалі після кожного ходу й перед видаленням папки; на GitHub — при закритті картки). Не тримати на диску купу клонів і запущених процесів. Присипити = закомітити все незакомічене (разом із новими файлами) окремим WIP-комітом → запушити в прихований ref `refs/factory/wip/<картка>` (не звичайна гілка: не засмічує список і не будить CI) → зупинити процеси → видалити папку. Працює однаково для локальної пісочниці, Docker і хмари, бо на рівні git.
- ✅ **Відновлення** (ADR-0039; агентові — сигнал `<factory-sandbox>` на наступному ході) при наступному повідомленні чи старті агента: клон → checkout гілки → WIP-коміт назад як незакомічені зміни (`reset --soft`) → команда налаштування. Агентові сказати, що пісочницю відновлено і що ігнорованих файлів (`node_modules`, збірки, локальні `.env`) і запущених dev-серверів уже немає.
- ✅ **Ліміти** (ADR-0039: налаштування Factory, типово 5 і 2 год, прохід кожні 5 хв; «Зберегти й зупинити» в Settings › Середовище › Пісочниці). Не більше N активних пісочниць (напр. 5); понад ліміт присипляються ті, що найдовше без роботи; окремо — усі, неактивні довше за T (напр. 2 год). Ніколи не присипляти пісочницю, де агент зараз працює; ту, що чекає відповіді людини, — можна (процесу агента там немає).
- ✅ **Закриття картки** (ADR-0039; приховані refs на GitHub прибирає збірка: одразу після мержу закритої картки, інакше за строком): спершу присипляння (WIP-пуш), потім видалення — нічого не губиться; WIP-ref прибирати через певний час.
- **Невдалий WIP-пуш** (мережа, права) — папку не видаляти ✅ (ADR-0039: видалення лише після перевіреного збереження), показати в «Потребує вас» ✅ (вид `sandbox-problem` у `/attention`; у живому UI — «Пісочниці», бо сторінку «Потребує вас» запарковано).
- ✅ **Конфлікт при відновленні** (ADR-0039: збережені коміти лишаються на гілці, GitHub — в `origin/<гілка>`, людині — «гілка розійшлася»; незакомічене, що не накладається, лишається збереженим) (у гілку запушили, поки спала) — явна поведінка: rebase або питання людині, без мовчазного перезапису.
- ✅ **Швидкість відновлення** (ADR-0039: дзеркало на репозиторій і `git clone --local` замість `--reference`; спільні сховища pnpm/npm/yarn з імпортом `clone-or-copy`): спільне сховище git-об'єктів на репозиторій (клон через `--reference`) і спільний кеш pnpm — щоб відновлення займало секунди, а не хвилини.
- **Ізоляція:** Docker-пісочниця з оригіналу (`workspaces/docker`, реалізує `FactorySandbox`) як основна локальна; E2B — опція для команди чи сервера. Перед поверненням E2B з'ясувати, чому його прибрали (`d5f3548`).
- **Заборона пушу в main / базову гілку** в правилах дозволів Factory (зараз `git`/`gh` у терміналі для сесій Claude Code дозволені автоматично, `GH_TOKEN` у середовищі).
- **Список «Потребує вас» після перезапуску** — відновлювати з диска, а не лише з завантажених сесій.
- **Тайм-аут очікування відповіді** — чи потрібен і що тоді (нагадування, а не скасування).

## MCP-сервери

Зроблено: ADR-0025. Лишилось:

- Зупиняти сервери сесії, коли сесію видалено чи картка закрита (зараз — після 15 хв простою або при вимкненні Factory).
- Версії конфігу сервера, як збережені MCP-клієнти upstream (історія змін, відкат).
- OAuth для HTTP-серверів (upstream `authProvider`); зараз лише заголовки.
- «З підтвердженням» для Codex (зараз такі інструменти Codex не отримує).
- Шлюз (MetaMCP / Docker MCP Gateway) під хабом, коли реплік стане кілька.
- MCP Apps (інтерактивні вікна, які MCP-сервер показує в чаті: таблиця, графік) — як у t3code (`apps/mobile/src/features/threads/McpAppWebView.tsx`, `McpAppFullscreenScreen.tsx`, `mcpAppSizing.ts`); у Studio upstream інструменти з `_meta.ui.resourceUri` позначено «App».
- Claude Code: `mcpAskToolsFor` знає лише id сесії — чат Factory, що впізнається тільки за ресурсом, рахується як приватна сесія для списку інструментів «з підтвердженням»; передати ресурс у цей хук.
- «Спробувати» для інструментів без анотацій (лише з явним підтвердженням людини), форма аргументів зі схеми замість JSON (як `ToolPlayground` у Studio).
- Записи каталогу (`server.json` + оверлей, пакет із точною версією): Firebase MCP (`firebase-tools`, `--only crashlytics`), Google Cloud Observability MCP (`@google-cloud/observability-mcp`), Sentry — і порівняти з нашою інтеграцією логів (ADR-0019). Зараз у каталозі лише MCP Toolbox, бо інших пакетів у залежностях немає.
- Підтягувати каталог з `registry.modelcontextprotocol.io` (оверлеї лишаються нашими); іконки серверів у картках каталогу.
- Тип аудиту «База» / «AI-чат» — частково закрито профілем `prod-chats` (плейбук проєкту + логи + «База»). Лишилось: згода клієнта на аналіз переписки користувачів як явна позначка Factory.
- **Масове читання «Бази» для `prod-chats`** (перевірено на емуляторі з Toolbox 1.16): `query_collection` не має collection group, фільтр за часом не спрацьовує ні з ISO-рядком, ні з `{"timestampValue"}`, курсора сторінок немає, і кожен результат іде в контекст моделі — день активного продукту (~1–2 тис. повідомлень) не прочитати цілком. Варіанти: (а) інструмент Factory `database_export` в інтеграції Google Cloud — Firestore REST `runQuery` (collection group, фільтр часу, сторінки) акаунтом прив'язки, маскування `redactDeep` по полях, JSONL у `.factory/` сесії (як `factory_list_attachments`), агенту — лише лічильники й шлях; потребує ADR, бо розширює ADR-0027; (б) власний `tools.yaml` Toolbox з запитами проєкту (беклог вище) — не знімає ліміту контексту; (в) лише вибірка (як зараз у чеклісті).
- Маскування результатів MCP рядком: Toolbox повертає JSON текстом, тож `redactDeep` маскує й числа з 9+ цифр (epoch-секунди/мілісекунди) як `[phone]` і може зламати JSON (`"startMs":[phone]`). Маскувати після розбору JSON, по значеннях.
- Інтеграції (ADR-0027): список дозволених колекцій для «Бази» Google Cloud (prebuilt Toolbox його не має — згенерувати `tools.yaml` з дозволених колекцій); перевести логи й креші Google Cloud на офіційні MCP під капотом, якщо вони з маскуванням не гірші за наш адаптер; наступні сервіси (Supabase, Sentry) — сторінка сервісу + `managedMcpServers`; синк керованих серверів на старті для всіх організацій, коли сховище вмітиме їх перелічити.

## Підключення

Зроблено: ADR-0031. Лишилось:

- Окрема сторінка підключень організації (як «Organization connections» у Mastra): усі акаунти й сервери з тим, до яких Factory вони під'єднані; зараз це видно лише з форми сервера й з картки акаунта Google Cloud.
- Приватні підключення (на рівні Factory чи користувача): своя ланка Factory чи людини до облікового запису — окрема назва, «Відв'язати», власний токен людини. Зараз підключення — лише організації (ADR-0031, доповнення 4).
- Перейменування й видалення для GitLab через Mastra Platform і прямого GitLab токена організації — коли GitLab перейде на токен організації (ADR-0032).
- Записувати в аудит читання логів і крешів Google Cloud, щоб «Активність» показувала їх поруч із викликами MCP; період «Активності» на вибір (24 год / 7 днів) і фільтр за підключенням.
- Перейменування прив'язки Google Cloud власною назвою (зараз рядок названо проєктом).
- Стан прив'язки без «Бази» — зберігати результат «Перевірити доступ», як стан MCP-сервера.
- «Канали» у фільтрі «Додати підключення», коли з'являться канали розмов (ADR-0018).
- Інтеграція «Бази даних» першої сторони (PostgreSQL, MySQL… через MCP Toolbox під капотом): зараз Toolbox у каталозі належить Google Cloud, інші бази — лише як «Власний сервер MCP».

## Токени інтеграцій (ADR-0032)

Зроблено: ClickUp (токен організації, міграція `integrations.envTokensToOrg.clickup.v1`), перевірка адміністратора для `/web/github/pat`. Лишилось:

- **GitLab прямим токеном** — за рішенням ADR-0032: підключення організації (токен, тип, `baseUrl`) у «Підключення › GitLab» з перевіркою в GitLab; база `GitLabIntegrationBase` бере контексти за організацією (`activeContexts`, `contextById`, `listSources`, `resolveActiveConnectionForHost`, `#contextForReference` зараз без `orgId`); ідентифікатор `gitlab-connection:direct:<orgId>` і міграція збережених встановлень `direct` (`installationExternalId`, посилання на репозиторії, `merge-request-reconciler` з перевагою `direct`); webhook `/web/gitlab/webhook/:orgId` із секретом організації; міграція `integrations.envTokensToOrg.gitlab.v1`; e2e (`tests/e2e/src/stack.ts`) підключає підроблений GitLab через API замість `GITLAB_ACCESS_TOKEN`/`GITLAB_BASE_URL`. Тоді прибрати `GITLAB_ACCESS_TOKEN`, `GITLAB_ACCESS_TOKEN_TYPE`, `GITLAB_BASE_URL`, `GITLAB_WEBHOOK_SECRET`.
- **GitHub режимом токена** — за рішенням ADR-0032: токен організації в `integration_connections`, встановлення `token:<orgId>` замість id акаунта, ланцюжок встановлення → організація → токен у клієнтах, clone/push і `mintInstallationToken`; опитування на кожну організацію (зараз один робітник і `projects[0].orgId`); git-ідентичність із токена організації сесії (зараз на процес); слот `github` (App / Platform / токен) — режим токена як підключення організації за відсутності App; міграція `integrations.envTokensToOrg.github.v1` і прибирання запису-заявки. Тоді прибрати `GITHUB_ACCESS_TOKEN`, `GITHUB_ACCESS_TOKEN_ORG_ID`.
- `GET /web/github/pat` не каже, чи може людина змінювати токени (`canManage`): учасник бачить кнопки й отримує 403 з поясненням.
- Коди прив'язки акаунтів (`connect FCT-…`) — у пам'яті одного сервера, спільні для всіх організацій; з токеном на організацію бот у треді — свій, а код — ні (працює, але варто прив'язати код до організації треду).
