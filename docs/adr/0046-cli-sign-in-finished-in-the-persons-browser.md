# 0046. Вхід Claude і ChatGPT завершується в браузері людини, де б не працював сервер

Дата: 2026-11-15 · Статус: прийнято, зроблено (Claude Code, Codex). Змінює частину [ADR-0036](0036-agents-are-connections-ui-shows-usable-harnesses.md) («вхід CLI на машині сервера») і [ADR-0040](0040-mac-mini-production-build-same-data.md) (вхід Claude/ChatGPT як функція «власної машини»).

**Контекст.** Підключення акаунта Claude Code чи Codex (Налаштування › Підключення) запускало на сервері `claude auth login --claudeai` / `codex login`, і CLI відкривав сторінку входу в браузері **на машині сервера**. Коли сервер працює на Mac mini, а людина — за іншим комп'ютером, сторінка відкривалась там, де нікого нема, а в UI посилання не було. Тому вхід пропонувався лише в локальній розробці (`localDevelopment` = `FACTORY_OWN_MACHINE` / development), а на Mac mini додати акаунт агента було нíяк.

Перевірено на CLI: `claude` 2.1.325 відкриває сторінку командою `$BROWSER <url>` (інакше `open`), а в пайп друкує `If the browser didn't open, visit: <authorize URL>` і `Paste code here if prompted >`; код зі сторінки `platform.claude.com/oauth/code/callback` читає з **пайпа** stdin (pty не потрібен; неправильний код — `Login failed: That code wasn't accepted…`, вихід 1). Під pty URL обгорнуто в OSC 8 і в сирому виводі він повторюється. `codex` 0.166.0 має `codex login --device-auth`: друкує сторінку `https://auth.openai.com/codex/device` і одноразовий код (15 хв), сам опитує, доки людина не введе код.

**Рішення.**
- **Браузер на сервері не відкривається.** Вхід запускається з `BROWSER=/usr/bin/true` (`NO_BROWSER`, `accounts/sign-in-command.ts`); `open` CLI не викликає, коли `BROWSER` задано (окремої теки з фальшивим `open` не потрібно).
- **Claude: URL до людини, код назад.** Раннер віддає вивід частинами (`onOutput`) і stdin (`onStarted`). `findSignInUrl` (`accounts/sign-in-output.ts`) знімає escape-послідовності (OSC 8, кольори), бере перший цілий `https`-URL на хостах провайдера (`claude.com`, `claude.ai`, `anthropic.com`; для Codex — `openai.com`, `chatgpt.com`), обрізає повтор (`…state=xhttps://…`), повторений параметр лишає першим, і чекає, доки за URL щось надруковано (вивід приходить шматками). Потік отримує `prompt: { url, acceptsCode: true }`; людина відкриває сторінку у своєму браузері, входить і вставляє показаний код — сервер пише `код\n` у stdin CLI. Далі все як було: пара з Keychain/`.credentials.json`, тимчасова тека й запис Keychain видаляються, стандартний запис `Claude Code-credentials` повертається. Код приймається один раз, лише від того, хто почав вхід (та сама організація й людина), один рядок друкованих символів без пробілів до 2048. Помилку CLI (`Login failed: …`) показано людині.
- **Codex: device code.** `codex login --device-auth -c cli_auth_credentials_store="file"`; `prompt: { url, userCode, acceptsCode: false }` — людина відкриває сторінку й вводить код, CLI завершує сам. Локального callback і браузера на сервері нема. Робочий простір ChatGPT має дозволяти вхід кодом пристрою; інакше CLI падає, і його останній рядок помилки показано людині.
- **Контракт підключень 1.4.0** (додано, не змінено): `AuthorizationStatusResponse.prompt?: { url, userCode?, acceptsCode? }` для `pending`; `POST /web/connections/authorizations/:authId/code?connector=` (`{ code }`) → `IntegrationConnections.submitAuthCode`; `DELETE /web/connections/authorizations/:authId?connector=` → `cancelAuth`. Обидва маршрути — `factory.configure` (як `POST /web/connections`), конектор агентів перевіряє, що потік — свій (`404` для чужого), `409 not_waiting` без очікуваного коду, `400 invalid_code`.
- **UI** (`ConnectorSteps.tsx`): поки вхід чекає — «Відкрити сторінку входу» (нова вкладка, `rel="noopener noreferrer"`, лише `https`), код пристрою для введення, або поле «Код зі сторінки входу» з «Надіслати». «Назад» або закриття діалогу скасовує вхід (CLI не чекає свої 5 хв). en + uk.
- **Обмеження «власна машина» для входу знято.** Воно існувало лише через браузер, що відкривався на машині сервера (коментарі `claude/sign-in.ts`, `codex/sign-in.ts`, модулів і ADR-0040). `localDevelopment` прибрано з конфігів Claude Code і Codex; `createClaudeSignInService` / `createCodexSignInService` створюються завжди, `claudeSignIn` / `codexSignIn` у `/web/config/features` — `true`, коли harness працює. Keychain — не причина: захоплення в тимчасову теку з відновленням стандартного запису працює для будь-якого користувача сервера з доступним login Keychain; якщо Keychain недоступний (заблокований у фоновому сервісі), людина бачить «The macOS Keychain could not be read.». Для OpenCode `localDevelopment` лишився — там він про читання локальної бази сесій людини.
- Ні код, ні URL (його `state` і `code_challenge`), ні код пристрою не пишуться в лог.

**Перевірка.** Юніт-тести з фальшивим CLI, що друкує справжню форму виводу (OSC 8, повтор URL, шматки): `accounts/sign-in-output.test.ts`, `claude/sign-in-remote.test.ts` (URL, `BROWSER`, код у stdin, власник, один раз, неправильний код, скасування, тайм-аут, маршрути з реальним сервісом), `codex/sign-in.test.ts` (device code, помилка), `accounts/sign-in-command.test.ts` (stdin у справжньому процесі); маршрути — `api/agent-connections.test.ts`, `integrations/connections.test.ts`; UI — `ConnectionsSection.msw.test.tsx`. Справжній `claude`: `FACTORY_CLAUDE_SIGN_IN_SMOKE=$(which claude) npx vitest run src/claude/sign-in-remote.test.ts` у `packages/server` — лише отримує URL і скасовує, ніколи не входить.

**Що лишилось.** Повний вхід справжнім акаунтом з іншої машини (Mac mini ↔ ноутбук) не перевірено автоматично. Codex device code у робочих просторах, де його вимкнено адміністратором, не перевірено.

**Альтернативи.** pty (`script -q /dev/null`, `node-pty`) — не потрібен: CLI читає код із пайпа. Проксувати OAuth-callback Codex (`localhost:1455`) через сервер — складніше й крихкіше за device code. Лишити вхід лише на власній машині — відкинуто: на Mac mini акаунт агента не додати.
