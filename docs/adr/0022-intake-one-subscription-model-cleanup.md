# 0022. Надходження: одна модель підписки (маршрути) і прибирання після переробок

Дата: 2026-11-11 · Статус: прийнято (оновлено 2026-11-11, третій прохід) · Доповнює: [ADR-0021](0021-one-list-of-intake-routes.md)

**Контекст.** Другий незалежний перегляд надходження після п'яти переробок (ADR-0015 → 0021) дав вердикт «майже чисто»: ядро й рушій добрі, але лишились хвости старої моделі й одне видиме розходження. Людина: «виправляй, зроби як сеньйор, прибери запах». Рекомендація: одна модель підписки на джерела — маршрути — для всіх трекерів, щоб перенесення Jira/Linear з upstream мало одну модель.

**Рішення (зроблено).**

- **Розміщення — лише диспетчер.** Опитувач ClickUp більше не вирішує, куди лягає нова задача: він вирішує тільки підписку (маршрут називає List задачі, `routeSubscribesSource`) і комітить звичайне надходження з опціями `routing` — `skipCatchAll` (бере лише маршрут з умовою) і `holdAtInitialPhase` (задача, що існувала до старту, лягає в першу фазу дошки маршруту й нічого не запускає). Диспетчер ставить картку однією функцією ядра `placeArrival` (перший маршрут → дошка за замовчуванням). Прапорець `routesApplied` і обхід у диспетчері прибрано; збережений `routesApplied` у старих рішеннях приймається й ігнорується. Картка маршруту за розкладом позначає свій маршрут тим самим штампом `intakeRouteId`, який диспетчер і так зберігає. Задача, чий маршрут уже не може її поставити, лягає в першу фазу дошки за замовчуванням замість падіння опитування.
- **Дошка «має джерело»** для ClickUp — це «ClickUp увімкнено і маршрути проєкту називають List» (`routedSourceLists`), а не прив'язка List з дошкою й вибір `sourceIds`, які UI вже не пише.
- **Підписка лише через `equals`/`in`.** `routeSourceValues` ігнорує інші оператори: маршрут «List ≠ X» більше не змушує читати List X.
- **Міграції на двох репліках.** `createIntakeRoute` перевіряє фіксований id усередині транзакції запису: репліка, що програла гонку первинному ключу, повторює й знаходить рядок переможця. `copyLegacyFires` вважає програну вставку вже скопійованою. Інтеграція, чия міграція впала, вимикається на цей старт (без воркерів, маршрутів, каналів) з помилкою в журналі, а не працює на напівперенесених даних; наступний старт пробує знову.
- **Прибрано мертве:** `ClickUpIntake.bindingBoard`, `ruleFor`, псевдонім `toTriggerRoute`; застарілі коментарі. Дію аудиту `intake_rule` лишено з поміткою: її ніхто не пише, але за нею читаються минулі рядки журналу.
- **UI.** `IntakeRoutesSection.tsx` (1 088 рядків) розділено: список, редактор (`IntakeRouteEditor.tsx`), стан розкладу (`IntakeRouteTriggerStatus.tsx`), формулювання (`intakeRouteLabels.ts`).

**Зроблено пізніше (2026-11-11, другий прохід).**

- **Модуль міграцій старту** (`packages/server/src/migrations/`). Усі разові міграції (маршрути за мітками, виведення дошки Review, фази «Продукту» й «Аудитів», старі правила надходження, картки, утримані тріажем, міграції інтеграцій, вибір репозиторіїв GitHub) — один впорядкований список зі сталими версійними id (`intake.labelRoutes.github.v1`…). `runBootMigrations` виконує їх по черзі; завершена записується в `factory_boot_migrations` (`BootMigrationsStorage`) і на наступних стартах пропускається. Позначка лише економить роботу: кожна міграція й далі ідемпотентна, тож дві репліки можуть виконати її разом, а друга вставка позначки — no-op. Політика збою — у самій міграції: зупинити старт, попередити, або вимкнути одну інтеграцію на цей старт. Змінити зроблене = нова міграція з новим id, а не правка завершеної. `factory.ts` викликає одну функцію.
- **GitHub на маршрути (рішення (а)).** Репозиторії, які читає проєкт, — це GitHub-маршрути на `source.repository` (`routedSourceScopes(routes, 'source.repository', 'github')`, загальна заміна `routedSourceLists`, та сама для Lists ClickUp). Ручна стрічка «Вхідних» лишається окремою можливістю: показує issues прив'язаних репозиторіїв, які названо маршрутами; опитування в режимі токена подає лише їх. Посилання репозиторію додає маршрут на сервері (перед «усім іншим», з його ціллю, сталий id), а не пише вибір організації. Міграція `intake.githubRepositorySelections.v1` перетворює старий вибір (`sourceIds`: id або повна назва) на маршрут для кожного вибраного прив'язаного репозиторію в кожному проєкті — проєкт читає рівно те, що й раніше. Перемикач організації «GitHub увімкнено» лишився. Маршрути Factory позначено `origin: { kind: 'repository' }` і названо мовою читача.

**Зроблено (2026-11-11, третій прохід).**

- **GitLab на маршрути.** Проєкт читає прив'язані проєкти GitLab, які називає його маршрут (`source.integration = gitlab`, `source.repository = <шлях>`): стрічка «Вхідних» (`/web/gitlab/issues`), деталі задачі й правила вебхуків беруть охоплення з `routedGitLabProjects` / `readsGitLabProject` (`integration-gitlab/src/routed-projects.ts`). Непрозорий `gitlab-project:…` зіставляється зі шляхом через прив'язаний репозиторій (id проєкту + хост). Посилання репозиторію GitLab додає маршрут, як для GitHub (хук посилання тепер знає хост). Міграція `intake.gitlabProjectSelections.v1`: вибраний, прив'язаний до проєкту й залінкований проєкт GitLab → маршрут на його шлях. Перевірка ідентичності джерел GitLab (`reconcileGitLabSourceIdentity`) прибрана — вона перекладала саме вибір і прив'язки.
- **Прибрано мертві ендпоінти:** `GET/PUT /web/intake/bindings` (з переносом карток при зміні дошки прив'язки) і `GET /web/intake/items`; у UI — хук і ключ запиту прив'язок. Модель підписки тепер одна: маршрути. Таблиця прив'язок лишається лише як дані, з яких читають міграції ClickUp і GitLab.
- **Канонічна форма маршрутів.** Міграція `intake.canonicalRoutes.v1` (і та сама функція після посилання репозиторію): набір хостів (`in ['github','gitlab']`) або умова на факт лише репозиторних карток (репозиторій, тип, довіра автора) без названого джерела → хости, з яких проєкт лінкує репозиторії (для syncts і post-airborne — лише GitHub); обидва → маршрут ділиться на два підряд, порядок зберігається. Умова на List → ClickUp. Маршрут лише на подію pull request **не** отримує джерела: така подія стосується картки з будь-якого джерела (картка ClickUp, чия сесія відкрила PR), тож він — «будь-яке джерело», а в цього джерела тепер є й події pull request.
- **Прибрано код сумісності:** `candidates`, `leaf`, `named`, `impliedBy`, виведення джерела з умов і подій, примітка «також GitLab». Маршрут, умову якого редактор не показує (набір джерел, поля поза редактором), лишається лише для читання.
- **Описи джерел — у дескрипторах:** `availability` (`always` / `org-connection` / `linked-repository`) і `wording`; `createIntakeSourceRegistry` будує незмінний реєстр, і в UI він створюється в одному місці (`settings/services/intakeSources.ts`). Глобального змінного реєстру й назв провайдерів у логіці UI більше немає.

**Лишилось лише для читання** (умова, яку редактор не редагує): «Pull requests that close a waiting issue join its card» (поля `pullRequest.closesIssue`, `closedIssue.*`) і «Issues whose pull request closed unmerged go back to Intake» (`source.kind ≠ pull_request` — бере й картки ClickUp, тож джерело не назвати без зміни поведінки). Новий проєкт без жодного репозиторію бачить маршрути «GitHub або GitLab» лише для читання, доки не залінкує репозиторій.

**Наслідки.** Поведінка для ClickUp та сама (тести рівнозначності: імпорт, фаза, закриття, ігнор, утримання старих задач, катч-ол не бере задачу List). Зміна: задача, чий маршрут не може її поставити, більше не валить опитування, а лягає в першу фазу дошки за замовчуванням.
