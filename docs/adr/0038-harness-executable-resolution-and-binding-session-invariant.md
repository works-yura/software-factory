# 0038. Виконуваний файл харнесу знаходить сервер; активна прив'язка завжди вказує на наявну сесію

Дата: 2026-11-12 · Статус: прийнято, зроблено. Продовжує [ADR-0036](0036-agents-are-connections-ui-shows-usable-harnesses.md).

**Контекст.** Інцидент на Mac mini. Сервер під launchd стартує з `PATH=/usr/bin:/bin:/usr/sbin:/sbin` (+ nvm), а `claude` лежить у `~/.local/bin`, тож кожна сесія Claude Code падала з `Unable to start Claude Code: spawn claude ENOENT`. Диспетчер вважав це звичайною помилкою запуску й повторив детерміновану невдачу п'ять разів. Потім людина видалила невдалу сесію: `clearSessionReferences` прибрав посилання картки, але рядок `factory_run_bindings` лишився активним на видаленій сесії, і всі наступні запуски падали в диспетчері з «Factory binding … has no authenticated session owner.» (п'ять однакових місць). Вузьке виправлення (adecb6f8) відкликало прив'язки при очищенні посилань; тут — архітектурне.

**Рішення: виконуваний файл харнесу.**
- **Один резолвер для всіх CLI-харнесів** — `@factory/harness/executable` (лише Node). Порядок: команда, яку задало розгортання (`FACTORY_CLAUDE_CODE_COMMAND`, `FACTORY_CODEX_COMMAND`; шлях береться як є і лише він — помилка в шляху не запускає мовчки інший бінарник; голе ім'я шукається як типове) → `PATH` сервера → місця, куди ставляться CLI агентів: `~/.local/bin`, `~/.claude/local`, bin node, що запустив сервер, і `NVM_BIN`, `/opt/homebrew/bin`, `/usr/local/bin`.
- **Знайдений шлях кешується — пошук не коштує нічого на запуск.** Відсутній шукається знову при кожному зверненні, тож CLI, встановлений після старту, підхоплюється без перезапуску. Якщо spawn кешованого шляху впав остаточно (ENOENT, EACCES, ENOTDIR, ENOEXEC), кеш скидається (`spawnFailed`), і наступний запуск шукає наново.
- **Харнеси запускають розв'язаний шлях.** Ядра Claude Code і Codex (сесія, app-server, проба каталогу) і входи CLI (`claude auth login`, `codex login`) приймають `HarnessCommand` — рядок або резолвер. Сервер (`packages/server/src/harness-executables.ts`) створює резолвер з конфігурації; хост зі своїм `spawn` (тести, віддалений раннер) отримує команду як є. `findCodexBinary` прибрано.
- **На старті — у журнал:** шлях, звідки знайдено, `--version`, або «not found» з переліком, де шукали.
- **Доступність.** `withExecutableAvailability` (фасет моделей) робить харнес недоступним усім, доки CLI немає, з `reasonCode: 'executable_missing'` і причиною словами сервера. `withConnectionAvailability` тепер дає `reasonCode: 'connection_missing'`. `/web/config/models` → `instances[].reasonCode`; UI (`harnessUnavailableReason`, en/uk у `common.harnessUnavailable`) пише причину мовою людини скрізь, де показує доступність (Settings › Моделі, «Створити Factory», вибір моделі); для відсутнього CLI підказка не веде до конектора — акаунт тут не допоможе. Codex тепер у списку всюди, де він налаштований, з причиною, а не відкидається на старті.
- **Діагностика.** `/health` лишається як є (без автентифікації, `{"success":true}` 200 — для watchdog). Автентифікований `/web/config/versions` (Settings › Налагодження) додає `harnessExecutables`: шлях, джерело, версія або «не встановлено» і де шукали; рядки йдуть і в «Копіювати версії».

**Рішення: класифікація помилок.**
- Новий `failure_code` **`harness_not_configured`** (`needsPerson`, `canRetry: true`): рішення падає з першої спроби, словами харнесу, без п'яти повторів; людина повторює його, коли CLI встановлено.
- Диспетчер розпізнає це за самою помилкою, а не за рядками: `isHarnessExecutableUnavailable` проходить ланцюжок `cause`/`error` і шукає `HarnessExecutableUnavailableError` або spawn-помилку Node (`code` ENOENT/EACCES/… і `syscall: spawn …`). `ClaudeCodeError` і `CodexAppServerSpawnError` зберігають spawn-помилку як `cause`. Перевірка стоїть і в `runErrorCode` (подія `error` запуску), і в `dispatchFailureCode` (харнес відмовив у відправці ще до запуску), тож однаково класифікується, де б її не спіймали. Помилка запуску тепер — `cause` невдачі диспетчера.

**Рішення: інваріант «активна прив'язка → наявна сесія».**
- **Одне місце видалення сесії** — `deleteSessionRecord` (`@factory/store`). Його кличуть маршрути сесій Factory і GitHub та `session-retirement`. Спершу `clearSessionReferences` в одній транзакції work-items (libsql, pg) відкликає активні прив'язки сесії й прибирає посилання карток, потім видаляється рядок сесії. Вони в різних доменах сховища, тож спільної транзакції немає; порядок тримає інваріант: збій посередині лишає сесію, на яку ніщо не вказує (повторне видалення завершує), і ніколи — прив'язку на видалену сесію.
- **Зачистка.** `revokeStaleRunBindings` відкликає також прив'язки, чия картка не називає власника для її ролі, і (через `sessionExists`, у диспетчері — `harness.getSession`) ті, чиєї сесії вже немає; помилка перевірки прив'язку лишає.
- **Самовідновлення в диспетчері.** Прив'язку без власника `#findBinding` відкликає й пропускає. Шлях старту (invokeSkill, sendMessage з `prepareBinding`) готує нову прив'язку/сесію так само, як будь-який старт: власник наявної сесії або той, хто схвалив рішення (`approvedBy`). Без шляху старту рішення нікого не будить. П'ять копій пошуку `startedBy` замінив один `#runOwner`; він кидає (`run_user_unauthenticated`, без повторів, з ім'ям прив'язки, картки, сесії й ролі) лише коли власника визначити неможливо, і перед тим відкликає прив'язку.

**Альтернативи.**
- Лише дописати `~/.local/bin` у `PATH` launchd-скрипта — це було першим виправленням (d9bfb281); лишається для сумісності, але не рятує інші розгортання й не каже, чому харнес не працює.
- Шукати CLI на кожен запуск — відкинуто: зайва робота, коли він знайдений; кеш + повторний пошук лише відсутнього дає те саме без вартості.
- Розпізнавати `ENOENT` у тексті помилки в диспетчері — відкинуто: та сама фраза буває від інструментів агента; рішення — за структурою помилки.
- Каскадне видалення прив'язок зовнішнім ключем — неможливо: сесії й прив'язки в різних доменах (і різних сховищах інтеграцій).
