# 0045. Права доступу: ролі, дозволи на маршрутах, посилання для вступу

Дата: 2026-11-15 · Статус: прийнято · Доповнює: [ADR-0030](0030-google-sign-in-organizations-invite-links.md)

**Контекст.** ADR-0030 дав організації без ролей: `owner`, `admin`, `member` жили в better-auth, зміну ролі вимкнено, запрошення — лише `member`, а маршрути Factory перевіряли тільки «адмін чи ні» (`isOrganizationAdmin`, розкидано по ~15 файлах). Людина хоче три ролі, як у Mastra Platform (Viewer, Member, Admin), запрошення з роллю, посилання для вступу з параметрами (назва, роль, домени, термін, ліміт), перейменування й аватарку організації, своє ім'я, аватарку й сесії. Листів Factory не надсилає — лише посилання. Перша спроба (глядача тримали ворота за методом HTTP і списком регулярних виразів, посилання для вступу жили в плагіні better-auth) замінена цим рішенням до того, як потрапила на прод.

**Рішення.**

- **Пакет `@factory/access`** (`packages/access`) — єдине місце, де вирішено, хто що може, без залежності від better-auth:
  - каталог дозволів `PERMISSIONS`: `board.read`, `self.write`, `card.write`, `comment.write`, `run.start`, `session.write`, `factory.configure`, `factory.manage`, `connections.manage`, `org.manage`, `members.manage`, `join-links.manage`, `content.moderate` — виведений з того, що маршрути роблять;
  - матриця ролей `ROLE_PERMISSIONS`: глядач — `board.read`, `self.write`; учасник — ще картки, коментарі, запуски, сесії, налаштування Factory рівня учасника; адмін і власник — усе. Єдина перевірка — `can(role, permission)`; невідома роль не має нічого;
  - інтерфейси `MembershipDirectory` (роль, учасники, додати, змінити роль, видалити, вийти, людина, організація), `InvitationService`, `JoinLinkStore`, `AvatarStore`;
  - правила посилань і аватарок (`joinLinkStatus`, `joinRefusal`, `normalizeDomains`, `emailDomainAllowed`, `parseAvatarDataUrl`).
- **Маршрути оголошують, що їм треба.** `@factory/http`: `route(path, { access })`, `withAccess(access, route)`, `declareAccess(routes, table)` — модуль маршрутів сам перелічує `"METHOD /path" → дозвіл` (або `public` для вебхуків, входу, MCP, що автентифікує себе сам). `enforceRouteAccess` ставить перевірку перед кожним маршрутом сервера: дозвіл, якого роль не має, — 403 `{ error: 'forbidden', permission }`; запис без оголошення — 403 `permission_undeclared` і запис у лог (заборонено за замовчуванням). Тест `factory.test.ts › route access` будує всі маршрути сервера з GitHub, GitLab, ClickUp і Firebase і падає, якщо хоч один маршрут, що змінює, нічого не оголосив.
- **Тонші перевірки в обробниках** (адмінські поля проєкту, ключі організації, модерація чужих сесій і коментарів, `canEdit` у відповідях) — `RouteAuth.can(c, permission, orgId?)`; `isOrganizationAdmin` з `RouteAuth` прибрано, другого механізму нема.
- **Власний API Mastra** (`/api/*`: агенти, workflow, пам'ять) — одна група маршрутів, запис у яку потребує `run.start` (`MASTRA_API_ACCESS`, перевіряють ворота).
- **Роль людини** читає `packages/auth` один раз на запит, коли щось питає: у провайдера-довідника — `MembershipDirectory.role` (better-auth, кеш 10 с, зміна в цьому процесі скидає одразу); в інших провайдерів — `isOrganizationAdmin` (адмін або учасник); без організації — власник свого простору. Збій читання — 503, роль не вгадується. `/auth/me` віддає `organizationRole` і `permissions`; UI питає `useCan(permission)`, а не назву ролі.
- **better-auth — лише адаптер** `MembershipDirectory` і `InvitationService` (`MastraAuthBetterAuth`), плюс роль `viewer` в його access control і заборона давати чи змінювати `owner` (`beforeCreateInvitation`, `beforeUpdateMemberRole`). `/organization/update-member-role` знову ввімкнено (адмін, без `owner`). Власник один: «останній адмін» — завжди він, вийти чи бути пониженим він не може.
- **Посилання для вступу** — `@factory/store`, `JoinLinksStorage` (колекція `join_links`, створюється при старті як усі таблиці Factory; наявні не змінюються): назва, роль, домени (точний збіг домену email), термін, ліміт, лічильник, хто створив, коли відкликано, токен (32 випадкові байти). Використання рахується під блокуванням рядка (`updateAtomic`), тож одночасні вступи не перевищать ліміт. Маршрути (`@factory/api`, `buildTeamRoutes`): `GET/POST /web/org/join-links`, `POST /web/org/join-links/:id/revoke` (`join-links.manage`), `GET /web/join/:token`, `POST /web/join/:token/accept` (`self.write`; підтверджений email, домен, термін, ліміт). Уже учасник — успіх без нового використання.
- **Аватарки** — `AvatarsStorage` (колекція `factory_avatars`, байти — у сховищі вкладень `AttachmentBlobStore`; без нього аватарок нема, 503 це каже): png/jpg/webp до 256 КБ (браузер зменшує до 256 px). `POST /web/avatars`, `GET /web/avatars/:id`. Аватарка організації — поле `logo`, людини — `image`. Google не перезаписує вибрані ім'я й фото (`overrideUserInfoOnSignIn` вимкнено; `updateUserInfoOnLink` — лише при першому прив'язуванні).
- **Сесії** — `list-sessions`, `revoke-session`, `revoke-other-sessions` better-auth; IP — з `X-Forwarded-For` (його ставить `tailscale serve`), пристрій — з User-Agent.
- **Аудит** (`factory.organization.*`): зміни ролей, видалення, вихід, запрошення, правки організації — з подій better-auth (`setOrganizationEventHandler`); створення, відкликання й використання посилань — з маршрутів посилань.

**Наслідки.** Новий маршрут, що змінює, не запрацює, доки його модуль не оголосить дозвіл. Глядач не пише в чат агента, не коментує й не запускає; дія, що лише читає через `POST`, оголошує `board.read`. Slack та інші канали роль не перевіряють (поза цим рішенням). Таблиці `join_links` і `factory_avatars` плагіна better-auth з першої спроби на прод не потрапили, тож переносити нема чого. Аналітики (перемикача в акаунті Mastra) нема — у v4 її нема.
