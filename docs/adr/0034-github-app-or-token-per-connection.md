# 0034. GitHub: App або токен — на кожне підключення, не на сервер

Дата: 2026-11-12 · Статус: прийнято, зроблено. Змінює GitHub-частину [ADR-0032](0032-integration-tokens-belong-to-organization.md) (там — «режим токена» сервера як `integration_connections` з ідентифікатором `token:<orgId>`). Сторінка «Підключення» — [ADR-0031](0031-connections-one-list.md).

**Контекст.** Сервер вмикав GitHub в одному з двох режимів: GitHub App (усі п'ять `GITHUB_APP_*`) або один `GITHUB_ACCESS_TOKEN` (тоді App вимкнено, а токен забирала перша організація, що натиснула Connect). Людина: «коли підключаю GitHub, має бути вибір: персональний токен або через App (мій App), який надає доступ». Встановлення App на організацію GitHub потребує згоди її власника; токен працює з будь-яким акаунтом, що вже має доступ (наприклад, репозиторії клієнта). Обидва способи потрібні одночасно в одній організації Factory: свою організацію GitHub — через App, репозиторії клієнта — токеном. Ще знайдено баг: поки був увімкнений App, маршрут `/web/github/repos` на 404 від GitHub **видалив** рядок встановлення старого режиму токена (`pruning stale GitHub installation 28900885`), і його 7 репозиторіїв та 3 підключення проєктів лишились без встановлення.

**Рішення.**
- **Підключення токеном — звичайний рядок `source_control_installations`.** `external_id` — числовий id акаунта токена (як і в старому режимі), `provider_metadata.auth = 'token'` (у рядків App поля немає). Репозиторії й підключення проєктів посилаються на нього так само, як на встановлення App, тож решта коду (клон, пісочниці, правила, опитувачі) не розрізняє способи. Кілька підключень на організацію — норма: App-установки й токени різних акаунтів поруч.
- **Токен зберігається на встановлення, зашифровано.** У налаштуваннях інтеграції (`integration_settings`, шифрує `secretEncryption` сховища) — рядок на акаунт токена поза будь-якою організацією (`__github_token_installations__` / `<id акаунта>`): `{ login, tokens: { <orgId>: <token> } }`. Чому не `integration_connections` організації: усі виклики GitHub адресовані лише id встановлення (`getInstallationOctokit(id)`, `mintInstallationToken(id)`, `{ type: 'app-installation', installationId }`), без організації; пошук за id встановлення дає токен без протягування організації крізь кожен виклик. Дві організації з токенами одного акаунта GitHub зберігаються окремо; виклики для цього акаунта беруть перший збережений токен — це той самий акаунт GitHub, доступ той самий.
- **Одна інтеграція, автентифікація на кожне встановлення.** `GithubIntegration` питає `installationAuth(id)`: є збережений токен → токен; id збігається з акаунтом `GITHUB_ACCESS_TOKEN` → запасний env-токен; інакше → App; App немає → помилка «немає облікових даних» (409), а не тихий запит. Octokit встановлення має власну стратегію автентифікації, що вирішує на кожен запит, тож доданий, замінений чи видалений токен діє без перебудови клієнтів (кеш рішення — 60 с, на випадок іншої репліки). Для токен-підключень зберігається вся поведінка колишнього `GithubTokenIntegration` (клас прибрано, логіку перенесено в `token-auth.ts` і гілки інтеграції): репозиторії — ті, куди акаунт може пушити; перевірки коміту — commit statuses, а не check runs; автор комітів — акаунт токена (`gitIdentityForInstallation`); тріаж-коментар впізнається за маркером і логіном токена; опитування замість webhook-ів: вибірка задач лише з репозиторіїв, названих маршрутами надходження, активність PR — лише для токен-підключень. Працівник звірки тікає кожні 2 хв (темп токенів), а репозиторії App-підключень пропускає до свого темпу (година, виявлення PR — 5 хв), якщо інтервал не задано в env.
- **`authMode` / `mode: 'token'` прибрано.** `/web/github/status` повертає `appConfigured`, `canManage` і для кожного встановлення `kind` (`app`/`token`), `tokenSource` (`stored`/`env`), `needsAttention`. Нові маршрути (організація з `resolveOrgTenant`, змінювати може лише адміністратор організації, як ClickUp у ADR-0032): `GET /web/github/connections` (живий підрахунок репозиторіїв), `POST /web/github/token-connections` (перевірка `GET /user`, перелік доступних репозиторіїв, upsert рядка за id акаунта, токен — зашифровано; 422 з поясненням, який токен вставити; 502, якщо GitHub недоступний), `PUT /web/github/token-connections/:id` (заміна; токен іншого акаунта — 422 `account_mismatch`; так само «старий» рядок env-режиму переходить на збережений токен), `DELETE /web/github/connections/:id` (409 `connection_in_use`, доки проєкти користуються його репозиторіями). Токен у браузер не повертається ніколи. Аудит — `factory.integration.token_connected` / `token_removed`, без токена.
- **UI.** «Додати підключення» має два окремі простих способи: «GitHub» (одразу потік встановлення App; лише коли App налаштовано) і «GitHub · токен» (поле, підказка про права: classic `repo` або fine-grained Contents / Issues / Pull requests / Commit statuses на запис, Workflows — якщо агенти правлять CI; панель «Не вдалося підключити»). Сторінка GitHub перелічує всі підключення (App / Токен / Токен з env сервера, акаунт, кількість репозиторіїв, «потребує уваги») з діями «Керувати на GitHub», «Замінити токен», «Відключити» і «Додати ще». У «Репозиторіях» кнопки «Підключити GitHub» більше немає — лише посилання на «Підключення».
- **`GITHUB_ACCESS_TOKEN` — необов'язковий запасний.** Обслуговує лише рядки старого режиму (id його акаунта, без збереженого токена), доки адміністратор не замінить токен у налаштуваннях. Може стояти разом із `GITHUB_APP_*` — це і є цільова конфігурація. Нові організації автоматично його не отримують (на відміну від колишнього «перша організація забирає»); `GITHUB_ACCESS_TOKEN_ORG_ID` більше не читається. Неповна група `GITHUB_APP_*` не валить старт: App вимкнено, діагностика каже, чого бракує, токени працюють. Без App, без env-токена і без Platform інтеграція все одно встановлюється — щоб організації могли підключити токени.
- **Обрізання встановлень (баг).** На 404 від GitHub токен-підключення не чіпається ніколи (404 нічого не каже про рядок). Рядок App видаляється, лише коли на нього не посилається жоден репозиторій чи підключення проєкту; інакше він позначається `provider_metadata.attention = 'not_found'` (сторінка показує «потребує уваги»), а позначка знімається, щойно встановлення знову відповідає. Сховище отримало `installations.usage` і `installations.setProviderMetadata`.

- **Видалення підключення, яким користуються Factory (доповнення).** Замість глухого кута 409: `GET /web/github/connections/:id/usage` каже, від яких Factory відв'язується підключення і що буде з кожним репозиторієм — перейде на інше підключення організації, яке його бачить (App або токен; збіг за числовим id репозиторію GitHub з живого переліку кожного підключення), або відв'яжеться, і Factory перестане його бачити. Діалог «Видалити» показує це простими словами й кнопку «Видалити й перенести» / «Видалити й відв'язати». `DELETE …?confirm=1` робить саме це в одній транзакції сховища (`installations.removeMovingRepositories`): репозиторій переходить на інше встановлення (або на рядок, який там уже є), його зв'язки з проєктами — на підключення того проєкту до цього встановлення (створюється за потреби), id зв'язку й сесії лишаються; решта відв'язується тим самим кодом, що й «прибрати репозиторій» (`unlinkProjectRepositoryRows`), після чого видаляються рядок встановлення і його токен; аудит `factory.integration.connection_removed` з тим, що перенесено й відв'язано. Сесії зв'язків, що відв'язуються, зупиняються до транзакції, як і при звичайному відв'язуванні. `DELETE` без `confirm` і далі відповідає 409 — тепер із тим самим переліком, — тож старі клієнти нічого не видалять мовчки.

**Наслідки.**
- Після оновлення живий рядок works-yura (`provider_metadata = {}`, id = акаунт env-токена) працює, як і раніше, через запасний токен — і з увімкненим App теж; його можна перевести на збережений токен кнопкою «Замінити токен».
- Ризик збігу чисел: id акаунта (токен) і id встановлення App — з різних послідовностей GitHub; якщо вони колись збіжуться в одному сервері, рядок із таким id обслуговуватиметься токеном. Вважаємо практично неможливим; не варте зміни формату `external_id`, на якому тримаються всі посилання.
- ADR-0032 щодо GitHub-токена (ідентифікатор `token:<orgId>`, міграція env-токена в організацію, «запасного токена немає») не реалізовано і замінено цим рішенням: id лишився id акаунта, бо на ньому вже тримаються репозиторії й підключення проєктів, а env-токен лишився запасним за прямою вимогою людини.

**Альтернативи.** Лишити один режим на сервер — відкинуто: це і є проблема. Два об'єкти інтеграції (App і токен) з однаковим id `github` — відкинуто: фабрика тримає одну інтеграцію на id, а сховище й правила розраховані на одну. Токен у `integration_connections` організації (як ClickUp) — відкинуто: один рядок на організацію, а потрібно кілька токенів; і виклики не знають організації. Префікс `token:` у `external_id` — відкинуто: `Number(externalId)` використовується по всьому коду й у збережених рядках.
