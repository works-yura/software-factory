# 0048. Хости пристроїв і пісочниці за можливостями; окрема пісочниця перевірки

Дата: 2026-11-15 · Статус: запропоновано (лише дизайн) · Продовжує [ADR-0026](0026-env-files-and-sandbox-stages.md) (стадії й команди налаштування), [ADR-0039](0039-local-environment-template-mirrors-and-session-work.md) (дзеркала, чекаут), [ADR-0041](0041-agents-run-as-a-separate-macos-user.md) (агент — окремий користувач), [ADR-0044](0044-harness-modules.md) (модулі), [ADR-0045](0045-repository-cache-and-session-work-are-replaceable-ports.md) (порти шаблону)

## Контекст

**Що потрібно.** Проєкти клієнтів — увесь спектр: мобільні застосунки на Flutter, сервери, веб-адмінки. Близько 80% перевірок застосунку (функціональність, верстка, відео для рев'ю) можна зробити на Android, тобто на Linux (Docker, віддалений Linux). Близько 20% — специфічне для iOS (дозволи, можливості платформи) і потребує macOS: зараз локальний Mac mini, згодом віддалений Mac. Хост може бути локальним або віддаленим; бажано, щоб **той самий код** (хаб + agent-device) працював або в процесі сервера, або окремим процесом на іншій машині. Пісочниця, що пише код, і пісочниця, що перевіряє, мають бути різні: перевірка стартує з чистого коміту (як CI), запускає тести й сценарії, записує відео й скриншоти, і автор не може на неї вплинути.

**Що є зараз (факти).**
- **Пристрої** (`packages/device`). `DevicePlatform = 'ios' | 'android'`; `DeviceHostSummary.kind` — лише `z.literal('local')` (`src/contracts.ts`; коментар: SSH, EAS і Simlock-хости прибрано при перенесенні). Інтерфейс `DeviceHost` (`src/server/DeviceHost.ts`) уже загальний: прапорець `remote?` (втрата з'єднання не закриває сесії), `upstream()` для проксі хаба на кілька адрес, `DeviceOperations.agentEndpoint` для daemon на пристрій, `endsDevices` для хмарних хостів. Єдина реалізація — `createLocalDeviceHost` (`LocalDeviceHost.ts`): запускає `expo-device-hub` на `127.0.0.1`, на не-macOS — з `--platform android`; iOS недоступний поза `darwin`. Кілька хостів уже підтримує `makeDeviceServiceWithHosts` (`DeviceService.ts`; тест `DeviceMultiHost.test.ts`: однакові серійники на різних хостах, збій одного не валить інших). `DeviceHubProxy.ts` пропускає до хаба лише білий список шляхів.
- **Як агент дістається пристрою.** `AgentDeviceTarget.ts` пише файл кінцевої точки (`daemonBaseUrl`, токен) у стан сервера; лаунчер `AgentDeviceShim.ts` приймає лише loopback-адресу daemon (`127.0.0.1`/`localhost`/`[::1]`). Тобто сьогодні пісочниця мусить бути на тій самій машині, що й пристрій. Запис відео вже є: `agent-device record start --scope device out.mp4` (`agentTools.ts`).
- **Підключення на сервері** (`packages/server/src/device.ts`): маршрути `/web/device/*` під дозволом `session.write`, WebSocket хаба — через той самий вхід. `apps/server/src/mastra/index.ts` вмикає пристрої лише на власній машині (`ownMachine`, ADR-0040).
- **Браузер уже є**: `@mastra/agent-browser` за `FACTORY_BROWSER=agent-browser` — headless Chromium **на хості сервера, не в пісочниці**, один браузер на тред (`apps/server/src/mastra/index.ts`). Playwright — лише в e2e самого Factory (`apps/ui/e2e`), не для проєктів.
- **Пісочниці** (`packages/sandbox`, `docs/features/sandbox/design.md`): лише локальна (`FACTORY_SANDBOX_PROVIDER` — тільки `local`); інтерфейс Mastra `FactorySandbox` (`create`, необов'язкові `template`, `builds`, `settings`) і `CallbackFactorySandbox` для будь-якого `MastraSandbox`. Порти `RepositoryCache` / `SessionWorkStore` (ADR-0045) — вже заміна для не-локального кешу. Агент працює від імені `FACTORY_AGENT_USER` (ADR-0041); браузер, пристрої й MCP — ще від імені сервера.
- **Тулчейни**: сервер бере node з nvm (`scripts/mac-mini/start-server.sh`), Flutter агентові ставить fvm (`scripts/mac-mini/isolation/2-system.sh agent-mobile-tools`); проєкт ніде не оголошує, які тулчейни й версії йому потрібні.
- **Upstream** (`temp/mastra-fork`): `workspaces/docker/src/factory-sandbox.ts` і `workspaces/e2b/src/factory-sandbox.ts` реалізують `FactorySandbox` з шаблонами й збірками; `daytona`, `modal`, `apple-container` — лише `MastraSandbox` (через колбек). `workspaces/e2b-desktop` — `E2BDesktopSandbox extends E2BSandbox`: повний Linux-десктоп, можливість `computer` (screenshot, миша, клавіатура → інструменти `mastra_workspace_computer_*`) і noVNC-потік. **Окремої пісочниці перевірки в upstream немає**: є лише фаза самоперевірки (вердикт `factory_record_review_verdict`; `source_control_create_change_request` відмовляє до вердикту й закриває PR, якщо голова інша) і дошка рев'ю, що звіряє `git rev-parse HEAD` з головою MR — обидва в тій самій пісочниці, що й автор. Менеджера тулчейнів в upstream теж немає.
- **Дошка «Розробка»**: `intake → triage → planning → execute → pr-review → done` (`docs/features/work-board/design.md`); `execute` відкриває PR і переносить картку в Рев'ю.

## Рішення

**1. Хост — це можливості + вид.** Запис хоста (`DeviceHostSummary`): `kind: 'local' | 'remote'` і `capabilities`: `ios`, `android`, `browser`, `desktop`, `video` (список відкритий; `ios`/`android` лишаються `DevicePlatform` для пристроїв). Можливість обслуговує драйвер:
- `ios`/`android` — нинішній хаб + agent-device (`DeviceHost`);
- `browser` — `agent-browser` (те, що вже є), але як хост у списку, а не прапорець сервера;
- `desktop` — драйвер computer-use (screenshot/миша/клавіатура + потік), перший — `E2BDesktopSandbox` з upstream. Це **ще один хост у тому самому списку** (весь десктоп: браузер, Android Studio, будь-який GUI), не окремий механізм;
- `video` — хост уміє записувати (agent-device `record`, відео браузера чи десктопа).

Агент отримує інструменти за можливостями вибраного хоста; панель пристроїв показує потік хаба або noVNC десктопа.

**2. Віддалений хост — той самий код окремим процесом.** `factory-device-host` — демон, що запускає ту саму `createLocalDeviceHost` (і драйвер браузера) на іншій машині й **сам підключається до сервера** (вихідне WebSocket/TLS-з'єднання, на хості не треба відкривати портів): автентифікація токеном хоста, реєстрація summary й можливостей, heartbeat, статус у `DeviceHostStatus`. На сервері його представляє `RemoteDeviceHost` (`remote: true`), що реалізує `DeviceHost` і тунелює через з'єднання запити хаба (`upstream()`), WebSocket потоку й RPC agent-device. Він додається в `makeDeviceServiceWithHosts` поруч із локальним; `DeviceHubProxy` і його білий список не змінюються. В процесі сервера — як сьогодні, без демона.

**3. Пісочниця дістається пристрою лише через сервер.** Кінцева точка agent-device, яку отримує пісочниця (`AgentDeviceTarget`), — адреса **сервера** з коротким токеном на сесію й пристрій, а сервер пересилає її на хост (локальний daemon чи тунель). Перевірку «тільки loopback» у `AgentDeviceShim` замінює «loopback або пересилання Factory». Так місце пісочниці й місце пристрою незалежні: Docker-пісочниця на Mac mini керує Android-емулятором на віддаленому Linux, локальна — симулятором iOS на віддаленому Mac. Браузеру/десктопу, що відкриває dev-сервер пісочниці, потрібен шлях до порту пісочниці: локально — localhost, Docker — проброс порту, хмара — публічна адреса провайдера; це теж пересилає сервер, а не пряма мережа між хостом і пісочницею.

**4. Пісочниці коду — види за тим самим інтерфейсом.** `local` (сьогодні), `docker` (перенести `workspaces/docker` з upstream), `remote` (Linux VM чи хмара: E2B, Daytona… через `FactorySandbox` / `CallbackFactorySandbox`). Пісочниця теж оголошує можливості: ОС (`linux`, `macos`), тулчейни (`node`, `flutter`, `xcode`, `android-sdk`…), `kvm`. Порти ADR-0045 — для не-локальних кешів і сховищ роботи. `FACTORY_SANDBOX_PROVIDER` перестає бути одним рядком: Factory має список пісочниць організації, як хости.

**5. Вимоги оголошує фаза й картка, Factory вибирає.** Налаштування Factory задають типові вимоги репозиторію (напр. Flutter-застосунок: `sandbox: linux+flutter`, `devices: android`); фаза додає свої (збірка — лише пісочниця; перевірка — ще пристрої й `video`); картка може додати (`ios` для iOS-специфічної задачі). Factory вибирає пісочницю й хост, що покривають вимоги (перевага — локальні й уже прогріті). **Нічого не підходить — запуск не стартує, картка в «Потребує вас» з назвою відсутньої можливості.** Тихої заміни немає: iOS-задача не перевіряється на Android, перевірка з `video` не йде без запису.

**6. Пісочниця перевірки — окрема.** Новий вид пісочниці `verification`:
- стартує з **конкретного запушеного коміту** гілки картки (чекаут з дзеркала ADR-0039 за SHA), у власній теці, не в теці картки; після прогону знищується;
- автор не має до неї інструментів; результат записує Factory з SHA, а новий пуш робить його застарілим;
- що запускати — визначення перевірок у налаштуваннях Factory (команди тестів, лінтерів, збірки, сценарії пристроїв), а не лише скрипти з репозиторію, які автор може змінити; зміни тестів у диффі бачить рев'ю;
- без токена пушу й без `GH_TOKEN`, env-файли лише потрібної стадії (ADR-0026);
- артефакти — відео, скриншоти, логи, звіти тестів — вкладення картки (наявне сховище вкладень) з посиланням на SHA;
- сценарії на пристрої може вести агент перевірки (окрема сесія в контексті `verify`, без запису в репозиторій), але вердикт «пройдено» дають команди перевірки, а не слова агента.

**Місце в дошці.** Необов'язкова фаза «Перевірка» (`verify`) на «Розробці» між `execute` і `pr-review`: збирач пушить і переносить картку в `verify`; провал повертає в `execute` зі звітом і артефактами (як колись самоперевірка); успіх — у `pr-review`, де рецензент бачить відео. Та сама пісочниця перевірки доступна дошці рев'ю для чужих PR.

**7. Android-емулятору потрібна апаратна віртуалізація.** Docker на Mac mini не має KVM, тож емулятор у Docker-пісочниці там не працює. Варіанти: (а) віддалений Linux-хост з KVM; (б) емулятор нативно на Mac (HVF) — нинішній `LocalDeviceHost`, а Docker-пісочниця керує ним через сервер (пункт 3), `adb install` — теж через пересилання. Хмарні пісочниці (E2B — Firecracker; Daytona) — підтримка KVM не перевірена, тому `android` їм не приписується, доки не перевірено.

**8. iOS — лише на macOS-хостах**: Mac mini зараз, віддалений Mac пізніше (той самий демон). Ізоляція агента (ADR-0041) — на кожному хості: збірки, `agent-device`, хаб і браузер — від імені агента, не власника машини.

**9. Безпека.** Віддалений хост і хмарна пісочниця бачать код і збірки клієнта, дані на екранах і env-файли.
- Хости й пісочниці — **ресурси організації** (як підключення); реєструє й відкликає лише `org.manage`; приватні для однієї Factory — пізніше.
- Токен хоста — на один хост, зашифрований, відкликається; хост підключається сам, вхідних портів немає; кожна сесія — свій короткий токен на пристрій.
- Білий список шляхів хаба лишається на сервері й не довіряє хосту.
- Хмарна пісочниця чи віддалений хост на репозиторії клієнта — лише зі згоди клієнта (як моделі OpenCode, ADR-0043); налаштування Factory показує, де фізично виконується код.
- Секрети — як зараз: env-файли пишуться на старті сесії, не в образ шаблону; git-токен — на операцію.

## Наслідки

- `DeviceHostSummary.kind` розширюється, додається `capabilities`; клієнти UI вже показують список хостів.
- Пісочниця й пристрій розходяться по машинах: з'являється мережевий тунель і затримка потоку; локальний випадок не змінюється.
- Перевірка подвоює витрати на збірку (окремий чекаут і встановлення залежностей); зменшують прогрітий шаблон (ADR-0039) і кеші.
- Вибір «що де запускати» стає явною помилкою, а не прихованою поведінкою; людина бачить, якої можливості бракує.

## Альтернативи

- **Один десктоп-хост на все** (e2b-desktop чи VM з GUI для браузера, Android Studio й тестів). Просто, але iOS там немає, емулятор без KVM не працює, computer-use по пікселях повільніший і менш надійний за agent-device і браузерні інструменти. Лишається одним із хостів (`desktop`), не єдиним.
- **Емулятори всередині пісочниці коду.** Кожна пісочниця тягне SDK, образ емулятора й KVM; автор має доступ до пристрою перевірки; на Mac у Docker не працює зовсім. Відкинуто: пристрої живуть на хостах.
- **Перевірка в пісочниці автора** (як самоперевірка upstream). Автор може змінити робоче дерево, залишити процеси чи файли між ходами; результат не прив'язаний до коміту. Відкинуто.
- **Пряма мережа між пісочницею й хостом** (VPN, `adb connect` по мережі). Обходить авторизацію й білий список сервера. Відкинуто на користь пересилання сервером.

## Відкриті питання / варіанти

- **KVM** в E2B і Daytona (вкладена віртуалізація для емулятора); вкладена віртуалізація на Apple Silicon M3+ у Docker/VM — перевірити на конкретному Mac mini.
- **Запис відео**: agent-device `record` (вже є), `xcrun simctl io recordVideo`, `adb screenrecord` (ліміт 3 хв), scrcpy, запис Playwright, запис VNC-потоку — що брати для кожної платформи й де зберігати великі файли.
- **Вартість** хмарних пісочниць і десктопів (E2B зберігає призупинені VM і бере за них), віддаленого Mac.
- **Хто оголошує перевірки**: лише налаштування Factory чи ще файл у репозиторії (зручніше, але його змінює автор).
- **Тулчейни проєкту** (не рішення, людина подумає пізніше). Зараз — nvm і fvm на Mac mini, оголошення немає. Варіанти:
  - **mise** (https://mise.jdx.dev): версії node/flutter/java/android-sdk/ruby (cocoapods)/python з `mise.toml` чи `.tool-versions` репозиторію, env і задачі, `mise.lock` з контрольними сумами; той самий файл працює на Mac, у Docker і на віддаленому Linux; стадія налаштування (ADR-0026) запускала б `mise install`. Не перевірено: якість бекендів для Flutter (asdf/vfox-плагін) і Android SDK (у реєстрі є, але плагіни сторонні), чи покриває lockfile ці бекенди контрольними сумами.
  - **devcontainers**: образ на проєкт, добре для Linux-паритету, але лише Docker, без macOS/iOS, важкі образи.
  - **Nix**: найкраща відтворюваність і ланцюжок постачання, але висока ціна входу, Flutter/Android на macOS незручні, Xcode поза Nix.
  - Ланцюжок постачання для будь-якого варіанту: закріплені версії й контрольні суми, встановлення від імені агента (ADR-0041), спільний кеш тулчейнів — лише для читання агентам.
- **Відкриті компоненти, які варто розглянути** (варіанти, не рішення): Playwright (браузер, вбудований запис відео); `budtmo/docker-android` (емулятор у Docker з noVNC, потребує `/dev/kvm`); Appium (кросплатформна автоматизація; agent-device має прапорці для Appium і AWS Device Farm — з'ясувати, що з цього працює); Maestro (сценарії UI у YAML з відео, підтримує Flutter) і Patrol / `integration_test` для Flutter; Tart (одноразові macOS-VM на Apple Silicon для віддаленого Mac — перевірити ліцензію).

## План (кожна фаза окремо придатна до використання)

1. **Можливості й вибір — локально.** `capabilities` і `kind` у хостах; можливості локальної пісочниці; вимоги в налаштуваннях Factory, фазі й картці; вибір з голосною відмовою в «Потребує вас»; UI показує можливості хостів. Нічого віддаленого, але правило «нема — не стартує» працює вже на Mac mini.
2. **Пісочниця перевірки — локально.** Чекаут за SHA з дзеркала в окрему теку, команди перевірок з налаштувань, запис відео agent-device, артефакти у вкладеннях картки, фаза `verify` на «Розробці». Найбільша користь без нової інфраструктури.
3. **Пересилання кінцевої точки agent-device через сервер.** Токен на сесію, shim приймає адресу Factory. Передумова для будь-якої не-локальної пісочниці; локально перевіряється з тією самою пісочницею.
4. **Docker-пісочниця** (перенесення `workspaces/docker`): Linux-тулчейни, Android-пристрій — нативний емулятор Mac через пункт 3. Покриває ~80% перевірок ізольовано.
5. **Демон віддаленого хоста.** Спершу Linux з KVM (Android, браузер, відео), потім віддалений Mac (iOS) тим самим демоном; реєстрація хостів організації.
6. **Хмарні пісочниці й десктоп** (E2B/Daytona, `E2BDesktopSandbox` як хост `desktop`) — після перевірки KVM, вартості й згоди клієнтів.
