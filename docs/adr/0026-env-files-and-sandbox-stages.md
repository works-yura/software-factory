# 0026. Env-файли репозиторіїв і стадії пісочниць

Дата: 2026-11-11 · Статус: прийнято · Коміти: `6d426f1e`, `27e54d66`

**Контекст.** Скрипти проєктів і мобільні збірки читають конфіг не з оточення процесу, а з **файлів**: `.env.development`, `.env.staging`, `.env.production`, `apps/mobile/.env`, `ios/Config.xcconfig`, flavor-конфіги. Пісочниця Factory отримувала лише один плаский набір змінних Factory як оточення процесу (`packages/sandbox/src/sandbox-env.ts`: `runtime` — кожній команді, `build` — збиранню шаблону й командам налаштування; сховище `SandboxEnvStore`, зашифроване). Репозиторії клонуються з git, де `.env*` у `.gitignore`, тож у пісочниці цих файлів немає, і `pnpm dev`/`expo`/`xcodebuild` падають або беруть чужі значення.

**Рішення.**

- **Env-файли на репозиторій.** У налаштуваннях «Середовище» кожна картка репозиторію (розгорнута шевроном) має список «Env-файли»: відносний шлях у репозиторії, стадія, вміст. Вміст шифрується тим самим `FactorySecretEncryption`, що й змінні; при старті Factory з ключем вміст, збережений відкритим текстом чи старим ключем, перешифровується (як у змінних). Таблиця `factory_sandbox_env_files` у домені `SandboxEnvsStorage` (`packages/store/src/sandbox-envs/base.ts`), один файл на шлях у межах прив'язки репозиторію (`project_repository_id`).
- **Перевірка шляху** (`sandboxEnvFilePathProblem`, одна функція для сховища, контрактів і запису в пісочницю; UI повторює її лише для підказки): відносний, без `..`, без абсолютного чи `~`, без порожніх і `.` сегментів, жодного сегмента `.git`, лише `[A-Za-z0-9._@+-]` в іменах, до 256 символів. Обмежений алфавіт робить шлях безпечним у shell, у `.git/info/exclude` і як gitignore-шаблон без екранування. Вміст — до 64 КБ, без NUL.
- **Стадії:** `development` | `staging` | `production` — у кожного env-файла **і** кожної змінної Factory. Наявні змінні мігрують у `development` (адитивна колонка `stage` з `DEFAULT 'development'`). Розділення `runtime`/`build` лишається як було. Налаштування Factory «Staging у пісочницях» (`factory_sandbox_env_settings`, типово лише `development`) вмикає staging. Лише на рівні Factory: фази дошки не мають власного оточення пісочниці (картка ділить одну теку з усіма своїми сесіями, ADR про теки карток), тож перемикати стадію на фазі означало б переписувати файли посеред картки — поки не робимо.
- **Production ніколи не потрапляє в пісочницю агента.** Ні перемикача, ні винятку: `resolve()` навіть не розшифровує production-рядки, а запис у пісочницю додатково відкидає їх. Зберігати production-змінні й файли можна (щоб конфіг жив в одному місці), але збирати й деплоїти production треба **поза пісочницями агентів — у CI**. Надалі можливий механізм «запиту секрету»: агент просить одне значення для однієї дії, людина підтверджує, значення передається інструменту без показу моделі. Це окреме рішення.
- **Ревізії.** Змінні, файли й стадії ділять одну ревізію (`factory_sandbox_env_revisions`): будь-який запис її змінює, тож наявний механізм оновлення (`attachSandboxEnvRefresh` + `CachedSandboxEnvs`, подія `factory.sandbox-env` між репліками) підхоплює й файли. Build-ревізія змінюється лише тоді, коли зміна торкається Build-змінних (змінна з build змінила стадію; перемкнено стадію, у якій є Build-змінні). Файли build-ревізію не чіпають.
- **Матеріалізація** (`packages/sandbox/src/sandbox-env-files.ts`, підключено в `packages/harness-mastra/src/workspace.ts`): у старті сесії **після** клонування й синхронізації гілки кожного репозиторію і **перед** його командою налаштування (`runSessionSetup` для основного, `runSessionEnvironmentSetup` для решти) Factory пише файли увімкнених стадій у копію цього репозиторію:
  - режим 0600 (umask 077, `chmod 600`, запис через тимчасовий файл і `mv`);
  - шляхи — у блок між маркерами Factory у `.git/info/exclude`, тож `git add -A`, `commitAll`, `git status` і знімок змін їх не бачать;
  - шлях, який git уже відстежує (`ios/Config.xcconfig`), позначається `skip-worktree`: справжні значення не з'являються в diff і не комітяться; при видаленні — `--no-skip-worktree` і відновлення закоміченої версії;
  - список записаного — у `.git/info/factory-env-files`; наступний запис видаляє те, що зникло або чию стадію вимкнули;
  - теку, що через symlink веде за межі копії, пропущено; шляхи й вміст передаються аргументами, ніколи в тексті скрипта;
  - помилка запису логується й не зупиняє старт.
  Після редагування наступна команда агента (через `ensureRunning`) бачить нову ревізію, перечитує й переписує файли в усіх копіях, які записав старт. Команди самого запису йдуть повз цю перевірку (`AsyncLocalStorage`), тож немає взаємоблокування.
- **Збирання шаблонів env-файлів не отримують**: образ шаблону кешується й ділиться між сесіями, вшивати в нього секрети не можна. Файли з'являються під час старту сесії, до команди налаштування сесії. Команда налаштування, що виконується в збиранні образу, їх не бачить — їй лишаються Build-змінні.
- **Видимість.** Агенти в пісочниці **можуть читати** ці файли — для того вони й існують; агенту, якому файл не потрібен, його не варто вмикати на цій стадії. Переглядач файлів у UI (`packages/api/src/fs.ts`) і далі ховає `.env*` та все ігнороване, а також усе зі списку `factory-env-files` (навіть відстежуваний шлях). Diff ходу й знімок файлів сесії їх не містять (exclude + `skip-worktree`).
- **Доступ (API `/web/factory/projects/:id/sandbox-env-files`, `/sandbox-stages`):** будь-який учасник організації бачить шляхи, стадії й розміри; вміст (`GET …/:fileId`), додавання, редагування, видалення env-файлів і зміна стадій — лише адміністратор організації (у локальному режимі без авторизації — оператор). Відповіді `no-store`; без ключа шифрування додавання й редагування відмовляються (409), видалення дозволене. Змінні, як і раніше, лише для запису: значення не повертається нікому. Аудит — `factory.sandbox_env.{stages_updated,file_created,file_updated,file_deleted}` без вмісту (ці дії треба зареєструвати у WorkOS Audit Logs).
- **UI** (дизайн-система, ADR-0014; en + uk): у картці репозиторію — таблиця шлях / вміст (замаскований) / бейдж стадії / дії; діалог з полем шляху, вибором стадії й вмістом, прихованим за замовчуванням (кнопка «Показати» для адміністратора, «Замінити» — без читання старого). Біля «Змінні середовища» — перемикач «Staging у пісочницях» і нагадування, що production туди не потрапляє; у змінних — колонка й вибір стадії. Доповнення: змінні додаються через «Додати або імпортувати» (форма або вміст `.env` з перетягуванням / вибором файла, перегляд перед збереженням), env-файл можна заповнити з файла; див. [settings/design.md](../features/settings/design.md#розділ-середовище-змінні-й-env-файли).

**Наслідки.**

- `.env.staging` чи `ios/Config.xcconfig` з'являються в копії до `pnpm i`/`pod install`, змінюються з наступною командою після редагування і не потрапляють у PR.
- Файли, що лишилися від відв'язаного репозиторію, не пишуться (немає копії), але рядки залишаються, поки їх не видалити.
- Агент, що виконує `git checkout` іншої гілки, де відстежуваний env-шлях відрізняється, може натрапити на конфлікт із `skip-worktree`; наступне оновлення запише файл знову.
