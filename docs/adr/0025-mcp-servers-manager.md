# 0025. MCP-сервери: менеджер, доступ і політика інструментів

Дата: 2026-11-11 · Статус: прийнято · Коміти: `a30f6047`, `a72d9f76`, `62bc3d5d`, `33f1bb50`, `7b9c7a55`, `928377af`; каталог і форма — `81645abb`, `d0e36459`

**Контекст.** Агентам потрібні зовнішні інструменти: читати продакшн-базу клієнта (Syncta — Firestore), згодом логи, Sentry тощо. Готові рішення — MCP-сервери (MCP Toolbox for Databases від Google, Firebase MCP, Observability MCP). Досі сесії отримували лише власний MCP-сервер Factory, а підключити чужий не можна було ніде. Людина хоче два окремі налаштування: (1) чи має картка доступ до сервера; (2) що дозволено з його інструментів — і нічого не забороняти за замовчуванням.

**Рішення.** Розділ «MCP-сервери» у налаштуваннях — менеджер MCP усередині Factory, перенесений з upstream Mastra, а не вигаданий:

- **Перенесено з upstream:**
  - форма конфігу — збережений MCP-клієнт Mastra (`packages/core/src/storage/types.ts` `StorageMCPServerConfig`: stdio `command`/`args`/`env` або http `url`);
  - CRUD — як `packages/server/src/server/handlers/stored-mcp-clients.ts` (`/stored/mcp-clients`), у нас `/web/mcp-servers`;
  - форма Studio (`packages/playground/src/domains/mcps/components/mcp-client-create`), перебудована з частин дизайн-системи;
  - стан сервера — як `McpServerStatus` mastracode (`mastracode/sdk/src/mcp/types.ts`): підключено, кількість інструментів, помилка;
  - назви інструментів `server_tool` і підстановка `${VAR}` в аргументах — як у upstream (`MCPClient`, `mastracode/sdk/src/mcp/config.ts` `expandEnvVars`, у нас лише зі змінних самого сервера);
  - запуск — `MCPClient` з `@mastra/mcp`.
- **Додано Factory:**
  - **секрети** окремо від конфігу, зашифровані (`FactorySecretEncryption`), назад не віддаються — лише їхні імена; секретні файли (ключ сервісного акаунта, `tools.yaml`) пишуться у приватну тимчасову теку на час роботи сервера;
  - **доступ:** прив'язки сервера до Factory з необов'язковими дошками й фазами (`McpServerAssignment`); новий сервер не отримує ніхто, поки його не призначили;
  - **політика інструментів:** типова для сервера плюс перекриття для кожного інструмента — `allow` / `ask` / `deny`, за замовчуванням `allow`;
  - **маскування персональних даних** у результатах (типово увімкнено) — той самий модуль, що для логів (`@factory/capabilities` `redactDeep`);
  - **журнал:** кожен виклик інструмента — подія `factory.mcp_server.tool_called` (сервер, інструмент, сесія, результат; без аргументів і відповідей).
- **Хаб (`McpServerHub`)** — одна точка, через яку проходять усі інструменти: сесія отримує сервери, призначені її картці; вони стартують з першим запитом інструментів і зупиняються, коли сесія простоює (15 хв), при `release` чи вимкненні сервера Factory. Окремого постійного процесу-менеджера немає. Mastra отримує інструменти в процесі; Claude Code і Codex — з MCP-ендпоінта Factory (той самий `createSession`), тож політика й маскування однакові для всіх.
- **`ask`:** Mastra — підтвердження інструмента (`requireApproval`); Claude Code — `askEachTime` для `mcp__factory__<server>_<tool>` (картка без людини паркується й чекає, як інші питання); Codex не вміє питати посеред ходу — йому такі інструменти не видаються. `deny` — інструмент не видається нікому.
- **Каталог — офіційний формат MCP Registry `server.json`** ([схема 2025-12-11](https://static.modelcontextprotocol.io/schemas/2025-12-11/server.schema.json)), як це роблять MCP Registry, Docker MCP Toolkit і Smithery: кожен вбудований сервер — файл `packages/server/src/mcp-servers/catalog/<id>.server.json` (пакет і зафіксована версія, оголошені вхідні дані: `environmentVariables`, `packageArguments` з `isRequired`/`isSecret`/`default`/`choices`/`format`) плюс маленький оверлей Factory `<id>.factory.json`: назви й описи українською/англійською, способи запуску (`variants`: аргументи й які вхідні дані показати) і які вхідні дані заповнюються з того, що організація вже має (`credential: google-cloud-account`, `suggest: google-cloud-project`). Форма налаштувань будується з них — у коді UI жодної назви поля. Пізніше каталог можна підтягувати з `registry.modelcontextprotocol.io`, оверлеї лишаться нашими.
- **Облікові дані беруться, а не вставляються.** Вхідні дані типу «акаунт Google Cloud» — вибір з акаунтів «Логи і креші»: інтеграція Firebase позичає їх через порт `CredentialProvider` (`@factory/capabilities`), сервер тримає лише посилання `{kind, id}`, а ключ читає лаунчер у момент запуску й пише в приватний тимчасовий файл. Проєкт Google Cloud підказується з прив'язки Factory.
- **Пакети зафіксовані:** запис каталогу запускає встановлений пакет із `node_modules` тим самим Node, `npx` останньої версії ніколи; версія з `server.json` мусить збігатися з установленою, інакше запуск падає явно. Перший запис — «База даних (MCP Toolbox)» (`@toolbox-sdk/server` 1.16.0, Apache-2.0; npm-обгортка над бінарником платформи) з трьома способами: Firestore (`--prebuilt firestore`), PostgreSQL (`--prebuilt postgres`), власний `tools.yaml` (`--tools-file`).
- **Власний сервер** — для всього, чого немає в каталозі: «Локальна команда» (команда, аргументи, змінні й секретні змінні) або «Адреса» (URL, заголовки й секретні заголовки).
- **Ідентифікатор** утворюється з назви й живе в «Додатково»; розділ — у групі «Агент» навігації налаштувань.
- **stdio-сервер бачить лише свої змінні** плюс `PATH`/`HOME`, а не оточення сервера Factory.

**Наслідки.** Нова база чи сервіс — новий сервер у налаштуваннях (або запис каталогу: `server.json` + оверлей і зафіксований пакет), без коду інтеграції. Сервери, збережені з першими пресетами, переносить міграція `mcpServers.presetsToCatalog.v1`. Лише читання гарантує насамперед роль у джерелі (Cloud Datastore Viewer), політика `deny` для інструментів, що пишуть, — другий рівень. Сервери живуть у процесі сервера Factory: на кількох репліках кожна запускає свої для своїх сесій.

**Альтернативи.**
- Окремий шлюз MetaMCP або Docker MCP Gateway — відкладено: це ще один сервіс зі своєю базою, а доступ за дошкою й фазою — логіка нашого домену. Коли Factory стане сервісом на кількох серверах, шлюз можна підкласти під хаб як спосіб запуску, не змінюючи налаштувань.
- Віддавати Claude Code сервери напряму в його `mcpConfig` — відкинуто: тоді секрети йдуть у конфіг CLI, а маскування, `deny` і журнал довелося б робити окремим проксі.
- Свій ORM чи інтеграцію для кожної бази — відкинуто на користь MCP Toolbox.
- Пресети, зашиті в код (перша версія), — замінено каталогом: форма з сирими назвами змінних і вставлянням ключа була ні універсальною, ні персоналізованою.
