# 0039. Локальний шаблон середовища: дзеркала репозиторіїв, спільні сховища пакетів і робота сесій у дзеркалі (присипляння)

Дата: 2026-11-13 · Статус: прийнято, зроблено (крім «Відкладено») · Коміти: `6db34056`, `5edce7d7`, `b2d0455d` і наступні в гілці · Втілює пропозицію «Присипляння замість паузи» з [backlog](../changes/backlog.md#пісочниці) · Продовжує [ADR-0026](0026-env-files-and-sandbox-stages.md)

**Контекст.** Локальна пісочниця (Mac mini, `LocalFactorySandbox`, папки під `/Volumes/dot/factory-sandboxes`, диск HFS+ — без APFS clonefile, жорсткі посилання працюють) не мала нічого з того, що віддалені провайдери отримують від збірки середовища (`factory-environment-build`). Кожна сесія клонувала кожен репозиторій Factory з GitHub з нуля (`git clone --depth=1`, `materializeRepo`): у Syncta п'ять репозиторіїв, на повільному GitHub один клон — 140–167 с, розгортання ~3 хв до першої відповіді агента; потім установлення залежностей кожного разу. Папка сесії була єдиним місцем її роботи: видалена папка (закриття картки, видалення, збій) — втрачені незапушені коміти й незакомічені зміни.

## Як працює віддалений шаблон (те, з чим маємо паритет)

- **Що будує.** `builds.start(ctx, settings)` провайдера (E2B, платформа Mastra) збирає образ: кожен репозиторій середовища клонований на голові гілки за замовчуванням, виконані команди налаштування (з Build-змінними), маркери налаштування (`.mastra-sandbox/…`) записані. Голови фіксує Factory (`resolveHead` з записаних `lastBuildHeads`), ідентичність шаблону — голови + `environmentBuildInputs` (налаштування, репозиторії й порядок, команди, робоча папка, ревізія Build-змінних).
- **Коли перебудовується.** Три тригери, усі через workflow `factory-environment-build` (`build-runner.ts`, `build-workflow.ts`): «Зібрати зараз» (`manual`, будує завжди), cron проєкту (`schedule`, core `Schedules`, `build-schedule.ts`) і пуш у гілку за замовчуванням репозиторію середовища (`push`, вебхук, з дебаунсом). `schedule`/`push` пропускають збірку, коли остання `ready` і ні голови, ні входи не змінились. Лізинг старту (`claimBuildStart`, 10 хв з поновленням) — дві репліки чи два тригери не стартують дві збірки; збірка, що вже йде, не дублюється (`in_progress`).
- **Як сесія стартує з нього.** Сесія бере закріплений шаблон (`activeTemplateId`), чекаут уже є → `materializeRepo` його не чіпає; `checkoutSessionBranch`/`syncEnvironmentRepository` дотягують лише дельту (fetch базової гілки чи гілки сесії); маркер налаштування збігається → команда налаштування пропускається.
- **Застарілість, статус, історія.** Рядок проєкту: `lastBuildId`, `lastBuildAttemptedAt`, `lastBuildHeads`, `lastBuildInputs`, `activeTemplateId/Heads`. UI «Середовище › Шаблон» (`BuildStatusBlock`, `BuildHistoryBlock`, `BuildTriggersBlock`) показує живий статус останньої збірки (`builds.get`), історію (`builds.list`: початок, кінець, помилка, журнал), тригери; усе вмикається можливістю провайдера `capabilities.builds`.
- **Збої.** Невдалий `builds.start` очищає `lastBuildId`; збірка `failed`/`unknown` не закріплюється, сесії йдуть зі старим шаблоном; без шаблону сесія клонує сама (повільний шлях). Помилки маскуються (`redactCredentials`, `maskSandboxEnvValues`).

## Паритет: що отримує локальний провайдер

| Віддалений шаблон | Локально (це рішення) |
| --- | --- |
| Образ зі склонованими репозиторіями | Дзеркало `git` на кожен репозиторій на сервері; сесія — `git clone --local` (жорсткі посилання) з дзеркала, повна історія |
| Збірка за тригерами `manual`/`schedule`/`push`, лізинг, пропуск незміненого | Той самий workflow і ті самі тригери: `LocalFactorySandbox.builds` реалізує `start/get/list` |
| Сесія дотягує лише дельту | Дешевий `git fetch` дзеркала (вікно свіжості 15 с, лок на репозиторій) перед клоном, далі звична логіка гілки |
| Залежності встановлені в образі | Збірка виконує команди налаштування в шаблонній копії зі спільними сховищами пакетів на тому ж томі; установлення в сесії бере пакети локально (див. нижче) |
| Статус/історія збірок у UI | Ті самі компоненти: записи збірок на диску, журнал — коміт і тривалість на репозиторій, помилки |
| Збій → старий шаблон або клон сесією | Немає/зламане дзеркало → мережевий клон як раніше, у журналі й у ході розгортання («з мережі»), збірка (або фоновий ремонт) відновлює дзеркало |
| Пауза VM зберігає роботу | Робота сесії (коміти + незакомічене) зберігається в дзеркалі після кожного ходу і перед видаленням папки; при закритті картки — ще й прихований ref на GitHub |

## Рішення

**Порти й адаптери** (як [ADR-0016](0016-intake-rules-ports-and-adapters.md)), `packages/sandbox/src/template/`:

- `RepositoryCache` — `prepare(repo)` (перевірити, оновити дельтою, повідомити джерело), `cloneInto(...)`, `refresh(repo)` (збірка), `prune(keep)`, `maintain()`. Адаптери: `LocalMirrorRepositoryCache` (дзеркала на диску сервера) і `NetworkRepositoryCache` (нічого не кешує — поведінка до цього рішення; так працюють провайдери без дзеркала).
- `SessionWorkStore` — `save(checkout, snapshot)`, `load(checkout, branch)`, `forget(repo, branch)`. Адаптери: `MirrorSessionWorkStore` (refs у дзеркалі, без мережі), `RemoteHiddenRefSessionWorkStore` (прихований ref на origin; працює зсередини будь-якої пісочниці, тож E2B/Railway підключать його без змін), `CompositeSessionWorkStore` (зберегти в усі, читати з першого, де є).
- `SessionWork` — нейтральна до провайдера служба: знімок роботи в чекауті (`snapshot`), збереження в сховища, відновлення з правилом порядку й розбіжності. Провайдер дає їй сховища; `LocalFactorySandbox` збирає локальний набір (`localTemplate`), віддалений провайдер у майбутньому — свій.

**Дзеркала.** Корінь шаблону — `$FACTORY_LOCAL_TEMPLATE_ROOT`, типово `<корінь пісочниць>/.factory-template` (той самий том, інакше жорсткі посилання неможливі). Дзеркало — `mirrors/<host>/<owner>/<repo>.git`: `git init --bare` + явні refspec `+refs/heads/*`, `+refs/tags/*`, `+refs/pull/*/head`, `+refs/factory/wip/*:refs/factory/origin-wip/*` (не `--mirror`: `fetch --prune` з `+refs/*:refs/*` стер би refs роботи сесій). URL без облікових даних; токен — лише в середовищі процесу git (`gitAuthenticationEnvironment`); `remote.origin.pushurl` вимкнено, автоматичний пуш з дзеркала неможливий. `gc.auto=0`, `maintenance.auto=false` (паки видаляє лише наша обслуговча `gc` під локом), `core.logAllRefUpdates=always` (рефлог: примусове оновлення ref роботи не губить попередній коміт). Створюється у тимчасовій папці й перейменовується атомарно — напівклон ніколи не видно як дзеркало.
- **Лок на репозиторій**: у процесі — черга (з тим самим обмеженням очікування); між процесами/репліками — `mkdir`-лок з `owner.json` (host, pid, час), поновлюється, поки операція йде; застарілий (мертвий pid на цьому хості або без поновлення довше за 10 хв) забирається. Лок тримають створення, fetch, перевірка й **реєстрація читача**; сам клон іде без лока, паралельно з іншими сесіями (fetch паків не видаляє: `gc.auto=0`). Паки видаляє лише обслуговча `gc`: вона під локом чекає, доки читачів (`<repo>.git.readers/`, з pid і часом; мертві й старші за 30 хв відкидаються) не стане, інакше пропускає цей раз. Збереження роботи лока не бере (атомарні `update-ref` з очікуваним старим значенням).
- **Сесія**: `prepare` → дзеркало є й ціле → `fetch --prune` (якщо останній був давніше 15 с; ті самі обмеження зависання — `GIT_HTTP_LOW_SPEED_*`, повтори лише для читань) → `git clone --local --branch <default>` з дзеркала (повна історія, об'єкти — жорсткі посилання на незмінні пак-файли; клон не залежить від дзеркала, тож gc дзеркала його не ламає — тому не `--reference`/`--shared`, як пропонував backlog) → `origin` = справжній URL GitHub, `refs/remotes/origin/*` уже свіжі. Далі без змін: гілка сесії (`b770b10a`), env-файли, налаштування. Подія ходу розгортання має `source: 'mirror' | 'network'` — чат каже «клоную з дзеркала» чи «з мережі».
- **Збій**: немає дзеркала → мережевий клон як раніше + фоновий `ensure` (наступна сесія вже з дзеркала); дзеркало не пройшло перевірку → у карантин (видаляється), мережевий клон, ремонт; fetch не вдався → клон зі старого дзеркала, у журнал (гілку все одно звіряє `checkoutSessionBranch` з GitHub). Кожен перехід на запасний шлях — `console.warn` з сесією й репозиторієм і `source: 'network'` у події, не мовчки.

**Збірка середовища для локального провайдера.** `LocalFactorySandbox.builds.start` повертає `building` одразу, робота йде у фоні процесу: для кожного репозиторію — доступ (`getRepositoryAccess`), `refresh` дзеркала, перевірка, що закріплена голова (`resolveHead`) є в дзеркалі; шаблонна копія `templates/<проєкт>/<repo>` на цій голові; команди налаштування (і команда робочої області) зі спільними сховищами пакетів і Build-змінними, збій однієї — у журнал, збірка йде далі (`continueOnSetupFailure`, як у віддалених); обслуговування (`gc --auto` під локом, прибирання дзеркал). Запис збірки — `builds/<проєкт>/<buildId>.json` (статус, початок/кінець, помилка, журнал: «owner/repo @ <sha> · 4,2 с»), пульс щохвилини; `building` без пульсу 3 хв (сервер упав посеред збірки) читається як `unknown` — workflow не закріплює такий шаблон, наступний тригер будує знову. Історія — 20 останніх записів. `templateId` — `local:<projectId>`. Решта — наявний код: лізинг, пропуск незміненого, cron, вебхук, «Зібрати зараз», UI.

**Залежності: спільні сховища пакетів, не спільні `node_modules`.** Середовище кожної локальної пісочниці (і збірки) отримує `npm_config_store_dir=<корінь>/package-stores/pnpm`, `npm_config_cache=<корінь>/package-stores/npm`, `YARN_CACHE_FOLDER=<корінь>/package-stores/yarn` і `npm_config_package_import_method=clone-or-copy`. Збірка прогріває сховища, установлення в сесії не ходить у мережу. **Відкинуто:** жорсткі посилання на `node_modules` шаблону і імпорт pnpm жорсткими посиланнями (його типове `auto` на HFS+ — це вони; так сесії вже ділили inode через `/Volumes/dot/.pnpm-store`): запис сесії «на місці» у файл пакета змінює той самий inode в шаблоні й у всіх інших сесіях. `clone-or-copy` дає CoW там, де ФС уміє (APFS), і копію на HFS+ — повільніше за жорсткі посилання, але локально й без спільного стану. Копіювати `node_modules` шаблону цілком — відкинуто: та сама копія, але з ризиком несумісного стану після зміни lockfile.

**Робота сесії в дзеркалі (присипляння й відновлення).** Один механізм для «зберегти після ходу» і «присипити перед видаленням».
- **Refs** (на гілку, бо гілка — ідентичність картки й сесії; ролі картки мають свої гілки): `refs/factory/wip/heads/<гілка>` — вершина гілки; `refs/factory/wip/tree/<гілка>` — знімок незакоміченого (включно з новими не ігнорованими файлами) як коміт, батько якого — вершина. Знімок робиться через тимчасовий індекс (`GIT_INDEX_FILE`, `add -A`, `write-tree`, `commit-tree`) — робоче дерево й індекс сесії не змінюються, хуки не запускаються. Чисте дерево → ref знімка видаляється.
- **Атомарність.** Об'єкти пушаться в дзеркало (локальний шлях, `--no-verify`, без хуків) у тимчасовий ref `refs/factory/tmp/<uuid>`, далі одна транзакція `update-ref --stdin` з очікуваними старими значеннями переносить обидва refs і видаляє тимчасові; потім перевірка, що refs указують на очікувані коміти. Збій посередині лишає лише тимчасовий ref (його прибирає обслуговування), ніколи — напівзаписаний стан.
- **Коли.** Після кожного кінця запуску будь-якого харнесу (той самий хук, що `reportSessionRunEnd`; у фоні, по черзі на папку). Перед видаленням папки (закриття картки, видалення сесії, перестворення пісочниці) — синхронно; **папка видаляється, лише коли збереження перевірене**, інакше лишається, а збій іде в журнал. Закриття картки додатково **публікує** обидва refs у прихований `refs/factory/wip/…` на GitHub (`RemoteHiddenRefSessionWorkStore`; не гілка — не будить CI, не видно в списку гілок) — переживає втрату диска сервера.
- **Відновлення** на свіжому клоні, а також у чистому чекауті картки, де гілки цієї сесії ще немає (папку відбудувала інша роль); чекаут зі своїми незакоміченими змінами не чіпається: збережене в дзеркалі (`refs/factory/wip/heads/<гілка>`, інакше прихований з GitHub — `refs/factory/origin-wip/…` після fetch) > гілка на GitHub (логіка `b770b10a`) > база. Обидва є: GitHub — предок збереженого → збережене; збережене — предок GitHub → GitHub (робота вже там і пішла далі); розійшлися → **гілка = збережене** (коміти не губимо), гілка GitHub лишається в `origin/<гілка>`, людині й у журнал — «гілка розійшлася з GitHub» (подія ходу розгортання `notice: 'diverged'`). Ніколи примусового перезапису. Знімок незакоміченого повертається як незакомічені зміни (`cherry-pick --no-commit` + `reset`, 3-way, якщо вершина відрізняється); конфлікт → скасувати, лишити ref, сказати людині.
- **Прибирання refs.** Видалення сесії — refs її гілки прибираються з дзеркала (людина свідомо викинула сесію). Закриття картки — refs у дзеркалі прибираються, коли вершина гілки вже є на GitHub (у будь-якій гілці) і знімка незакоміченого немає; інакше лишаються (і є прихований ref на GitHub). Прихований ref на GitHub з часом — наступний крок.
- **Прибирання дзеркал.** Після збірки: дзеркало, якого немає в жодному маніфесті проєкту (`builds/<проєкт>/repos.json`), без refs роботи сесій і без використання 7 днів, видаляється; тимчасові refs старші за добу — теж.

**Виміри** (Mac mini, HFS+ `/Volumes/dot`, `packages/sandbox/scripts/local-template-load.ts`; «мережевий» клон — `git clone --depth=1 file://…`, тобто пакетний транспорт без інтернету, справжній GitHub лише повільніший):
- репозиторій Factory v4 (21 МБ паків, ~60 МБ дерево): мережевий клон 3,4 с, створення дзеркала 1,6 с, **клон сесії з дзеркала 1,7 с** (на повільному GitHub той самий клон був 140–167 с); 5 сесій паралельно — 11,6 с кожна (запис робочих дерев на HFS+), `git fsck` чистий;
- 5 синтетичних репозиторіїв × 15 сесій паралельно (75 чекаутів): стіна 4,3–6,9 с, чекаут p50 2,3–5,5 с, очікування лока p50 1,1–2,1 с (черга подій Node під 75 процесами git), диск сесій 44,6 МБ проти 51,6 МБ при окремому підрахунку (об'єкти спільні), 0 помилок `fsck`.

**Залишкові ризики.**
- Знімок незакоміченого бере всі не ігноровані файли: великий незаігнорований артефакт збірки потрапить у дзеркало (і в прихований ref на GitHub при закритті картки).
- Дзеркало з refs роботи сесій ніколи не прибирається автоматично (за задумом); refs незмерженої роботи видаленої картки живуть, доки людина не видалить їх.
- Розбіжність визначається за `origin/<гілка>` з дзеркала; якщо fetch дзеркала не вдався, порівняння йде зі старим станом (збережене все одно лишається — нічого не губиться, але повідомлення про розбіжність може не з'явитись).
- Збірка ганяє команди налаштування на хості в шаблонній копії — та сама довіра, що й до команд сесії, але без env-файлів (як і віддалені збірки).
- Збій збереження перед видаленням лишає папку й пише в журнал; у «Потребує вас» він ще не з'являється.

**Відкладено (наступні кроки).** Ліміти присипляння (не більше N активних, сон після простою T, ніколи не присипляти робочу); показ невдалого збереження в «Потребує вас» (зараз — журнал і збережена папка); повідомлення агентові «пісочницю відновлено, ігнорованих файлів і dev-серверів немає»; прибирання прихованих refs на GitHub за віком.

**Альтернативи.**
- `git clone --reference`/`--shared` з дзеркала (backlog) — відкинуто: клон залежить від об'єктів дзеркала, gc чи видалення дзеркала ламає сесії.
- `git clone --mirror` як є — відкинуто: refspec `+refs/*:refs/*` з `--prune` стирає refs роботи сесій, а `remote.origin.mirror=true` робить `git push` дзеркальним.
- Створювати дзеркало синхронно в першій сесії — відкинуто: повний клон великого репозиторію довший за `--depth=1`; першу сесію обслуговує мережевий клон, дзеркало будується у фоні.
- WIP лише на GitHub — відкинуто як основне: мережа на кожен хід. Лише в дзеркалі — не переживає втрату диска; тому обидва: дзеркало завжди, GitHub при присиплянні.

## Що має перевірити тестувальник

Ручні сценарії на Mac mini (корінь пісочниць на `/Volumes/dot`), очікуваний результат:

1. **Перша сесія без дзеркала.** Ход розгортання: «клоную … з мережі»; після неї з'являється `.factory-template/mirrors/github.com/<owner>/<repo>.git`. Друга сесія: «з дзеркала», клон за секунди.
2. **«Зібрати зараз»** у «Середовище › Шаблон»: статус «Збирається» → «Готово», в історії рядок з комітом і тривалістю кожного репозиторію; повтор за розкладом без змін — пропуск (`unchanged`).
3. **Папку сесії видалено посеред сесії** (`rm -rf` вручну) після коміту й незакомічених змін: наступне повідомлення — клон з дзеркала, гілка з комітом, зміни повернулись як незакомічені.
4. **Перезапуск сервера посеред розгортання**: наступна спроба розгортає наново; лок дзеркала, лишений мертвим процесом, забирається (у журналі «stale lock»), не чекаємо 10 хв, якщо pid мертвий.
5. **Перезапуск сервера посеред ходу**: робота до кінця попереднього ходу збережена; після рестарту сесія продовжує в тій самій папці.
6. **Перезапуск посеред збірки**: збірка в історії стає «Невідомо» (≤ 3 хв), наступна будує знову.
7. **GitHub недоступний**: сесія з наявним дзеркалом клонує з нього, у журналі «mirror fetch failed»; перевірка гілки з GitHub падає як раніше («не вдалося зв'язатися з github.com»). **GitHub повільний/завис**: fetch обривається за 60 с < 1 КБ/с, повтор, далі старе дзеркало.
8. **Токен прострочено/відкликано**: fetch дзеркала падає з `no_access`, сесія клонує зі старого дзеркала; збірка — «Помилка» з причиною без токена в тексті.
9. **Дві сесії однієї картки / дві репліки**: обидві готуються, одна чекає на лок дзеркала (у журналі час очікування), дзеркало ціле (`git fsck`).
10. **Диск заповнено**: створення дзеркала падає, тимчасова папка прибирається, сесія — мережевим шляхом; збереження роботи падає → папка картки при закритті **не** видаляється, у журналі причина.
11. **Дзеркало пошкоджене** (видалити пак-файл): сесія — «з мережі», дзеркало в карантині, наступна збірка/сесія створює його знову.
12. **Гілку примусово перезаписано на GitHub, поки картка спала**: відновлення лишає локальні коміти, `origin/<гілка>` — версія GitHub, у чаті «гілка розійшлася з GitHub».
13. **Великий репозиторій**: перше створення дзеркала довге (фонове), сесії не чекають на нього.
14. **Репозиторій прибрано з проєкту**: після наступної збірки й 7 днів без використання дзеркало видаляється (якщо не тримає роботи сесій).
15. **Картку закрито, поки агент працює**: зупинка запуску, збереження роботи (дзеркало + прихований ref на GitHub), лише потім видалення папки; на GitHub `git ls-remote origin 'refs/factory/*'` показує refs.
16. **pnpm-проєкт**: друга сесія ставить залежності без мережі; правка файлу в `node_modules` однієї сесії не змінює той самий файл в іншій.
