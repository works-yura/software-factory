# 0032. Токени інтеграцій належать організації, без токенів розгортання

Дата: 2026-11-12 · Статус: прийнято. ClickUp — зроблено; GitLab (прямий токен) і GitHub (режим токена) — рішення нижче, реалізацію відкладено (див. «Наслідки» і `docs/changes/backlog.md`). Спирається на [ADR-0030](0030-google-sign-in-organizations-invite-links.md) (організації), [ADR-0031](0031-connections-one-list.md) (сторінка «Підключення»), [ADR-0019](0019-observability-accounts-and-bindings.md) (акаунти Google Cloud — взірець).

**Контекст.** Токени ClickUp, GitLab і GitHub без App жили в `.env` розгортання: `CLICKUP_API_TOKEN`; `GITLAB_ACCESS_TOKEN`, `GITLAB_ACCESS_TOKEN_TYPE`, `GITLAB_BASE_URL`, `GITLAB_WEBHOOK_SECRET`; `GITHUB_ACCESS_TOKEN`, `GITHUB_ACCESS_TOKEN_ORG_ID`. Поки організація була одна, це було те саме, що токен організації. З організаціями (ADR-0030) один токен сервера став спільним: ClickUp читав Lists і писав коментарі одним акаунтом для всіх організацій; прямий GitLab має один контекст `direct` на всіх, а webhook з одним секретом розсилає подію всім організаціям; GitHub-токен забирає перша організація, що натиснула Connect. Підключити чи замінити токен міг лише той, хто має доступ до сервера, а не адміністратор організації. Взірець уже був: акаунти Google Cloud організація додає сама, ключ лежить зашифрованим у її рядку `integration_connections`, у env нічого. Рішення людини: «токени інтеграцій більше не беруться з env розгортання; кожна організація підключає їх у налаштуваннях, зашифровано; env-токени прибрати зовсім».

**Рішення.**
- **Токен — підключення організації.** Рядок `integration_connections` (інтеграція, організація), зашифрований `secretEncryption` сховища. Підключає, замінює й відключає його **лише адміністратор організації** на сторінці підключення (Налаштування › Підключення › інтеграція, ADR-0031); учасник бачить стан і акаунт, але не кнопки. Перед збереженням токен перевіряється в провайдера; відмова — 422 з поясненням, що вставити (ClickUp: «personal API token `pk_…` з ClickUp › Settings › Apps»), недоступний провайдер — 502. Токен у браузер не повертається ніколи; сторінка показує акаунт токена (ім'я, Workspaces). Зміни — в аудиті: `factory.integration.token_connected` (з `replaced`, акаунтом) і `factory.integration.token_removed`, без токена.
- **Кожна дія — токеном своєї організації.** Клієнт провайдера будується з токена тієї організації, для якої дія: маршрути — з тенанта запиту, опитувачі — з організації проєкту, диспетчер — з `resolveIntakeDispatch({ orgId })`, агент — з організації сесії. Організація без токена нічого не читає і не пише; опитувач пише це в підсумок проходу (видно в лозі), запити відповідають 409 `…_not_connected`. Запасного токена немає.
- **Env-токенів немає.** Рантайм не читає жодної з цих змінних. У env лишається лише ідентичність розгортання: `GITHUB_APP_*` і `GITHUB_APP_WEBHOOK_SECRET` (він же підписує OAuth state), `MASTRA_PLATFORM_*`, `MASTRA_GITLAB_*`, а також налаштування, що не є обліковими даними (`CLICKUP_POLL_INTERVAL_SECONDS`).
- **Одноразове перенесення, без втрати даних.** Міграція старту `integrations.envTokensToOrg.<інтеграція>.v1` (окрема на кожну інтеграцію, `factory_boot_migrations`): якщо змінна ще задана, а в організації `factory-local-org` (`EXISTING_ORGANIZATION_ID`, власниця всіх даних до організацій) немає свого токена — кладе його туди, пише в лог; уже збережений токен ніколи не перезаписує (лише пише, що env не скопійовано). Ідемпотентна: повтор на іншій репліці нічого не змінює; після мітки більше не запускається. Збій вимикає лише цю інтеграцію на цей старт, наступний старт повторює. Вхідна точка (`apps/server/src/mastra/index.ts`) читає змінні лише щоб передати їх цій міграції (`retiredIntegrationEnv`). **Після першого старту на новій версії змінні можна видалити з env.**
- **ClickUp (зроблено).** Інтеграція встановлюється завжди; без токена організації вона просто нічого не читає. Розмови (ADR-0018): тред — `<taskId>:<commentId>:<orgId>` (організація URI-кодована) — відповідає токен організації, що прочитала коментар; інструмент `factory_conversation_reply` відповідає від організації сесії й відмовляє в треді іншої організації; треди старого вигляду `<taskId>:<commentId>` (у вже запущених сесіях) відповідають від організації сесії. Бот (акаунт токена) — свій у кожної організації.
- **GitLab прямим токеном (рішення).** Підключення організації: токен, тип (`personal`/`group`) і адреса GitLab (`baseUrl`, для self-hosted) — поля підключення, не env. Ідентифікатор підключення — `gitlab-connection:direct:<orgId>` замість спільного `direct`; база інтеграції бере контексти за організацією (`activeContexts(orgId)`, `contextById(id)` перевіряє організацію), `listSources` — лише своєї організації. Збережені рядки встановлень `direct` міграція переносить на `direct:<orgId>` того ж рядка; у `factory-local-org` вони продовжують працювати з перенесеним токеном, рядки інших організацій (що досі користувались чужим токеном) стають «потрібно підключити» — без видалення посилань на репозиторії. **Webhook:** окрема адреса на організацію `/web/gitlab/webhook/:orgId` і секрет, який Factory генерує при підключенні, зберігає в підключенні й один раз показує адміністратору, щоб вставити в GitLab; подія діє лише для організації з адреси, з перевіркою її секрету; без webhook-а працює опитування. Спільного `GITLAB_WEBHOOK_SECRET` немає. e2e підключає підроблений GitLab через API, а не через env.
- **GitHub режимом токена (рішення).** App і Platform лишаються режимами розгортання (env). Без App GitHub — токен організації (`integration_connections`, як ClickUp), а не одна заявка першої організації: `GITHUB_ACCESS_TOKEN_ORG_ID` і запис-заявку прибирає міграція. Ідентифікатор встановлення в режимі токена — від організації (`token:<orgId>`), не id акаунта GitHub, тож дві організації з тим самим акаунтом не збігаються; ланцюжок «встановлення → організація → її токен» для всіх викликів API, clone і push. Опитування — окремий прохід на кожну організацію з токеном (не `projects[0].orgId`); git-ідентичність (автор комітів) — з акаунта токена організації сесії, не на весь процес.
- **Інше, знайдене дорогою:** `/web/github/pat` (токени `gh` CLI для пісочниць) змінює лише адміністратор організації — раніше міг будь-який учасник.

**Наслідки.**
- Організації ізольовані: токен організації А не видно й не використовують для Б; опитувачі та розмови діють лише для організації-власниці.
- Нове розгортання не потребує токенів у env; адміністратор організації підключає все сам у «Підключеннях».
- Наявне розгортання з `CLICKUP_API_TOKEN` після оновлення працює як раніше для `factory-local-org`; інші організації мають підключити свій токен (раніше вони мовчки користувались токеном сервера).
- Доки GitLab і GitHub не перенесено, їхні env-змінні ще читаються, а описані вище витоки між організаціями в них лишаються — див. беклог.

**Альтернативи.** Лишити токен у env і прив'язати до однієї організації (як `GITHUB_ACCESS_TOKEN_ORG_ID`) — відкинуто: працює лише для однієї організації, і змінює його власник сервера, а не адміністратор. Токен у env як запасний для організацій без свого — відкинуто: тихий запасний шлях, той самий витік. Особисті токени людей — відкинуто: інтеграції діють від імені організації, сервісний акаунт переживає зміну людей. Один спільний секрет webhook-а GitLab з пошуком організації за проєктом — відкинуто: один проєкт GitLab можуть підключити дві організації, і секрет однієї підписував би події для іншої.
