# 0041. Агенти працюють від імені окремого користувача macOS

Дата: 2026-11-14 · Статус: прийнято, у роботі (Claude Code, Codex, команди Mastra і збірки — від імені агента; браузер, пристрої, MCP — далі).

**Контекст.** На Mac mini агенти (Claude Code, Codex, Mastra) працюють від імені власника, тобто бачать усе, що бачить він: документи, логіни (`~/.claude`, `~/.codex`, `gh`), базу й `server.env` Factory, код сервера, що працює. Агент може прочитати чи змінити будь-що з цього навіть без злого наміру: через prompt injection у репозиторії чи задачі, через хук git або `postinstall`. Віртуалку відкинуто для активної iOS-розробки: симулятор у ній гальмує, і агент на відео не відрізнить повільний код від повільної віртуалки. Розглянуто sandvault (окремий користувач + `sandbox-exec`, Apache-2.0), Docker Sandboxes (microVM, без Xcode), srt (лише `sandbox-exec`).

**Рішення.**
- **Межа — окремий звичайний користувач macOS** (`FACTORY_AGENT_USER`, на Mac mini — `factory`). Без змінної все як раніше. Систему готують скрипти `scripts/mac-mini/isolation/`: файли сервера лише власнику, сервер лише на `127.0.0.1`, власники на диску `dot` увімкнені й записані явно (`fix-owners`: файли, записані без власників, мають uid 99, і HFS+ віддає їх будь-кому як власнику), теки закриті, користувачу `factory` — лише прохід до `Project/factory/sandboxes` (ACL `search` + успадкована заборона для нових тек), перевірка `check-as-agent.sh` від його імені.
- **Другий шар — профіль Seatbelt**, як у sandvault: запис лише в home агента, теки карток і тимчасові теки; читання жодного home, крім власного; жодних інших дисків, ключниць, сирих дисків, монтування; жодних з'єднань із портами сервера Factory (5874) і налагоджувача Chrome (9222). Профіль належить root і лежить поза досяжністю агента (`/var/factory/agent-<user>.sb`). Для `xcodebuild`/`swift`, які мають власну пісочницю (macOS не вкладає пісочниці), профіль не застосовується — межею лишається користувач.
- **Запуск** (`@factory/agent-user`, переписано з `sv` sandvault на TypeScript): `sudo -n -C 4 -u <user> -- env -i HOME… PATH… sh -c <завантажувач> sandbox-exec -f <профіль> <команда>`. Секрети ніколи не потрапляють у командний рядок (його бачить будь-який локальний користувач через `ps`): оточення йде каналом на fd 3; завантажувач вимагає маркер наприкінці й без нього виходить з 125, а не запускає команду без оточення. `sudo -n` — без пароля, тож без правила sudoers запуск падає одразу, а не чекає.
- **Будова пакета.** Інтерфейси з замінними реалізаціями: `ProcessLauncher` (той самий користувач / шари-обгортки), `CommandWrapper` (sudo, `env -i`, завантажувач, Seatbelt — кожен шар окремо), `EnvTransport`, `SandboxPolicy` (профіль із наборів правил через `SbplProfileBuilder`), `ProcessSignaller` (сервер, агент, обидва), `ProcessSpawner`, `CommandRunner`. Тести: модульні, справжній `sh` для завантажувача й лапок (200 випадкових рядків), справжній `sandbox-exec` для профілю — перевірки втечі sandvault, адаптовані до тек карток на диску даних, — і набір від імені справжнього агента, що вмикається після налаштування системи.
- **Відмінності від профілю sandvault, знайдені тестами й читанням:** теки над текою картки і `/Users` дозволено лише для метаданих (прохід), а не для читання (у sandvault `ls /Users` працює, у нас ні); заборона сирих дисків стоїть після дозволу запису в `/dev` (у sandvault — перед ним, і пізніший дозвіл її перекриває, бо Seatbelt застосовує останнє правило).
- **Зупинка**: група процесів сигналиться двічі — від сервера (доходить до sudo, а він передає своїй команді) і від імені агента через `sudo -u <user> kill -- -<група>` (доходить до всього, що агент запустив).
- **Правило sudoers** (ставить власник, `2-system.sh`): серверу дозволено без пароля лише `env` і `kill` від імені агента та `closefrom_override` для fd 3.

**Підключено** (`FACTORY_AGENT_USER`, `packages/server/src/agent-user`):
- **Claude Code**: CLI через `spawn` пакета; конфіги сесій, `mcp.json`, скрипт gate і теки чату Factory — у `<sandboxes>/.agent-state`, де спільна група з успадкованими ACL дає доступ і серверу, і агенту.
- **Codex**: так само, але без профілю Seatbelt: команди, які він запускає, Codex кладе у власну пісочницю Seatbelt, а macOS не вкладає пісочниці (`sandbox_apply: Operation not permitted`). Межа для самого CLI — користувач. `CODEX_HOME` сесій — у `.agent-state/codex-home`.
- **Mastra**: усі команди `LocalSandbox` (агента, налаштування сесії, git чекауту) йдуть через `processes.spawn` як рядок `sh`; він стає програмою (`ShellCommandBridge`), що відкриває оточення з приватного файлу сервера на fd 3, видаляє файл і запускає той самий ланцюжок. Значення не потрапляють у командний рядок.
- **Збірки шаблону**: команди налаштування (код репозиторію: `pnpm install`, `postinstall`) — від імені агента; git дзеркал лишається серверу.
- **`FACTORY_AGENT_SEATBELT=off`** знімає профіль з усіх запусків: Xcode і SwiftPM запускають власні пісочниці й під нашим профілем не збираються. Тоді межа — лише користувач, і закриті мають бути домашня тека (`chmod 700 ~`) та порти сервера й налагоджувача Chrome (фільтр мережі за користувачем).

**Що лишається.**
- Від імені сервера досі: браузер (Chromium), хаб пристроїв, MCP-сервери, файлові інструменти Mastra (у процесі сервера, межа — тека робочого простору).
- Процеси, що агент лишив після виходу CLI: сервер не бачить їх теки (`lsof`/`ps -E` чужого користувача), тож сон теки їх не знайде. Їх прибирає `AgentReaper` (`packages/agent-user/src/reap`): процес агента не під сервером (за ланцюжком батьків з `ps`) — залишок; вбиває як агент (`sudo -u factory kill`), тож чужих процесів не дістане. При старті сервера — одразу всі; далі щохвилини: 10 хв пільги, поки жодна картка не працює, 6 год максимум. Системні служби macOS користувача (`/System`, `/usr/libexec`, симулятор) не чіпає. `FACTORY_AGENT_REAP=off` вимикає.
- Агенти різних карток — один користувач і бачать оточення одне одного (`ps -E`). Прийнято: картки належать одній організації. Окремий користувач на картку — можливе продовження.
- Проєкти без застосунку (бекенд, документи, сайти) — кандидати на Docker Sandboxes (microVM): ізоляція сильніша, а Xcode там не потрібен.

**Альтернативи.**
- sandvault як є: робоча тека зашита (`/Users/Shared`), блокує всі `/Volumes`, CLI для людини, а не для сервера; патчити 2000 рядків bash — дорожче, ніж перенести потрібне.
- Лише srt / `seatbelt` Mastra: одна пісочниця на тому ж користувачі; не працює з `xcodebuild`; помилка в профілі відкриває все.
- Віртуалка (Tart): найсильніша межа, але симулятор гальмує, і агент неправильно оцінює продуктивність.
