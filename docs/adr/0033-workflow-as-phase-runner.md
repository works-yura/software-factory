# 0033. Workflow як виконавець фази: параметри картки за схемою, граф у Factory, чотири види кроків

Дата: 2026-11-12 · Статус: запропоновано

**Контекст.** Аудит prod-переписок Syncta (`audit-run`, вид `prod-chats`) показав межу «агент сам робить усе через інструменти»:

- Збір даних детермінований (логи, дамп Firestore, інваріанти `check.js`), а агент щоразу «пише» його заново через виклики інструментів. Це повільно, дорого і щоразу трохи інакше. Повний дамп за добу (~1200 повідомлень) через «Базу» не проходить: усе прочитане йде в контекст моделі, а запиту за часом немає (`docs/changes/backlog.md`, «масове читання Бази»).
- Скрипти плейбука (`logs.sh`, `dump.js`, `check.js`) — це по суті workflow, який модель написала сама, але без схем, версій і без місця у Factory.
- Картка — це вільний текст. Вид аудиту агент читає з рядка «Аудит: prod-chats» в описі (`audit-run/SKILL.md:21`). Типізованих полів у картки немає, лише `metadata` (`packages/store/src/work-items/work-item-schema.ts:47`). Шаблон маршруту — лише `titleTemplate`/`description` (`packages/core/src/intake/configs.ts:31-38`).
- Фазу сьогодні виконує лише сесія агента: `phaseRunDecision` повертає тільки `invokeSkill` (`packages/core/src/boards/phase-runner.ts:33-55`).

Що вже є в Mastra (перевірено в коді, `@mastra/core` 1.82.0):

- Workflows: кроки зі `inputSchema`/`outputSchema`/`suspendSchema`/`resumeSchema`, `.branch/.parallel/.foreach/.dountil/.map`, ретраї, знімки запусків у storage, `watch`/`stream`, агент і інструмент як крок. Factory вже має два закодовані workflows (`factory-environment-build`, `factory-intake-route-fire`).
- Динамічні workflows: формат графа (`DynamicWorkflowGraph`), `validateDynamicWorkflow`, `rehydrateWorkflow` (агенти, інструменти й workflows — лише за id із живого реєстру, без `eval`), JSON Schema → Zod. Довільного коду в збереженому графі немає за дизайном. Suspend/resume у збереженому графі «не підтримується» напряму. Версій немає: `upsert` перезаписує. Org/project у визначенні немає.
- Studio UI (`packages/playground-ui/src/domains/workflows`): граф (`WorkflowGraph`), список і деталі запусків, форма відновлення з `resumeSchema`, `DynamicForm` зі схеми. Працює через `MastraClient` і вбудовані маршрути Mastra.
- Агент-будівельник `createWorkflowBuilderAgent` і його playbook — у core (Apache). Обгортка редактора — в `editor/ee` під окремою ліцензією.

**Рішення (запропоноване).**

1. **Параметри картки за схемою.** Виконавець фази (агент чи workflow) оголошує схему входу. Картка отримує поле `inputs`, яке сервер перевіряє за цією схемою; опис лишається текстом для людини. Хто заповнює `inputs`:
   - маршрут — із шаблону (`period = {firedAt − 24h, firedAt}`), без моделі;
   - людина — у формі, яку UI будує зі схеми (`DynamicForm`);
   - модель — лише якщо картка прийшла вільним текстом (ClickUp тощо): витягує параметри, сервер перевіряє; не пройшло — «Потребує вас», запуску немає.

   Те саме і для агентських фаз: вид аудиту, період, плейбук — параметри, а не рядок в описі.
2. **Workflow — граф у Factory з версіями.** Формат графа — `DynamicWorkflowGraph` з core, перевірка — `validateDynamicWorkflow`. Зберігається у власній таблиці Factory (org, project, key, version, status, approvedBy), не в `workflowDefinitions` Mastra. Затверджена версія не змінюється; кожна реєструється в Mastra під незмінним id `fwf_<project>_<key>_v<n>`. Запуск закріплений за версією, тож resume старого запуску не перескочить на новий граф. Між репліками — маркер версії, як у дошок.
3. **Чотири види кроків**, кожен зі схемою входу й виходу, — заздалегідь зареєстровані в Mastra інструменти, на які граф посилається за id (`type: 'tool'`). Scope (org, project, картка) береться з даних запуску, не з контролера сесії:
   - **Крок Factory** (`factory_step:*`) — на сервері, з обліковими даними Factory: `database_export` (вивантаження у файл, назад — лічильники й шлях), групи логів тощо. Ключі не потрапляють у пісочницю.
   - **Код проєкту в пісочниці** (`sandbox_run`) — скрипт із репозиторію проєкту (`check.js`), JSON на вхід і вихід за схемою, великі дані — файлами в папці картки. Тут будь-яка логіка: валідація, фільтри, перетворення.
   - **Агент** (`agent_session`) — відкриває звичайну Factory-сесію в картці (харнес, права, тред), а не голий `agent.stream`. Workflow зупиняється; відновлюється на `agent_end` сесії. Результат — через exit tool фази, чия схема = вихідна схема кроку.
   - **Людина** (`human_input`) — зупинка з формою зі схеми; зупинка = «Потребує вас».
4. **Workflow як виконавець фази.** Новий варіант runner `{ workflow: key@version }` → рішення `startWorkflow` поряд з `invokeSkill` у `phaseRunDecision` і dispatcher. Інваріант «один активний запуск на картку» поширюється й на workflows. Маршрут за розкладом створює картку з `inputs`, як і зараз.
5. **Хто пише workflow.** Модель: скрипти комітить у репозиторій проєкту через PR (рев'ю як звичайного коду), граф пропонує у Factory, людина затверджує версію. Будівельник — `createWorkflowBuilderAgent` з core і його playbook, доповнений нашими чотирма видами кроків; `editor/ee` не беремо. Довільний код ніколи не виконується на сервері з обліковими даними.
6. **UI.** Граф, деталі запуску й форма відновлення — з `@mastra/playground-ui/domains/workflows`, але дані через власні маршрути Factory з авторизацією організації (адаптер замість `MastraClient`). На картці видно граф і хід запуску; агентський крок — звичайна сесія в картці.
7. **Схеми — підмножина JSON Schema** без `oneOf/anyOf/allOf/$ref`: так перевірка на сервері (core `jsonSchemaToZod`, з помилкою) і форма в UI (`jsonSchemaToZodRuntime`) бачать одне й те саме.

**Чому це не суперечить ADR-0002** («дошки — код, не конструктор в UI»). Дошка — процес Factory (фази, ворота), він лишається кодом. Workflow — процедура конкретного проєкту (як зібрати дані Syncta), її пише модель із кроків, які дає код Factory; довільної логіки в графі немає, вона в скриптах проєкту під рев'ю. Конструктора в UI теж немає: граф показується, а не малюється.

**Наслідки.**

- Перший крок Factory — `database_export` (розширює ADR-0027: «База» віддає дані файлом, а не в контекст). Перший workflow — аудит Syncta: `database_export` → `check.js` → групи логів → агент `review` (знахідки за схемою) → звіт → питання щодо P0/P1.
- Поле `inputs` змінює модель картки, маршрутів і форми створення картки; рядок «Аудит: <вид>» стає параметром (міграція наявних карток і маршрутів).
- Агентський і людський кроки як інструменти, що зупиняють workflow, у Mastra для збережених графів не протестовані — потрібні наші тести на цей шлях.
- Нова таблиця версій workflows і маршрути для них; Studio-компоненти потребують адаптера даних.
- Пісочниця прив'язана до сесії, а код-крок — ні: `sandbox_run` має брати папку картки під тим самим замком «один запуск на картку».

**Альтернативи.**

- **Агент робить усе через інструменти (як зараз)** — лишається для разових і творчих задач; для повторюваних процедур відкинуто: дорого, нестабільно, ліміт контексту.
- **Скрипти з ключем у пісочниці** — відкинуто власником для prod: ключ у слабко ізольованій пісочниці.
- **Workflows як TS-код у репозиторії проєкту, що виконується на сервері** — відкинуто: чужий код із обліковими даними Factory.
- **`workflowDefinitions` Mastra як сховище** — відкинуто: без версій (upsert перезаписує), без org/project.
- **Temporal / Inngest / Trigger.dev / n8n** — окремий сервіс; власник не хоче додаткових сервісів, а Mastra workflows уже в стеку разом з UI.
- **Лише декларативний граф без коду** — відкинуто: валідацію, фільтри й перетворення не описати декларативно.

**Відкриті питання.**

1. Де живуть `inputs` для агентських фаз: схема в описі фази дошки (код) чи у виді аудиту (`AUDIT_PROFILES`)?
2. Чи потрібен запуск workflow без картки (маршрут → workflow напряму, якщо звіт не потрібен)?
3. Хто затверджує версію workflow: будь-який admin організації чи лише owner?

**Повернутися,** коли буде готовий `database_export` і перший workflow (аудит Syncta) пройде хоча б тиждень щоночі.
