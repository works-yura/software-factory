# 0019. Логи й креші: багато акаунтів Google Cloud, прив'язки Factory → проєкт

Дата: 2026-11-11 · Статус: прийнято · Замінює в [ADR-0017](0017-observability-firebase.md): «один ключ на організацію», «один проєкт на Factory» і ручний підпис JWT · Коміти: `041f1c7` (сервер), `20e88a9` (UI)

**Контекст.** Перша версія тримала один ключ сервісного акаунта на всю організацію і один проєкт Firebase на Factory. Для нас це не годиться: клієнти різні, їхні проєкти Google Cloud часто в різних організаціях і з різними власниками (Syncta — `syncta-57c6a`, BookFate — `bookfate-prod`). Власник чужого проєкту може не пустити акаунт з іншого проєкту, політика домену може це заборонити. А одна Factory буває потрібна на кілька проєктів (prod і staging). До того ж «Прив'язані проєкти» в UI означали «Factory → проєкт Google Cloud», але читались як щось про Factory.

**Рішення.**

- **Акаунти.** Будь-яка кількість сервісних акаунтів Google Cloud на організацію, кожен із назвою («Syncta», «BookFate») і своїм ключем. Усі ключі — в одному зашифрованому рядку підключення інтеграції `firebase` (`{ accounts: { <id>: { serviceAccount } } }`); у метаданих рядка — назва, `clientEmail`, проєкт ключа, `keyId` кожного, тож список не розшифровує ключів. Окремої таблиці не потрібно.
- **Прив'язки.** Factory → акаунт → проєкт Google Cloud (ID і номер), з перемикачами логів і крешів і застосунками. У Factory їх може бути кілька. Зберігаються в налаштуваннях організації (`{ version: 2, bindings: [...] }`).
- **Відключення акаунта, через який читають прив'язки,** сервер відмовляє (409 з переліком прив'язок), доки запит не скаже `withBindings=true`; UI питає людину й показує, які прив'язки підуть разом з акаунтом. Без несподіваного зникнення.
- **Порт:** `ObservabilityProvider.sourcesFor(scope)` повертає джерело на кожну прив'язку; у джерела є `target { ref, name }` (id прив'язки і проєкт Google Cloud). Інструменти агента мають необов'язковий параметр `project` (ID проєкту або `ref`), обов'язковий, коли проєктів кілька; опис інструмента перелічує проєкти й застосунки; кожен результат містить `project`.
- **Готове рішення для автентифікації:** токени видає `google-auth-library` 11.3.1 (Apache-2.0, офіційна бібліотека Google) — клієнт `JWT` на кожен scope, з кешем токенів. Ручний підпис JWT на `node:crypto` прибрано. Запити до API лишились тонким REST-клієнтом: для Crashlytics v1alpha SDK немає, а `@google-cloud/logging` тягне gRPC і важчий за один виклик `entries:list`, який нам потрібен.
- **Перехід без втрати даних.** Перше читання організації (сторінка налаштувань, сесія агента, будь-який маршрут) перетворює стару форму: ключ `{ serviceAccount }` стає першим акаунтом (назва — проєкт із ключа, id виводиться з ключа, тож повторний прохід дає той самий), кожен мапінг `factories[<id>]` — прив'язкою `bnd-<factoryId>` через цей акаунт. Ідемпотентно; ключ заново завантажувати не треба. Мапінг без ключа лишається прив'язкою з акаунтом `unbound`, яку ніхто не читає, доки людина не вибере акаунт. Не «на старті сервера», бо сховище інтеграцій не вміє перелічити організації — тому при першому читанні кожної.

**Наслідки.** Для кожного клієнта — свій акаунт у його ж проєкті (типово), або один акаунт з ролями в кількох проєктах (можна, але не обов'язково). Factory може читати кілька проєктів; агент тоді мусить назвати проєкт. Двох *провайдерів* в одній Factory (Firebase + Sentry) і далі не можна — це агрегатор, у беклозі.

**Альтернативи.**
- *Ключ на Factory* — відкинуто: той самий ключ потрібен кільком Factory, а одна Factory — кільком проєктам; прив'язка розділяє «хто читає» й «чим читає».
- *Окрема таблиця акаунтів* — відкинуто: рядок підключення вже зашифрований і атомарно оновлюється; ключів на організацію одиниці.
- *`@google-cloud/logging`* — відкладено (див. вище); `google-auth-library` закриває те, що ми писали руками.
