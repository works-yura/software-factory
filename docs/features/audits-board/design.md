# Дошка «Аудити»

Аналіз проєкту лише на читання, вручну або за розкладом ([правила надходження](../intake/design.md)). Рішення — [ADR-0015](../../adr/0015-intake-rules-and-audits.md). Код — `packages/pipelines/src/audits/`, скіл — `packages/harness-mastra/factory-skills/audit-run/`.

## Фази

| Фаза | Вид | Що відбувається |
| --- | --- | --- |
| Вхідні (`intake`) | очікування | Як на кожній дошці: картку створено; правило одразу переводить в «Аналіз» |
| Аналіз (`analysis`) | робоча, **стартує сама** | Скіл `audit-run` у сесії `audit`; закінчує переходом у «Готово» |
| Готово (`done`) | кінцева | Звіт написано. Людина читає його й заводить роботу на «Розробці»; з «Готово» можна знову в «Аналіз» |
| Скасовано (`canceled`) | кінцева | Назад у «Вхідні» |

Окремої фази «Звіт» немає: «Готово» і є «звіт готовий». Перша версія мала «Заплановано» й «Звіт»; під час старту сервер один раз переносить збережені дошки, маршрути, картки й цілі правил надходження: `scheduled` → `intake`, `report` → `done` (`AUDITS_LEGACY_PHASE_RENAMES`).

## Що робить агент

1. Читає картку (опис = завдання; вид аудиту: `Аудит: security` тощо) і чекліст виду через `skill_read`.
2. Читає код і документацію; дозволені лише команди без змін (сканери в режимі звіту, лінтери без `--fix`, `git log`).
3. Кожна знахідка: серйозність, де, доказ, наслідок, що зробити.
4. Звіт — `<docs>/audits/<YYYY-MM-DD>-<тема>.md` за [стандартом](../../rules/docs-standard.md), коміт лише цього файлу в гілку картки, пуш; **PR не відкриває**.
5. Підсумок у чаті (Markdown). Знахідки від порогу профілю — питання людині карткою питань («Потребує вас»). Термінове — до переходу; потім перехід у «Готово».

## Типи аудитів — дані

`AUDIT_PROFILES` (`profiles.ts`): вид, назва, чекліст, поріг терміновості, тема файлу.

| Вид | Чекліст | Термінове від |
| --- | --- | --- |
| `security` | `references/security.md` | high |
| `dependencies` | `references/dependencies.md` | critical |
| `code-quality` | `references/code-quality.md` | critical |
| `docs-drift` | `references/docs-drift.md` | critical |
| `performance` | `references/performance.md` | critical |
| `stability` | `references/stability.md` | high |
| `prod-chats` | `references/prod-chats.md` | high (P0/P1 плейбука) |

Новий тип — рядок профілю + файл чекліста + рядок у таблиці скіла; тест `workspace.test.ts` перевіряє відповідність.

## Prod: переписки й логи (`prod-chats`)

Що реально отримали користувачі продукту в проді за період: переписки з бази й логи навколо них, за **плейбуком самого проєкту** (`<docs>/rules/prod-chat-audit/README.md` або шлях з картки). Чекліст загальний: він не знає схеми бази — її, інваріанти, таксономію й шаблон звіту дає плейбук.

- **Дані — лише інструментами Factory.** Логи — `observability_log_groups` (групи й лічильники, до 5000 записів за виклик: WARNING+ за сервісом, INFO-сигнали через `text`, 5xx через `httpStatusAtLeast: 500`) і `observability_query_logs` (окремі записи). База — read-only інструменти «Бази» прив'язки Google Cloud (MCP Toolbox Firestore, `db-<проєкт>_query_collection` тощо), з маскуванням. Ні ключа сервісного акаунта в пісочниці, ні `gcloud`.
- **Прод лише на читання**; інструменти запису «Бази» мають стояти «Заборонити».
- **Зібране — лише в `.factory/scratch/`** сесії, ніколи в коміт. Якщо в плейбуку є перевірка інваріантів (скрипт над дампом), агент пише дамп у формі, яку плейбук описує, і запускає її в пісочниці.
- **Серйозність:** P0 → critical, P1 → high, P2 → medium; термінове від high, тобто P0/P1 — питання людині («Потребує вас») до переходу в «Готово».
- **Звіт:** `<docs>/audits/<YYYY-MM-DD>-prod-chats.md` у гілку картки, без PR. Переписка — «бізнес …4 останні цифри id», без імен і повних номерів.
- **Період:** з картки; інакше 24 год до `intakeRouteOrigin.firedAt` картки за розкладом.

Обмеження «Бази» (Toolbox 1.16, перевірено на емуляторі Firestore): немає collection group і курсора сторінок; фільтр за полем-часом не спрацьовує — агент сортує за ним (`orderBy … DESCENDING` + `limit`) і відсікає сам; усе прочитане йде в контекст моделі, тож за активний день читається вибірка, а не все. Масове читання — у [беклозі](../../changes/backlog.md).

### Приклад: щоденно о 00:00 за Києвом

Налаштування › Надходження задач › «Додати маршрут»:

| Поле | Значення |
| --- | --- |
| Коли | За розкладом |
| Розклад | Щодня, `00:00` (або cron `0 0 * * *`) |
| Часовий пояс | `Europe/Kyiv` |
| Куди | Аудити › Аналіз (стартує сам) |
| Назва картки | `Аудит prod-переписок {date}` |
| Опис | див. нижче |
| Репозиторій | порожньо (усе середовище: docs + код бекенду) |
| Перекриття | `skip-if-open` |

```text
Аудит: prod-chats
Плейбук: rules/prod-chat-audit/README.md (репозиторій документації).
Період: 24 години до запуску маршруту.
Прод лише на читання; дані — тільки інструментами Factory (логи Google Cloud, «База»).
Звіт: audits/{date}-prod-chats.md. P0/P1 — питанням до людини.
```

Передумови: прив'язка Google Cloud цієї Factory з «Логи» і «База (Firestore)»; акаунт з `roles/logging.viewer` і `roles/datastore.viewer`; у «Базі» інструменти `add_documents`, `update_document`, `delete_documents` — «Заборонити».
